# 進捗の判定基準

`docs/progress.md` の各セルをどう決めるか。**推測で埋めない。**
どの材料からその判定になったかを説明できないセルは `❌` にして、理由を補足列に書く。

## 記号

| 記号 | 意味 | 集計での重み |
|---|---|---|
| `✅` | 完了。シナリオが全て `実装済` で、対応するテストがある | 1.0 |
| `🟡` | 一部のみ。機能の一部だけ実装、またはシナリオの一部が `未着手` / `保留` | 0.5 |
| `❌` | 未着手。シナリオ文書もテストも無い | 0 |
| `—` | 対象外。**分母から除外する** | — |

## 集計の単位はセル

**進捗は行ではなく「行 × 軸のセル」で数える。**

| 用語 | 定義 |
|---|---|
| 有効セル | その行の 4 軸のうち `—` でないセルの数 |
| 達成セル | `✅` 1.0 + `🟡` 0.5 の合計（小数第 1 位まで） |
| 残セル | 有効セル − 達成セル |
| 進捗率 | 達成セル ÷ 有効セル（小数第 1 位を四捨五入して整数 %） |
| 完了行 | `—` を除く全軸が `✅` の行。集計表に**列として残す** |

行を単位にすると、**実装と単体テストを入れて E2E を後回しにした行が 0 のまま**になる。
並行セッションではその進み方が普通に起きるので、手が動いているのに数字が動かない表になり、
進捗の記録として役に立たない。セル単位なら 4 軸のうち 2 軸で 50% と出る。

完了行を残すのは、セル単位の進捗率だけだと「どこまで一気通貫で終わったか」が見えないため。
**納品判断に使うのは完了行、作業量の把握に使うのは達成セル**と役割を分ける。

## 残作業の分類

**達成セルは「どこまで来たか」しか語らない。残セルは 1 つずつ中身が違うので、
そのまま速度で割れない。** 残セルを持つ行に 2 つのタグを付け、`docs/progress.md` の
`## 残作業の内訳` に書く。**完了した行にはタグを付けない**（意味が無いうえ、毎回の付け直しが増える）。

### タグ 1 — 作業類型

過去の速度が使えるのは、**同じ類型を一度作り終えている**ときだけ。
根拠列に **`実測`** か **`仮定`** を必ず書く。観測ゼロの類型に較正済みの見た目を与えないため。

| 類型 | 中身 | 根拠 |
|---|---|---|
| 実API追加 | 4 軸のうち E2E(実API) だけが残っている行 | 実測 |
| CRUDマスタ | `useCrudList` + `MasterFormDialog` が効く 一覧・追加・編集・削除 | 実測 |
| 検索一覧 | 絞り込みと結果一覧だけの画面 | 実測 |
| 共通部品 | 画面を持たない `## 共通基盤` の行 | 実測 |
| 入力フォーム | 検証付きの入力と、確認 → 完了の多段遷移 | 仮定 |
| タブ詳細 | 1 画面に複数タブ、タブごとに別 API | 仮定 |
| ファイル取込 | CSV のアップロード / ダウンロード / 事前検証 | 仮定 |
| 運用操作 | 状態を切り替えて履歴を残す操作（停止・再開・締め・取消） | 仮定 |

**仮定の類型が実測に変わる唯一の方法は、その類型を 1 本作り終えること。**
1 本目が入った回に、この表の根拠列を `実測` へ書き換える。
**根拠が `仮定` のままの類型に、実績から出したように見える倍率を書かない。**

### タグ 2 — バックエンド成熟度

その行が使うエンドポイントを `docs/api/openapi.json` と
[api-spec-sync/checklist.md](../api-spec-sync/checklist.md) の仕様ギャップ実測で判定する。
**画面名からの推測で決めない。** パスを引き当てられなければ `D` にする。

| 段階 | 判定 | 扱い |
|---|---|---|
| `A` 確定 | パスがあり、レスポンスの中身に型が付いている | 着手可能 |
| `B` 型のみ | パスはあるが中身が自由形式、またはエラー応答が未宣言 | 着手可能・往復 1 回を見込む |
| `C` 未定義 | パスはあるがレスポンスの中身が未定義 | **ブロック残** |
| `D` パス無し | `openapi.json` に該当エンドポイントが無い | **ブロック残** |

API を使わない行（共通レイアウトの表示のみ 等）は `—` とし、着手可能に数える。
**要件そのものが未確定の行**（モックに「要件整理中」と書かれている 等）は、
成熟度が `A` でも**ブロック残**に入れ、ブロック理由列にそう書く。

### 着手可能残とブロック残

```text
着手可能残 = A / B / — の行の残セル（要件が確定しているもの）
ブロック残 = C / D の行の残セル + 要件未確定の行の残セル
着手可能残 + ブロック残 = 残セル
```

**ブロック残を分母から外さない。** 外すと作るべき総量が見えなくなる。割って出すことで、
**「いま手を増やしても消化できない量」**が読める。これが行ベースでもセル単位の合計でも出てこない。

## 行を立てる基準はモック

**モックとはモックリポジトリ `../premarket-order-202609` のことで、公開モックのブラウザ表示
ではない。** 画面の実体は FastAPI + Jinja2 のテンプレートで、分母の出どころは 2 つ。

| 出どころ | 取れるもの |
|---|---|
| `python_app/templates/base.html` | サイドバーの区分と項目（`sidebar-section` / `sidebar-link`） |
| `python_app/routers/*.py` | サイドバー外の画面（`@router.get` と `_resp(request, "<template>.html", ...)`） |

`client/`（React の雛形）は未使用なので見ない。取り方は
[SKILL.md](SKILL.md) の手順 2。

**表に立てる行はモックにあるものだけ。** モックにあって開発環境（`navigation.js` /
`router/index.js` / `src/views/`）に無いものは、`❌` の行として立てる（未着手であって
対象外ではない）。逆に開発環境にだけあってモックに無いものは、行を作らない。

**モックが変わっても判定は下げない。** 実装済み（`✅`）の画面のモックが差分に出たときは、
`## モック差分（前回確認以降）` の節と補足列に `モック更新あり・追随未確認` と書くにとどめる。
実装が実際に古いかはコードを読まないと判らず、自動で下げると進捗率が根拠なく揺れる。

例外は `## 共通基盤` の区分（共通レイアウト / UI 部品 / マスタ共通部品 / 共通ロジック /
API クライアント層 / MSW モック基盤 / アクセス制御）。モック画面を成立させる土台なので、モックに
画面として現れなくても数える。

## モック由来でない追加要件行

**ユーザが「実装すべき機能」として指示した行は、モックに無くても分母に残す。**
モックは画面の分母であって要件の全量ではなく、横断機能（権限・ヘッダの表示物など）は
テンプレートを読んでも出てこない。`## 対象外の画面` には**入れない**（記録用であって
分母から外す節なので、要件を入れると進捗が過大に出る）。

置き場所は `## 共通基盤`。画面列には区分名を書き、補足列の末尾に
**`要件指示（モック外）`** と書いて、モック差分で消してよい行と区別する。

現在の対象は次の 2 行（2026-09-17 にユーザ指示で追加）。**次回以降の実行でも消さない。**

| 画面 | 機能名 | 由来 |
|---|---|---|
| アクセス制御 | 権限によるアクセス制限 | ロール（発注権限 / マスタ更新権限 / 発注停止権限）でメニュー・ルート・操作ボタンを出し分ける。`マスタメンテ / 権限マスタ` の実装と対 |
| 共通レイアウト | 市場取引時間の表示 | ヘッダに米国市場の取引時間帯を現地時刻・日本時刻で出す。既存の `市場ステータス表示`（開場 / 閉場の状態）とは別の行 |

`アクセス制御` は画面ではなく横断機能だが、**E2E(実API) は `—` にしない**
（権限 API に依存し、実 API で確かめる余地がある）。`市場取引時間の表示` は
他の `共通レイアウト` 行と同じく E2E(実API) を `—` にする。

要件行を増やすときも同じ形にする。**ユーザの指示が根拠で、推測で足さない。**

## 分母から外すもの

2 段階ある。混同しない。

1. **行ごと** — `## 対象外の画面` に置いた行は、行数にも有効セルにも入れない。
   ここに置けるのは**モックに無いのに記録として残したい行**だけで、いまの対象は
   `/`（注文一覧）と `/dev/ui-catalog`（UI カタログ）の 2 行。前者は実仕様が来たら
   差し替える参考実装、後者は開発用ページで、**どちらも納品対象ではない**。
   原則はモックに無い行を載せないことなので、**この節を増やさない**
2. **セルごと** — `—` を書いたセルは、その軸の分母からも有効セルからも除く
   （例: 実 API を叩かない行は E2E(実API) の分母に入れない）

モックに載った画面をあとから対象に加えるときは、`## 対象外の画面` から該当の節へ行を移す。
そのとき完了日・更新日も一緒に運ぶ。

## 列ごとの判定

| 列 | `✅` | `🟡` | `❌` | `—` |
|---|---|---|---|---|
| 実装 | `src/router/index.js` にルートがあり、対応する view にモックの当該機能の UI がある | 画面はあるが当該機能が未実装（例: 一覧はあるが編集が無い） | ルートが無い（`NotFoundView` に落ちる）。`navigation.js` に項目すら無い場合も同じく `❌` とし、補足列にそう書く | 画面を持たない行では使わない |
| UnitTest | `docs/unit/<...>.md` に当該機能のシナリオがあり全て `実装済`、`check:scenarios` が対応テストを `✓` にする | 一部が `未着手` / `保留`、または機能の一部しかシナリオが無い | シナリオ文書が無い、またはテストファイルが無い | 単体で確かめる対象が無い行（純粋な導線のみ 等） |
| E2E(MSW) | `docs/e2e/<画面>.md` に当該機能のシナリオがあり全て `実装済` | 同上 | 文書が無い | 画面から到達できない行 |
| E2E(実API) | `docs/e2e/<画面>-real-api.md` にあり全て `実装済` | 同上 | 文書が無い | 実 API を叩かない行（UI カタログ / UI 部品 / 共通レイアウト） |

## シナリオ表の「状態」欄だけを見ない

`docs/e2e/` と `docs/unit/` の状態欄は、**文書に書かれた範囲が終わっているか**しか語らない。
文書に書いていない機能は表に現れないので、状態欄だけを数えると進捗が 100% に見える。

**分母は画面と機能**であり、`✅` の根拠がシナリオの状態欄なら、`❌` の主な根拠は
**シナリオ文書が存在しないこと**になる。両方を見る。

`check:scenarios` の警告（`「未着手」でテスト未作成`、`ID の無いテストが N 件`）は
`🟡` の根拠として使える。error（`「実装済」ですが対応するテストがありません`）が出ている場合は、
その行を `✅` にしない。

## 日付

### 完了日

`—` を除く 4 軸が全て `✅` になった**最初の日**。次の順で決める。

1. 前回の `docs/progress.md` に値があれば**そのまま引き継ぐ**（再計算しない）
2. 前回が `-` で、今回はじめて全軸 `✅` になったなら、その行の関連ファイルの**最新コミット日**を入れる
3. まだ揃っていなければ `-`

**初回生成（前回の表が無い）だけは事情が違う。** すでに揃っている行がいつ揃ったかは
遡って特定できないので、最新コミット日を**上限値**として入れ、補足列に
`初回生成時の推定` と書く。以降の実行ではこの値が 1. で引き継がれるので、推定は 1 回で止まる。

一度入った完了日は、あとで判定が下がっても**消さない**。下がったことは補足列に書く
（完了日を消すと「いつ一度は揃ったか」が失われる）。

### 進捗の履歴

`## 進捗の履歴` の行（生成日ごとの 有効セル / 達成セル）は、**完了日と同じく前回の
`docs/progress.md` からそのまま引き継ぐ。過去行を書き換えない。**
この表が `## 進捗の推移と完了予想` の折れ線の唯一のデータ源で（SKILL.md の手順 7）、
毎回作り直すと過去の点が動いてグラフが信用できなくなる。

完了日を折れ線に使わないのは、**完了日が全軸の揃った行にしか付かない**ため。
「実装と単体は入れたが E2E は後回し」という進み方がグラフに現れず、
セル単位にした集計と食い違う。

### 更新日

完了日が入っている行に、**完了日より後**の関連コミットがあり、いまも全軸 `✅` のとき、
その最新コミット日。無ければ `-`。

### バックエンド待ち

`## バックエンド待ち` の行は、**完了日と同じく前回の `docs/progress.md` からそのまま
引き継ぐ。過去行を書き換えない。**

| 列 | 中身 |
|---|---|
| 発生日 | フロント側がバックエンドの不備・未実装に当たった日。シナリオを `保留` にした日、または判定を上げられないと判断した日 |
| 解消日 | バックエンドが直り、こちらの追随が終わった日。未解消なら `-` |
| 影響する行 | `<画面> / <機能名>`。複数あれば `・` で並べる |
| 内容 | 何が足りないか。1 行 |
| 状態 | `待ち` / `解消` |

行を立てる根拠は、`docs/e2e/*.md` の `保留` シナリオとその理由節、各行の補足列、
[api-spec-sync/checklist.md](../api-spec-sync/checklist.md) の未解決項目。**推測で足さない。**

解消日が入った行から **1 往復あたりのリードタイム**（発生日 → 解消日の営業日数）が貯まる。
**実測が 1 件も無いうちは推測値を置かない。**
「未解消 N 件・最長 M 営業日経過（上限不明）」とだけ書く。

### 手戻りは速度に織り込み済み

仕様の取り込みで**既に `✅` のセルを作り直す**作業（パスの移行、クエリ名の改名、
API に無い項目の取り消し）は手戻りで、実際に起きている。

ただし `## 進捗の履歴` から取る速度 `v` は、**その手戻りが起きた期間の実績**なので、
`v` には手戻りが既に含まれている。**完了予想で手戻りを別枠に足さない**（二重計上になる）。

手戻りは記録としての価値があるので、実測値だけ `## 残作業の内訳` の下に書く。
測り方は **その取り込みの追随コミットが触ったファイルを持つ 行 × 軸 のセル数 ÷ その時点の達成セル**。
追随コミットはパス指定ではなく件名で拾う（`fix:` / `refactor:` のうち、API 仕様の
取り込みコミットの直後にパス・クエリ名・項目の削除を扱ったもの）。

### 関連コミット日の取り方

**パス指定で機械的に取る。** コミット件名との対応づけを推測しない
（件名は「受注不可日マスタの削除を実装する」のように機能単位だが、機能名の表記ゆれで簡単に外れる）。

1 行ぶんの関連ファイルは、view / store / api / spec / シナリオ文書。

```bash
git log -1 --date=short --pretty=format:'%ad %s' -- \
  src/views/BlackoutDateListView.vue \
  src/views/BlackoutDateListView.spec.js \
  src/stores/blackoutDates.js \
  docs/e2e/blackout-dates.md \
  docs/unit/views-blackout-date-list-view.md
```

- `--pretty=format:'%ad %s'` は**クオートする**。`%ad|%s` のようにパイプを裸で書くと
  シェルがパイプとして解釈する
- `-1` で最新 1 件。完了日を新規に入れるときは、その行の**全軸が揃ったコミット**が知りたいので、
  4 軸のうち最後に揃った軸のファイル（多くは E2E か実 API のテスト）を指定する
