## A. 退行・不整合の修正

### #17 スライス基準マスタの更新が最新の `更新日時` を送っても 409 になる（退行）

**現象（2026-09-25 実測）**

1. `GET /masters/hard-limits` で `更新日時`（`2026-08-26T00:00:00`）を取得する
2. その値をそのまま添えて `PUT /masters/hard-limits` を送る
3. 409「他のユーザーによってスライス設定が更新されました」が返る

画面からの保存も、テストからの API 直叩きも同じ結果です。
2026-09-17 からこの操作の実 API E2E は通っており、フロント側の送出内容は変えていません。
バックエンドの 2026-09-24 の変更（Phase 39〜45）以降に出たと見ています。

**お願い**

楽観ロックで比較している値が、`GET` が返す `更新日時` とずれていないか確認をお願いします
（例: 秒未満の切り捨て、タイムゾーン変換、比較対象の列違い）。

フロント側では回避しません（`更新日時` を送らない等で通してしまうと楽観ロックの意味が無くなるため）。

**回答欄**:

### #18 受注不可日の事前検証（`validate`）が日付の変更を弾く（`PUT` との不整合）

**現象（2026-09-25 実測）**

- `POST /masters/blackout-dates/validate?blackout_date_id=<id>&is_update=true` に、本文の `受注不可日` を ID の指す日付と**別の日付**で送ると 400
  「IDが指す受注不可日（20350101）とリクエストの受注不可日（20350102）が一致しません。」
- 一方 `PUT /masters/blackout-dates/{blackout_date_id}` は、ID から旧日付・本文から新日付を取り、**日付の変更を受け付ける**
  （`BlackoutDateRequest.受注不可日` も required）

画面は「事前検証を通ったら PUT」の順で動くので、**日付を変える編集が実 API では必ず事前検証で止まります**。

**お願い（どちらかの方針で揃えてほしい）**

| 方針 | バックエンド | フロント |
|---|---|---|
| (a) 日付の変更を許す | `validate` も `PUT` と同じく、本文の日付を「変更先」として扱う | 変更なし |
| (b) 日付の変更を許さない | `PUT` でも日付の変更を弾く | 日付欄を読み取り専用にする |

## B. 方針の確認

### #19 `GET /masters/symbols` の `symbol` を Ticker にも当ててほしい

**現象（2026-09-25 実測）**

| リクエスト | 件数 |
|---|---|
| `GET /masters/symbols?symbol=AAPL`（Ticker） | 0 件 |
| `GET /masters/symbols?symbol=A0030`（銘柄コード） | 1 件 |
| `GET /masters/symbols?ticker=AAPL` | 1 件 |
| `GET /masters/ca?symbol=AAPL` | 3 件 |
| `GET /masters/balance-adjustments?symbol=AAPL` | 5 件 |

CA マスタ・残高マスタの `symbol` は description どおり「銘柄コードまたは Ticker」に当たりますが、
**銘柄マスタだけ銘柄コードにしか当たりません**。

画面の検索欄「銘柄コード・ティッカーコード」は 1 つで、値を `symbol` に乗せているため、
実 API では Ticker 検索が黙って 0 件になります。

**お願い**

銘柄マスタの `symbol` も CA・残高と同じく Ticker に当ててほしいです。
「当てない」方針であればその回答をください（フロントが検索欄を銘柄コードと Ticker に分けます。`ticker` クエリは効いています）。

**回答欄**:

### #20 `POST /masters/balance-adjustments` の `銘柄コード` に Ticker を受けるか

**現象（2026-09-25 実測）**

| `POST /masters/balance-adjustments/validate` の本文 | 結果 |
|---|---|
| `銘柄コード: "AAPL"`（Ticker） | 400「指定された銘柄コードが存在しません: AAPL」 |
| `銘柄コード: "A0030"`（銘柄コード） | 通る（`details` に `Ticker: AAPL` が付く） |

画面の新規追加はティッカー入力をそのまま `銘柄コード` に載せているため、
**実装済みの「残高マスタ / 新規追加」が実 API では必ず失敗します**。

**お願い（二択）**

- (a) バックエンドで `銘柄コード` に Ticker も受ける（銘柄コードに解決する）
- (b) 受けない。フロントが `GET /masters/symbols?ticker=` で銘柄コードに引き直してから送る

回答が無ければ (b) で進めます。

### #15 履歴の `変更前データ` / `変更後データ` / `差分データ` の中身の型

`SuspensionHistoryItem` / `AnnouncementHistoryItem` のこの 3 項目が `anyOf: [{}, null]`（any）です。
障害管理の**停止理由は履歴の独立項目に無く、この中にしか無い**ので、フロントは次の形を前提に読んでいます。

```json
{
  "変更後データ": { "発注停止フラグ": true, "停止理由": "システム障害のため" }
}
```

お知らせ管理も同様に `{ "表示フラグ": true, "本文": "…" }` を前提にしています。
この形で合っているか教えてください。できればスキーマに型を付けてほしいです。

### #12 `/market-status` のセッションコードに enum 宣言を付けてほしい（優先度低）

`現在のセッション`（`PRE` / `REGULAR` / `AFTER` / `BEFORE_OPEN` / `CLOSED`）と `MarketSessionItem.code` がどちらも素の `string` で、
値の体系が description の文章にしかありません。綴りが変わっても契約テストで検知できないので、enum として宣言してほしいです。

フロントは表示の主判定を `JPN開始` / `JPN終了` の時刻比較に寄せてあり、未知の綴りが来ても壊れません。

**回答欄**:

### #16 発注再開に理由を残す要件があるか

`ResumeRequest` に理由の項目が無く、履歴には「誰がいつ再開したか」しか残りません（停止理由は再開後も直前の値を保持）。
障害報告で**再開の判断根拠を残す要件**があれば項目の追加が要ります。無ければ現状のままで進めます。
