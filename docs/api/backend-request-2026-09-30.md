## A. 不整合の修正

### #21 `limit` の無い一覧・履歴 4 本に `limit` を足してほしい

次の 4 本は `offset` しか持たず、`?limit=2` を送っても無視されます（9/30 実測で、受注不可日は応答が `limit: 50` のまま）。
ほかの一覧・履歴はすべて `limit` を持っています。

| エンドポイント | 使う画面 |
|---|---|
| `GET /masters/blackout-dates` | 受注不可日マスタ（一覧） |
| `GET /customers`（注文画面用） | 新規注文（顧客検索） |
| `GET /masters/customers/{account_id}/history` | 顧客マスタ（履歴） |
| `GET /masters/blackout-dates/{blackout_date_id}/history` | 受注不可日マスタ（履歴） |

一覧の件数はフロントが決めて `limit` で送る方針にしました（2026-09-28）。他の一覧と同じく `limit`（1〜200・既定 50）を足してほしいです。
いまは受注不可日だけがこの方針に従えず、50 件固定のまま残っています。

**回答欄**:

### #28 注文取消（`POST /orders/{order_id}/cancel`）の 2 点

1. `responses` に **400 / 404 が宣言されていません**（9/30 時点で 200 / 422 だけ）。実装は `ValueError` を 400 で返し、description にも「取消不可（400エラー）」とあります。
   `amend` と同じく `ErrorResponse` を宣言してほしいです。
2. `OrderCancelRequest.取消者` の既定値が `"user"` なので、**誰が取り消したかが記録に残りません**。`amend` と同じく `X-User-Code` / セッションから解決してほしいです。
   フロントは `取消者` も `理由` も送りません（`理由` は削除予定と伺っています）。

`status` の複数指定（旧依頼の ①）は、Phase 55 の `GET /orders` の改修で解消しました。

**回答欄**:

### #29 みずほ注文締めの `実行者` を認証情報から解決してほしい

`POST /closing/mizuho` と `/closing/mizuho/reset` は、本文の `ClosingActionRequest.実行者` をそのまま `d_締め管理` に記録し、省くと `'SYSTEM'` になります
（`X-User-Code` / セッションは権限判定にしか使っていません）。画面から任意の値を送れるので、監査上の記録として信用できません。

発注停止（`/operations/order-suspensions/*`。未指定時は認証情報から解決）と同じく、操作者を認証情報から取る形にしてほしいです（本文の `実行者` は廃止か無視）。
いまのフロントは、`X-User-Code` と同じ値を本文の `実行者` に載せています。サーバで解決するようになったら本文から外します。

## B. 方針の確認

### #24 新規注文の送信で未確定の 5 点

| # | 論点 | フロントのいまの扱い |
|---|---|---|
| ① | `POST /orders/validate`・`POST /orders` の**業務エラー**（残高不足・売買規制・発注停止中など）を、200 の `valid:false` / `success:false` で返すのか、4xx で返すのか（宣言されている応答は 200 と 422 だけ） | どちらでも止まるように作っている（200 の不合格は「入力エラー」の帯、4xx / 5xx は通信エラーの帯） |
| ② | **`強制区分` の値の体系**（0 / 1 だけか）と、フロコン警告を強制区分付きの検証でどう返すか（`valid:true` で `warnings` を残すのか、消すのか） | 警告が返ったら強制区分を付けて送り直させる。`warnings` があっても `errors` が空なら確認画面へ進む |
| ③ | **`作成者`（必須）・`受注者`（任意）はフロントが埋めるのか**、`X-User-Code` から解決されるのか | どちらもログイン中の社員コードを送る |
| ④ | **`預り売買区分` の 0 / 1 の向き**。csv-spec は「0: 特定, 1: 非特定」だが、`SpecificDepositEnum` を使う残高マスタ（`特定預り区分`）とフロントの写しは「0: 非特定, 1: 特定」で逆。同じ意味の区分なのか | csv-spec に従い、「一般」を `1` で送る |
| ⑤ | **`証券受渡方法` の既定**（画面に欄が無い。画面モックは初期値が当社保管 `100`、実際の送信値が他社保管 `500` で食い違う） | `500` で送る |

Phase 58 で追加された重複確認（`重複確認区分`）は、フロントで別途対応します。

### #1② 確認 CSV（TWS の約定コンファメーション）の取込

9/29 に 2 点のご質問をいただきました。

**(1) TWS CSV の列仕様（サンプル 1 件）**

画面モックに入っているサンプルの実物は次のとおりです。

```text
order_id,confirmation_ref,confirmation_status,filled_quantity,average_price,confirmed_at,message
6,TWS-20260904-0006,CANCELLED,0,0,2026-09-04 10:15:00,TWSで取消確認
```

フロントは 2026-09-28 に、この列を前提にした取込の形を先に作っています（MSW で動かしているだけで、確定ではありません）。

```text
POST /operations/stalled-orders/confirmation-import
Content-Type: multipart/form-data
  file: コンファメーション CSV（UTF-8。BOM の有無はどちらも可）

200 → 既存の CsvImportResponse をそのまま使う
400 → 空ファイル・ヘッダ不一致・データ行なし（detail）
422 → file 欠落（FastAPI の検証エラー）
```

| 論点 | フロントの仮置き |
|---|---|
| `confirmation_status` の値 | `FILLED`（約定）/ `CANCELLED`（取消）→ 滞留一覧から外す。`WORKING`（注文中）/ `PARTIALLY_FILLED`（一部約定）→ 注文中へ移す。サンプルに出るのは `CANCELLED` だけで、**残りの値は推測です** |
| 行エラーの扱い | 1 行でも不備があれば 1 行も反映しない |
| 項目名 | `file`（既存の `/masters/*/import-csv` と揃える） |

**(2) 「確認済み」が業務上何を意味するか**

（要記入: 約定の照合なのか、発注が通ったことの確認なのか。フロントの手元の資料からは確定できないため、業務側に確認のうえ記入する）

約定の照合であれば、ご提案のとおり既存の `d_約定`・処理状況（010 / 011 / 020）に乗せる形で構いません。その場合、フロントは `確認状況` を使わず、処理状況で滞留一覧から外れる形に合わせます。

### #26 約定の預託先（注文ルート）をロールで制限してほしい（要件）

預託先は、管理者（`manager`）と管理責任者（`supervisor`）にだけ見せる要件です（画面モック `routers/executions.py` の `can_view_depositary`）。
いまの `GET /executions` と `GET /executions/export-csv` は、ロールに関係なく `注文ルート` / `注文ルート名` を返し、`route` の絞り込みも受け付けます。CSV には「預託先」列が常に入ります。

1. 見られないロールには、一覧・CSV とも預託先を返さない（CSV は列ごと落とす）
2. 見られないロールが `route` を指定したら、無視するか 403 にする
3. `PermissionFlags`（`/auth/me`。いまは `order` / `master` / `operation` / `branch_all`）に預託先の参照権限を足すか、ロールで固定するか

を決めて実装してほしいです。いまは画面側だけで出し分けていて（ロールが manager / supervisor のときだけ検索欄と列を出す）、API を直接呼べば取れます。
