## 2. 優先度「高」

### #23 操作ログの `操作区分` が一覧と絞り込みで食い違う（改修 または 方針回答）

**いま起きていること**（2026-09-29 に実測し、9/30 にも再現）

- `GET /operations/activity-logs` の一覧は、障害管理の `SUSPEND` / `RESUME` と、お知らせ管理の `SHOW` / `HIDE` を `操作区分` として返します
- 同じ API に `?operation=SUSPEND` を送ると 400（`指定可能: CREATE, UPDATE, DELETE, BATCH`）になります
- `ActivityLogItem.操作区分` の description にも 4 種（CREATE / UPDATE / DELETE / BATCH）しか書かれていません

そのため、**発注停止とお知らせの操作ログを操作区分で絞り込めません。**

**お願い**: 次のどちらの方針かを教えてください。

- (a) **区分を増やす**: `SUSPEND` / `RESUME` / `SHOW` / `HIDE` を `operation` で指定できるようにし、description（できれば enum）と指定できる値に反映する
  → フロントは画面の選択肢と表示名（停止 / 再開 / 表示 / 非表示）を足します
- (b) **4 種に寄せる**: 一覧が返す値を 4 種のどれかに寄せる（例: 停止・再開・表示・非表示は `UPDATE`）
  → フロントの変更はありません

**あわせて確認（優先度は低）**: `GET /operations/activity-logs/targets` の対象種別コードは、`schedule_times` だけがアンダースコアで、ほかはハイフン区切り（`order-suspensions` など）です。動作には影響しませんが、揃える予定があれば早めに知りたいです。

**フロントのいまの扱い**: 区分は 4 種のまま。知らない値（`SUSPEND` など）は英語のまま表示しています。

**回答欄**:

## 3. 画面項目の不足と性能（追加・改修のお願い）

### #31 一覧 API が行ごとに `codes.json` を読み直していて遅い（改修・性能）

**いま起きていること**（2026-10-01 に実測）

画面の初回表示を測ったところ、注文照会・注文一覧が約 2.2 秒、顧客マスタが約 1.3 秒かかり、その大半が API の応答待ちでした。
フロントを通さず API を直接叩いても同じ時間がかかります。

| API | 応答時間（直接・3 回） |
|---|---|
| `GET /orders?limit=50` | 1528 / 1911 / 2293 ms |
| `GET /masters/customers?limit=50` | 577 / 691 / 695 ms |
| `GET /masters/symbols?limit=50`（比較用） | 113 / 132 / 175 ms |

`api` コンテナの中で `list_orders` を段階ごとに測ると、SQL は合計 5 ms 程度で、時間のほぼすべてが行ごとの名称付与でした。

```text
search_orders (COUNT + 明細)     3 ms
summarize_orders                 1 ms
_fetch_fx                        1 ms
enrich_order × 50 行          2040 ms
  うち CodeMaster() × 100 回   1573 ms（1 回 約 16 ms）
```

**原因**: `CodeMaster.__init__`（`app/config/code_master.py`）は、作るたびに `codes.json` を開いて読み込みます。
`enrich_order` と `derive_quantity_breakdown`（`app/services/order_list_service.py`）が 1 行ごとに `CodeMaster()` を作るため、50 行で 100 回読み込みます。
顧客マスタも `attach_customer_display_fields`（`app/services/customer_service.py`）が 1 行ごとに作っています。

ローカルは `.:/app` のフォルダマウント越しなので 1 回の読み込みが特に重くなりますが、本番でも行数（`limit` は最大 200）に比例する無駄は残ります。

**お願い**: `codes.json` をプロセスで 1 回だけ読む形にしてください（例: モジュール単位で `CodeMaster` を 1 つ作って共有する、読み込みを `functools.lru_cache` で包む）。
`CodeMaster()` は 15 ファイル・39 か所で使われているので、`CodeMaster` 側の 1 か所を直せば、ほかの一覧 API にも効く見込みです。

**フロントのいまの扱い**: 手を入れていません（フロントでは速くできません）。起動時の API 5 本と画面の JS の読み込みは、どの画面も 0.6 秒以内に終わっており、遅さの原因ではないことを確かめています。

**回答欄**:

### #1② 確認 CSV（TWS の約定コンファメーション）の取込（ご質問への返答と相談）

9/29 に 2 点のご質問をいただきました。

**(1) TWS CSV の列仕様（サンプル 1 件）**

画面モックに入っているサンプルの実物です。

```text
order_id,confirmation_ref,confirmation_status,filled_quantity,average_price,confirmed_at,message
6,TWS-20260904-0006,CANCELLED,0,0,2026-09-04 10:15:00,TWSで取消確認
```

フロントは 2026-09-28 に、この列を前提にした取込の形を先に作りました（モックで動かしているだけで、確定ではありません）。

```text
POST /operations/stalled-orders/confirmation-import
Content-Type: multipart/form-data
  file: コンファメーション CSV（UTF-8。BOM の有無はどちらでも可）

200 → 既存の CsvImportResponse をそのまま使う
400 → 空ファイル・ヘッダ不一致・データ行なし（detail）
422 → file 欠落（FastAPI の検証エラー）
```

| 論点 | フロントの仮置き |
|---|---|
| `confirmation_status` の値 | `FILLED`（約定）/ `CANCELLED`（取消）→ 滞留一覧から外す。`WORKING`（注文中）/ `PARTIALLY_FILLED`（一部約定）→ 注文中へ移す。サンプルにあるのは `CANCELLED` だけで、**ほかの値は推測です** |
| 行エラーの扱い | 1 行でも不備があれば、1 行も反映しない |
