# E2E シナリオ

画面ごとの **受け入れ条件** を、E2E テストを書く前に Markdown の表で合意するための場所。
テストコードは「どう確認するか」、ここは「何を守るか」を書く。

## なぜ書くか

- レビュー担当が居ないため、E2E が回帰検知の主手段。守るべき挙動がテストコードの外にも必要
- Claude に E2E と実装を書かせるとき、**この文書を入力にする**。実装をなぞっただけのテストになりにくい
- API 仕様書にも画面モックにも書かれない「業務フロー」の置き場になる

## ルール

### ファイル

- 1 画面 = 1 ファイル。`docs/e2e/<画面のケバブケース>.md`（例: `order-list.md`）
- 冒頭で **画面略号** を宣言する（例: `略号: OL`）。略号は 2〜4 文字の大文字

### シナリオ ID

- `<略号>-<2 桁連番>`（例: `OL-01`）
- **欠番になっても振り直さない**。削除したシナリオは行ごと消してよいが、番号は再利用しない

### 表の列

| 列 | 書くこと |
|---|---|
| ID | 上記 |
| 前提 | どんな状態で始めるか。モック応答（`既定モック` / `API が 500` / `0 件` など）を含む |
| 操作 | 利用者が何をするか |
| 期待結果 | **利用者から見える事実**（表示される文言・件数・ボタンの有無）。セレクタや内部状態は書かない |
| 状態 | `実装済` / `未着手` / `保留` のいずれか |

「状態」の意味:

| 状態 | 対応するテスト | `check:scenarios` の扱い |
|---|---|---|
| 実装済 | **必須** | 無ければ error |
| 未着手 | まだ無くてよい | warning（件数のみ） |
| 保留 | 書かない（仕様待ち等） | warning（件数のみ） |

### テストコード側

- テストのタイトル先頭に ID を付ける: `test('[OL-01] 注文が 3 件表示される', …)`
- **1 テスト = 1 ID**。同じ ID を複数のテストに付けない
- 文書に無い ID をテストに付けない（**文書が正**。先に行を足す）
- 特定のシナリオだけ実行する: `docker compose run --rm e2e npx playwright test --grep "\[OL-01\]"`

## 対応チェック

```powershell
docker compose run --rm frontend npm run check:scenarios
```

`docs/e2e/*.md` の ID と `frontend/e2e/**/*.spec.js` のタイトルを突き合わせ、
「実装済なのにテストが無い」「文書に無い ID がテストにある」「ID の重複」を error にする。
コードを書き終えたら lint / unit と一緒に必ず通す。

## 画面を追加するときの流れ

1. `docs/e2e/<画面>.md` にシナリオを書く（全行 `未着手`）
2. Claude に「`docs/e2e/<画面>.md` の OL-xx を実装して」と依頼する
3. テストが通ったら該当行を `実装済` に変える
4. `check:scenarios` を通してコミット
