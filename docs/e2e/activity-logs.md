# 操作ログ

- 略号: `AL`
- 画面: `src/views/ActivityLogListView.vue`
- テスト: `e2e/activity-logs.spec.js`

**当てる先は MSW のモック。** 期待値にフィクスチャの中身（件数・特定の対象キー・特定の差分）を
使うので、実 API に当てると通らない。実 API との噛み合わせを見る版は [activity-logs-real-api.md](activity-logs-real-api.md)。

`/operations/activity-logs` の受け入れ条件。ページ位置と検索条件は URL クエリ（`offset` /
`start_date` / `end_date` / `operator` / `actor_group` / `category` / `operation` / `target_types` /
`target_key` / `sort`）を正としているため、**実ブラウザでの URL と画面の同期**（AL-15 / AL-24）と
**ブラウザバック**（AL-16）をここで守る。既定値（並び順の「新しい順」など）は URL に出ない。

検索条件と列の呼び名は画面モックに合わせてある。モックの「操作区分」（業務操作 / マスタ更新 / 運用管理）は
実 API の `区分`（2026-10-06 の回答 #38）で、クエリには無いので対象種別のカンマ区切り（`target_types`）に
展開して送る（AL-18 / AL-22）。一覧のバッジは応答の `区分名` を出す。
モックの「操作内容」（登録 / 更新 / 削除 …）が実 API の `operation`（AL-03）。
実行者区分は実 API の `actor_group`（営業員・IFA = `sales_ifa` / 管理者・管理責任者 = `manager`。AL-21）。
モックにある 結果 は実 API に無いので置かない（「追加しない」回答。`docs/api/requests.md` #1）。

既定モック（`src/mocks/fixtures/activityLogs.js`）は 64 件（1 ページ 50 件）で、操作日時の**降順**。
先頭 24 件が対象種別 9 種・操作区分 9 種を一通り含み、残り 40 件は古い日付の顧客マスタの更新。
先頭行は銘柄マスタ `AAPL` の更新。業務操作は対象種別「注文」（`orders`）の 3 件（受付 / 訂正 / 取消）で、
変更前後のレコードを持たず（変更項目は `—`）、変更の中身は操作内容の文（注文イベントの文）にある。
対象機能の選択肢は `GET /operations/activity-logs/targets`（9 種。業務操作は 注文、運用管理は
発注停止 / お知らせ の 2 種）から引く。

操作者の選択肢は `GET /masters/users`（`src/mocks/fixtures/users.js`）から「社員コード 氏名」で引き、
無効の操作者（`004`）も含む（操作ログには退職者の記録も残るため）。モックの実行者区分の絞り込みは
操作者のロールコード（`sales` / `ifa` → `sales_ifa`、`manager` / `supervisor` → `manager`）で行い、
操作者の無い行（一括処理）はどちらにも一致しない。

この画面は**読むだけ**で、追加・訂正・削除の導線を持たない（AL-12）。
行ごとの操作は「詳細」ダイアログを開くことだけ（AL-13 / AL-14）。

`mockApi()` は固定の body を返すだけで `offset` やクエリを解釈しないため、
ページングと絞り込み（AL-02〜AL-10 / AL-15 / AL-16 / AL-18 / AL-21 / AL-22 / AL-24）は
クエリを実際に処理する既定ハンドラで見る。

初期表示のローディングはモック応答が即座に返るため実ブラウザでは安定して観測できない。
ローディング表示の出し分け、`?offset=7` のような端数の `offset`、未知の操作内容・区分・並び順を手で URL に
書いたときの扱い、区分と対象機能の優先、値の整形（`formatActivityAt` / `formatActivityValue`）の境界は
画面の導線からは起こらない（または純関数で閉じる）ので、`docs/unit/` の単体テスト側の担保に譲り、ここには書かない。
