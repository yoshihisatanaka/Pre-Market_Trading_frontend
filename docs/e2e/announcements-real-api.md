# お知らせ管理（実 API 接続）

- 略号: `ANR`
- 画面: `src/views/AnnouncementsView.vue`
- テスト: `e2e/announcements.real-api.spec.js`

[announcements.md](announcements.md)（`AN`）と対象画面は同じだが、**当てる先が違う**。
`AN` は MSW のモックに当てて画面の細かい挙動を固定する。こちらは**実 API
（`/operations/announcements`）に当てて、フロントとバックエンドの噛み合わせだけ**を見る。

## なぜ分けるか

`AN` は「現在の本文はフィクスチャの 本文」「履歴は 1 ページ 50 行で 2 ページ目がある」
「成功文言は `お知らせを更新しました。`」のように、フィクスチャと既定ハンドラの中身を期待値にしている。
実 API のローカル DB は別の値を持ち、保存のたびに変わるので全滅する。
加えて `mockApi()`（`window.__mswOverrides`）は MSW を切ると効かないため、
取得 500・空応答・保存の拒否（400 / 409）の再現も成立しない。
`AN` を実データでも通るように書き換えると、代わりに画面の精度を失う。

そこで**期待値の立てかたを変えた別ファイル**にする。ここでは
「フォームの初期値が API の現在値と一致する」「更新したら履歴が 1 増える」のように、
**データの中身に依存しない不変条件**だけを書く。現在値・履歴件数は実行時に API から読んで比べる。
エラー応答・ローディング・未登録の網羅は `AN` の担当で、ここでは求めない。

10/15 の合格線にあたる**スモーク 2 本（表示 1 本・書き込み 1 本）**に加えて、
**更新履歴（ANR-03〜06）**を置く。履歴は MSW 版の `AN-04 / 05 / 14 / 15` が担当する範囲だが、
実 API の履歴は `変更後データ` が JSON 文字列で返るなど仕様書と形が違った前例があるので
（下の「履歴の 変更後データ は JSON 文字列」）、**各列が実 API の応答から読めているか**をここで見る。
網羅（表示 OFF・変更なし・400・409 など）は後日この表に行を足す。

## 実行方法

既定では**動かない**（`E2E_REAL_API` が無ければ丸ごとスキップ）。実 API に当てるときだけ、
2 つの前提をそろえて実行する。

1. `.env` の `VITE_ENABLE_MSW` を `false` にして `docker compose up -d --force-recreate frontend`
2. バックエンドを起動しておく（`(cd ../Pre-Market_Trading && docker compose up -d api)`）

```powershell
docker compose run --rm -e E2E_REAL_API=1 e2e npx playwright test announcements.real-api
```

MSW が有効なままだと実 API を見ていないので、各シナリオの冒頭で検出して失敗させる。
画面から更新系を送るには `.env` の `VITE_USER_CODE` も要る（未設定だと `X-User-Code` が飛ばず 422 になる）。

バックエンドの `api` と DB は 1 つしかないので、**実 API E2E は worktree 間で排他**にする。

## 実データを書き換える

**お知らせは DB に 1 行しか無い共有設定**（`ID` は常に 1）で、
「まだ使われていない値を選んで副作用を隔離する」ことができない。唯一の行を直接書き換えるしかない。

そこで**退避と復元**で辻褄を合わせる。

- `beforeAll` で `GET /api/operations/announcements` を取り、`表示フラグ` / `本文` を退避する
- ANR-02 は本文を**実行ごとに一意な文言**（`実 API 接続確認（E2E が元に戻す） <時刻>`）に書き換え、
  表示フラグを ON にして保存する
- `afterAll` で退避した値を PUT して**元に戻す**。楽観的ロックがあるので、復元の直前に
  もう一度 GET して最新の `更新日時` を添える。退避値が「空本文 + 非表示」なら
  `表示フラグ=0` / `本文=null` を送る。戻したあと GET し直して一致を確かめ、結果を標準出力に出す

**戻せないものがある。**

| 項目 | 実行後 |
|---|---|
| `更新日時` / `更新者` | サーバが付け直すので実行時刻・`e2e` になる |
| `ユーザー操作フラグ` | 更新のたびサーバが 1 を立てる。0 に戻す手段が API に無い |
| 操作履歴（`GET .../history`） | 1 回の実行で 3 行積まれる（ANR-02 の表示 ON + 本文変更、ANR-06 の本文変更、afterAll の復元）。消す API は無い |

したがって**ローカルの開発 DB 専用**。共有環境・本番では実行しない。
履歴が増えすぎたら DB 側で整理してよい（本文の `実 API 接続確認（E2E が元に戻す）` で見分けられる）。

ANR-01 → ANR-06 は `serial` で順に実行する。ANR-02 / ANR-06 だけを `--grep` で抜き出しても
退避と復元は `beforeAll` / `afterAll` が持つので崩れないが、スモークは 2 本まとめて流す。

## 更新履歴は実 API の応答と突き合わせる

履歴の表（`操作日時` / `操作区分` / `本文` / `操作者`）は、同じ `limit` / `offset` で
`GET /api/operations/announcements/history` を直接引き、**行ごと・列ごとに**応答と比べる。
期待値は応答から組み立てる（`操作日時` は画面と同じ `MM/DD HH:mm`、`本文` は `変更後データ` の `本文`、
空なら `—`）。件数や中身は書かない。

- `操作区分` は仕様書の説明では `SHOW` / `HIDE` / `UPDATE` の 3 つ。画面はこれで色を決め、
  知らない値は灰にする。実 API がそれ以外を返したら ANR-04 が落ちて、ズレとして報告する
- ANR-05（2 ページ目）は **履歴が 51 件以上あるときだけ**成立する。50 件以下なら前提不成立で
  スキップし、落とさない（履歴は実行のたびに 3 行ずつ増えるので、いずれ成立する）
- ANR-06 は 2 ページ目を見ている状態から保存し、**先頭ページに戻る**ことを見る。
  51 件以上無ければ 1 ページ目のまま保存し、「先頭ページに戻る」は見ない

## 成功文言は固定しない

ANR-02 の期待結果に、サーバの成功文言そのものを書かない（表示・非表示・本文変更・変更なしで変わり、
バックエンド側の資産なので変わってもこのテストが落ちる筋合いは無い）。
ここで見るのは「成功の枠に空でない文言が出ること」だけ。文言の固定は `AN` が持つ。

| ID | 前提 | 操作 | 期待結果 | 状態 |
|---|---|---|---|---|

| ANR-02 | 実 API に接続。現在値を退避済み | 本文を実行ごとに一意な文言に書き換え（表示フラグが OFF なら ON にして）「お知らせを更新」を押す | PUT が 200 で、送った本文に取得時の `更新日時` が入っている（null なら送らない）。成功メッセージが出る（文言は固定しない）。履歴の `total` が 1 増え、1 行目が新しい本文になる。再読み込みしても新しい本文のまま。API を直接引いても同じ | 実装済 |

## 履歴の 変更後データ は JSON 文字列（2026-09-29 実測・修正済み）

初回の実行で **「履歴の 1 行目が新しい本文」だけが落ちた**
（それ以外の期待結果 — PUT 200・合札・成功メッセージ・履歴 total +1・再読み込み・API 直叩き — は通った）。
製品コードを直した後の再実行（同日）で 2 本とも通った。

実 API の履歴は `変更前データ` / `変更後データ` / `差分データ` を **object ではなく JSON 文字列**で返す。

```json
{
  "操作区分": "SHOW",
  "操作区分名": "表示",
  "操作者": "admin",
  "変更後データ": "{\"ID\": 1, \"本文\": \"…\", \"更新日時\": \"2026-09-29 11:24:05\", \"表示フラグ\": 1, …}",
  "操作日時": "2026-09-29T11:24:05"
}
```

修正前の `src/api/announcements.js` の `historyMessage` は object しか読まず、履歴の本文欄が
常に「—」になっていた。MSW のフィクスチャも object で持っていたので `AN` では見えなかった。

直したこと:

- `historyMessage` が文字列なら `JSON.parse` してから `本文` を読む（壊れた JSON は空文字。`ANA-13` / `ANA-16`）
- フィクスチャ（`src/mocks/fixtures/announcements.js`）とハンドラ（`src/mocks/handlers/announcements.js`）も
  JSON 文字列で持つ。MSW 版でも実 API と同じ経路を通る

## 実測で判った実 API の挙動（2026-09-29）

- 初期状態は `表示フラグ=0` / `本文=null` / `更新日時` あり（作成者・更新者 `BATCH`）。履歴は 0 件
- `更新日時` は ISO（`2026-09-29T11:24:05`）で返り、そのまま送り返した合札で PUT が 200 になる
- 成功文言は操作で変わる。表示 ON + 本文変更は `お知らせを表示しました。`、表示 OFF は
  `お知らせを非表示しました。`（MSW は `非表示にしました。`）、変更なしは `変更はありません。`
- 表示 ON + 本文変更は履歴 1 行（`SHOW`）にまとまる。変更なしの PUT は履歴を積まない
- 更新者は `X-User-Code` の値になる（画面からは `VITE_USER_CODE`、afterAll は `e2e`）
