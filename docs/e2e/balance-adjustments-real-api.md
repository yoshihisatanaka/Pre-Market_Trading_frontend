# 残高マスタ（実 API 接続）

- 略号: `BAR`
- 画面: `src/views/BalanceAdjustmentListView.vue`
- テスト: `e2e/balance-adjustments.real-api.spec.js`

[balance-adjustments.md](balance-adjustments.md)（`BA`）と対象画面は同じだが、**当てる先が違う**。
`BA` は MSW のモックに当てて画面の細かい挙動を固定する。こちらは**実 API に当てて、
フロントとバックエンドの噛み合わせだけ**を見る。

## なぜ分けるか

`BA` は「1 行目はフィクスチャの先頭行」「件数はフィクスチャの件数」「1 ページ目に売却可と売却不可の行が両方ある」のように
フィクスチャの中身を期待値にしている。実 API に当てるとデータが違うので全滅し、
`mockApi()`（`window.__mswOverrides`）は MSW を切ると効かないため、エラー応答（BA-07）・0 件（BA-08）・
409 の再現（BA-18 / BA-33）も成立しない。
そこで**データの中身に依存しない不変条件**だけを書く。件数・値は実行時に画面か API から読み取って比べる。
エラー応答・ローディング・0 件の網羅は `BA` の担当で、ここでは求めない。

## 実行方法

既定では**動かない**（`E2E_REAL_API` が無ければ丸ごとスキップ）。実 API に当てるときだけ、
2 つの前提をそろえて実行する。

1. `.env` の `VITE_ENABLE_MSW` を `false` にして `docker compose up -d --force-recreate frontend`
2. バックエンドを起動しておく（`(cd ../Pre-Market_Trading && docker compose up -d api)`）

```powershell
docker compose run --rm -e E2E_REAL_API=1 e2e npx playwright test balance-adjustments.real-api
```

MSW が有効なままだと実 API を見ていないので、各シナリオの冒頭で検出して失敗させる。
画面から更新系を送るには `.env` の `VITE_USER_CODE` も要る（未設定だと `X-User-Code` が飛ばず 422 になる）。

バックエンドの `api` と DB は 1 つしかないので、**実 API E2E は worktree 間で排他**にする。

## 実データを書き換える

BAR-02 と BAR-09 以降は**実 DB に登録・更新・削除を行う**。ローカルの開発 DB を前提にしているので、
共有環境では実行しない。

残高には自由入力欄が無く、業務キーは **口座番号 × 銘柄コード × 特定預り区分** の組。
POST は「過去に削除済みの同じ組があれば再有効化」する（`openapi.json` の説明）ので、
**一度も使われていない組を実行時に選ぶ**。

- 顧客は画面のプルダウンと同じ取りかた（`GET /masters/customers?limit=200&offset=0`）で引いた中から選ぶ
- 銘柄は銘柄マスタ（`GET /masters/symbols`）の有効な行から、その口座で `include_deleted=true` でも
  `特定預り区分=1`（特定）の行が無い銘柄コードを選ぶ。1 回の実行で **2 組**使う（BAR-02 の下ごしらえと BAR-09 の登録）
- 試験用の行は**数量の目印**で見分ける。数量を `20,350,000` 以上 `20,351,000` 未満（2035 年に寄せた値）にし、
  `初期残高=null`（手動追加）かつ `取消区分=0` の行を、開始時（`beforeAll`）と終了時（`afterAll`）に API で DELETE する。
  前回が途中で落ちた残骸もここで片付くので、2 回続けて実行しても結果は変わらない
- 画面に削除の導線は無いので、削除は API を直接叩く（`DELETE /masters/balance-adjustments/{ID}`）

削除は論理削除なので、**1 回の実行につき `取消区分=1` の行が 2 件（途中で落ちた回は残骸の分も）DB に積まれる**。
あわせて `d_残高情報履歴` に登録・補正・売却可否・削除の履歴が残る。有効な行としては何も残らない。
組は実行のたびに消費されるので、使える銘柄が尽きたら DB から整理してよい（数量の目印で絞り込める）。

**既存の実データの行は書き換えない。** 売却不可区分の切替（BAR-02）を実データの行で行うと、
途中で落ちたときに売注文を受け付けない保有が残り、`ユーザー操作フラグ` も戻せない。
そのため下ごしらえで作った試験用の行で往復させる。

BAR-09〜12 は 1 本の流れ（登録 → 重複 → 補正 → 競合）で、BAR-09 で登録した行を後続が使う。
**順に実行する**。途中だけを `--grep` で抜き出すと前提が崩れる。

## 保留の理由

- **BAR-07（銘柄名の検索）:** 画面は銘柄名を `symbol_name` というクエリで送る（`src/api/balanceAdjustments.js` の冒頭コメント 1 番）が、
  現在の `docs/api/openapi.json` の `GET /masters/balance-adjustments` には `symbol_name_ja` / `symbol_name_en` が入っており、
  `symbol_name` は無い。FastAPI は知らないクエリを無視するので、実 API では**絞り込みが黙って効かない**見込み。
  フロントの送出名を仕様に合わせる（どちらの名前に送るかを決める）まで、期待結果を書かない
- **BAR-13（Ticker での登録）:** 画面はティッカー欄の値を大文字にしてそのまま `銘柄コード` として送る
  （`BalanceAdjustmentRequest` に Ticker の項目が無い）。実 API が Ticker を銘柄コードに解決するのか、
  銘柄マスタに無いとして弾くのかは仕様に書かれていない。拒否されるのが正しいのか受理されるのが正しいのかが決まるまで書かない

## 行の指しかた（BAR-02 / BAR-09〜12）

主キーは `ID`（integer）で、行の「売却を停止」「数量を加算」の `data-testid` は
`balance-adjustments-sell-<ID>` / `balance-adjustments-increase-<ID>` になる。`ID` は実 API の採番なので値は実行時にしか判らない。
BAR-02 は下ごしらえの POST の応答から、BAR-09 は登録後に API を `account_no` で引いて組から `ID` を特定する。
一覧は口座番号 → 銘柄コードの昇順なので 1 ページ目に出るとは限らず、画面は `?account_no=…&symbol=…` で絞って開く。
