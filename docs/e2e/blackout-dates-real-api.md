# 受注不可日マスタ（実 API 接続）

- 略号: `BDR`
- 画面: `src/views/BlackoutDateListView.vue`
- テスト: `e2e/blackout-dates.real-api.spec.js`

[blackout-dates.md](blackout-dates.md)（`BD`）と対象画面は同じだが、**当てる先が違う**。
`BD` は MSW のモックに当てて画面の細かい挙動を固定する。こちらは**実 API
（`/masters/blackout-dates`）に当てて、フロントとバックエンドの噛み合わせだけ**を見る。

## なぜ分けるか

`BD` は「既定モックは 56 件」「1 行目は 2029-12-25」のようにフィクスチャの中身を
期待値にしている。実 API に当てるとデータが違うので全滅し、しかも
`mockApi()`（`window.__mswOverrides`）は MSW を切ると効かないため、
エラー応答や 0 件の再現も成立しない。
`BD` を実データでも通るように書き換えると、代わりに画面の精度を失う。

そこで**期待値の立てかたを変えた別ファイル**にする。ここでは
「登録したら 1 件増える」「削除したら消える」のように、**データの中身に依存しない
不変条件**だけを書く。件数・日付は実行時に画面から読み取って比べる。

同じ作りの先行事例は [market-holidays-real-api.md](market-holidays-real-api.md)（`MR`）。
ただしこの画面には**再有効化の警告が無い**。実 API の事前検証は warnings を返さず、
取消済みの日付を登録し直すと黙って再有効化されるので、`MR-07` / `MR-08` にあたる
「警告 → 続行」の 2 段は BDR-09 の 1 行にまとまる。

## 実行方法

既定では**動かない**（`E2E_REAL_API` が無ければ丸ごとスキップ）。実 API に当てるときだけ、
2 つの前提をそろえて実行する。

1. 環境変数ファイルの `VITE_ENABLE_MSW` を `false` にして
   `docker compose up -d --force-recreate frontend`
2. バックエンドを起動しておく（`(cd ../Pre-Market_Trading && docker compose up -d api)`）

```powershell
docker compose run --rm -e E2E_REAL_API=1 e2e npx playwright test blackout-dates.real-api
```

MSW が有効なままだと実 API を見ていないので、各シナリオの冒頭で検出して失敗させる。

## 実データを書き換える

BDR-04 以降は**実 DB に登録・更新・削除を行う**。ローカルの開発 DB を前提にしているので、
共有環境では実行しない。

使う日付は実運用のデータと混ざらないよう 2035 年に寄せ、**まだ一度も使われていない日**を
実行時に選ぶ。削除が論理削除なので、一度使った日付をもう一度登録すると
「再有効化」の経路に入ってしまい、BDR-04（素の新規登録）が確かめられなくなるため。
終了時にその行を論理削除して戻すので、有効な行としては残らない。

つまり **1 回の実行につき、2035 年に取り消し済みの行が 1 件たまる**。
繰り返し実行しても結果は変わらないが、増えすぎたら DB から整理してよい
（365 日ぶんを使い切ると実行できなくなり、その旨のエラーで止まる）。

BDR-04〜09 は 1 本の流れ（登録 → 重複 → 更新 → 日付の変更 → 削除 → 再有効化）なので**順に実行する**。
途中だけを `--grep` で抜き出すと前提が崩れる。BDR-07 で行が変更後の日付へ移るので、
BDR-08 / 09 はその日付の行を対象にする（1 回の実行で消費する日付は 1 つ）。

行の操作ボタンは `blackout-dates-edit-<id>` / `blackout-dates-delete-<id>` で、`id` は実 API が
採番する `ID` なので実行時にしか判らない。テストは**日付で行を絞ってからボタンを引き**、
testid が数字で終わることを確かめる（空文字なら「実 API が `ID` を返していない」と判る形で落ちる）。

## BDR-07（日付の変更）を保留していた経緯

**2026-09-30 にバックエンドが validate を PUT に揃え、日付の変更を受けるようになった（#18 解消）。**
`test.fixme()` を外して `未着手` に戻し、2026-10-07 に実 API で BDR-01〜09 を通して `実装済` にした。以下は保留していた当時の記録。

もともとは「実 API の `PUT /masters/blackout-dates/{blackout_date}` が
**パスの受注不可日で本文の `受注不可日` を上書きする**ため、備考しか変更できない」として保留していた。
2026-09-18 の取り込みでパスが `/masters/blackout-dates/{blackout_date_id}`（integer の行ID）になり、
この食い違いは解消した（PUT は ID から旧日付、本文から新日付を取る）。

**2026-09-25 に実 API で通したところ、今度は事前検証で止まった。**
`POST /masters/blackout-dates/validate` は `blackout_date_id` を付けると、本文の `受注不可日` が
ID の指す日付と違うだけで 400「IDが指す受注不可日（20350101）とリクエストの受注不可日（20350102）が
一致しません。」を返す。画面は事前検証を通ってから PUT するので、日付を変える編集はここで必ず止まる。
PUT は日付の変更を受け付けるので、バックエンド内で validate と PUT がねじれている
（[docs/api/requests.md](../api/requests.md) の依頼 #18）。

テストは書いてあるが `test.fixme()` にして**既定で走らせない**。バックエンドが validate を PUT に
揃えたら `test` に戻して状態を `実装済` にする。日付の変更を許さない方針になった場合は、
画面の日付欄を読み取り専用にしてこの行を書き換える。
