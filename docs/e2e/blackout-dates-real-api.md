# 受注不可日マスタ（実 API 接続）

- 略号: `BDR`
- 画面: `src/views/BlackoutDateListView.vue`
- テスト: `e2e/blackout-dates.real-api.spec.js`

[blackout-dates.md](blackout-dates.md)（`BD`）と対象画面は同じだが、**当てる先が違う**。
`BD` は MSW のモックに当てて画面の細かい挙動を固定する。こちらは**実 API
（`/blackout-dates`）に当てて、フロントとバックエンドの噛み合わせだけ**を見る。

## なぜ分けるか

`BD` は「既定モックは 56 件」「1 行目は 2029-12-25」のようにフィクスチャの中身を
期待値にしている。実 API に当てるとデータが違うので全滅し、しかも
`mockApi()`（`window.__mswOverrides`）は MSW を切ると効かないため、
エラー応答や 0 件の再現も成立しない。
`BD` を実データでも通るように書き換えると、代わりに画面の精度を失う。

そこで**期待値の立てかたを変えた別ファイル**にする。ここでは
「登録したら 1 件増える」「削除したら消える」のように、**データの中身に依存しない
不変条件**だけを書く。件数・日付は実行時に画面から読み取って比べる。

同じ作りの先行事例は [market-holidays-real-api.md](market-holidays-real-api.md)（`MR`）。
ただしこの画面には**再有効化の警告が無い**。実 API の事前検証は warnings を返さず、
取消済みの日付を登録し直すと黙って再有効化されるので、`MR-07` / `MR-08` にあたる
「警告 → 続行」の 2 段は BDR-09 の 1 行にまとまる。

## 実行方法

既定では**動かない**（`E2E_REAL_API` が無ければ丸ごとスキップ）。実 API に当てるときだけ、
2 つの前提をそろえて実行する。

1. 環境変数ファイルの `VITE_ENABLE_MSW` を `false` にして
   `docker compose up -d --force-recreate frontend`
2. バックエンドを起動しておく（`(cd ../Pre-Market_Trading && docker compose up -d api)`）

```powershell
docker compose run --rm -e E2E_REAL_API=1 e2e npx playwright test blackout-dates.real-api
```

MSW が有効なままだと実 API を見ていないので、各シナリオの冒頭で検出して失敗させる。

## 実データを書き換える

BDR-04 以降は**実 DB に登録・更新・削除を行う**。ローカルの開発 DB を前提にしているので、
共有環境では実行しない。

使う日付は実運用のデータと混ざらないよう 2035 年に寄せ、**まだ一度も使われていない日**を
実行時に選ぶ。削除が論理削除なので、一度使った日付をもう一度登録すると
「再有効化」の経路に入ってしまい、BDR-04（素の新規登録）が確かめられなくなるため。
終了時にその行を論理削除して戻すので、有効な行としては残らない。

つまり **1 回の実行につき、2035 年に取り消し済みの行が 1 件たまる**。
繰り返し実行しても結果は変わらないが、増えすぎたら DB から整理してよい
（365 日ぶんを使い切ると実行できなくなり、その旨のエラーで止まる）。

BDR-04〜09 は 1 本の流れ（登録 → 重複 → 更新 → 削除 → 再有効化）なので**順に実行する**。
途中だけを `--grep` で抜き出すと前提が崩れる。

## BDR-07（日付の変更）が保留の理由

実 API の `PUT /blackout-dates/{blackout_date}` は現在、**パスの受注不可日で本文の
`受注不可日` を上書きする**ため、備考しか変更できない（バックエンド側が対応中）。
フロントは「本文の受注不可日が変更後の日付として効く」前提で実装済みなので、
日付を変えるシナリオはいまの実 API では通らない。

そのためテストは書いてあるが `test.fixme()` にして**既定で走らせない**。
バックエンドが対応したら `test.fixme` を `test` に変え、状態を `実装済` にする。
備考だけを変える BDR-06 は実 API でそのまま動くので、こちらは通っている。

| ID | 前提 | 操作 | 期待結果 | 状態 |
|---|---|---|---|---|
| BDR-01 | 実 API に接続。データ件数は問わない | 一覧を開く | 表が描画され、件数表示の数と表の行数が一致する（1 ページ分を超える分は 2 ページ目以降）。ページ送りが出て、エラーは出ない。0 件のときだけ空状態になりページ送りは出ない | 実装済 |
| BDR-02 | 実 API に接続。1 件以上ある | 一覧の最初の行の日付を日付（From）に入れて検索する | URL に `date_from` が付き、件数は全件以下になる。表示された行の日付がすべてその日以降になる | 実装済 |
| BDR-03 | 実 API に接続。1 件以上ある | 一覧の最初の行の日付を From / To の両方に入れて検索する | その日付の行だけが表示され、件数が「1 件」になる | 実装済 |
| BDR-04 | 実 API に接続。試験用の日付（2035 年の未使用日）は未登録 | その日付と理由を入れて「追加」を押す | モーダルが閉じて成功メッセージが出る。件数が 1 増え、その日付の行が一覧に現れる | 実装済 |
| BDR-05 | BDR-04 の直後 | 同じ日付でもう一度「追加」を押す | モーダルは閉じず、事前検証の理由（既に登録されている旨）が表示される。件数は変わらない | 実装済 |
| BDR-06 | BDR-04 の直後 | その行の「編集」で理由だけを別の文言に変えて「更新」を押す | モーダルが閉じて成功メッセージが出る。件数は変わらず、その行の理由が新しい文言になる（自分自身の日付は重複として弾かれない） | 実装済 |
| BDR-07 | BDR-06 の直後 | その行の「編集」で日付を 2035 年の別の未使用日に変えて「更新」を押す | モーダルが閉じて成功メッセージが出る。件数は変わらず、変更後の日付の行が現れ、変更前の日付の行は消える | 保留 |
| BDR-08 | BDR-06 の直後 | その行の「削除」→「削除する」を押す | モーダルが閉じて成功メッセージが出る。件数が 1 減り、その行が一覧から消える | 実装済 |
| BDR-09 | BDR-08 の直後（その日付は取り消し済み） | 同じ日付でもう一度「追加」を押す | 警告は出ずにそのまま再有効化される。モーダルが閉じて成功メッセージが出て、件数が 1 増え、その日付の行が一覧に戻る | 実装済 |
