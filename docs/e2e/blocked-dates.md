# 受注不可日マスタ

- 略号: `BD`
- 画面: `src/views/BlockedDateListView.vue`
- テスト: `e2e/blocked-dates.spec.js`

`/masters/blocked-dates` の受け入れ条件。ページ位置と検索条件は URL クエリ（`offset` / `date_from` /
`date_to`）を正としているため、**実ブラウザでの URL と画面の同期**をここで守る。
既定モックは 2023〜2029 年の 56 件（1 ページ 50 件）。

一覧・検索（BD-01〜10）に加えて、ヘッダの「新規追加」からの登録（BD-11〜18）と
行ごとの削除（BD-19〜23）、行ごとの編集（BD-24〜30）もこの画面の受け入れ条件に含む。
行の操作は「編集」「削除」の 2 つなので、BD-08 では表の列順（`日付` / `対象市場` / `理由` / 操作）と、
操作列が右端にあること、その中で編集が左・削除が右であることを守る。
[海外休場日マスタ](market-holidays.md)にある休場区分は持たない。

削除の既定モックも追加と同じく状態を保持するため、確認モーダルを経て
**削除後に件数が 1 減る**ところと、最終ページの最後の 1 件を消したときに
1 ページ前へ戻る URL の追従まで実ブラウザで見る。

登録は「サーバの事前検証 → 登録」の 2 段で、エラーの出し先が 3 系統に分かれる
（必須未入力は項目の直下 / 事前検証の不合格は箇条書き / 通信・サーバ障害は専用の表示）。
どの系統がどこに出るかを BD-12 / 14 / 16 で守る。登録の既定モックは追加した行を保持するため、
**登録後に件数が 1 増える**ところまで実ブラウザで見る（モックの状態はページを開くたびに初期化される）。

編集は登録と同じ「サーバの事前検証 → 更新」の 2 段で、日付も理由も変更できる。日付を変えるので
事前検証を編集でも通すが、**自分自身の日付は重複としない**（理由だけを直せる）。更新は
一覧取得時の更新日時を送り返す楽観的ロック付きで、他の利用者が先に更新していればサーバが 409 を返す。
409 は通信・サーバ障害と同じ枠に出す（画面は 409 を特別扱いしない）ので、実ブラウザでは
**その見えかた**だけを BD-29 で守る。

画面上部の説明バナー（国内拠点の受注停止日を管理する旨）は 4 状態の外にあり、
エラーでも 0 件でも消えない。検索カードも同じ理由で消えない（0 件やエラーのときこそ条件を直したい）。
`?offset=7` のような端数の扱いと、送信中に「追加中…」「削除中…」「更新中…」となってボタンが
押せなくなる過渡状態（応答を遅らせる必要があり実ブラウザでは安定して観測できない）、および
画面の導線からは起こらない削除・更新の 404（未知 id）は
[docs/unit/views-blocked-date-list-view.md](../unit/views-blocked-date-list-view.md)
側の担保に譲り、ここには書かない。編集についての分担は次のとおり。

| 論点 | E2E | 単体 | 理由 |
|---|---|---|---|
| 409 競合 | BD-29（PUT を 409 に差し替え、**見えかた**のみ） | BDS-32（既定モックに古い更新日時を送り**検知ロジック**を通す）+ BDL-32 | 実ブラウザで「他の利用者」を作るには 2 セッションが要る |
| 「更新中…」 | — | BDL-33 | 応答を握る必要があり実ブラウザでは安定しない |
| 更新の 404 | — | BDS-33 | 画面の導線からは起こらない |
| 絞り込み中の日付変更でのページ戻し | — | BDL-36 | 空状態が一瞬挟まる過渡状態。削除側（BD-23）が既に E2E にあるので二重に置かない |
| 更新の 500 | — | BDS-31 | 409 と同じ枠・同じ見えかたになる |
