# CAマスタ（実 API 接続）

- 略号: `CAR`
- 画面: `src/views/CorporateActionListView.vue`
- テスト: `e2e/ca.real-api.spec.js`

[ca.md](ca.md)（`CA`）と対象画面は同じだが、**当てる先が違う**。
`CA` は MSW のモックに当てて画面の細かい挙動を固定する。こちらは**実 API に当てて、
フロントとバックエンドの噛み合わせだけ**を見る。

## なぜ分けるか

`CA` は「既定モックは 56 件」「1 行目の銘柄・比率はフィクスチャの先頭」のように
フィクスチャの中身を期待値にしている。実 API に当てるとデータが違うので全滅し、しかも
`mockApi()`（`window.__mswOverrides`）は MSW を切ると効かないため、
エラー応答（CA-07 / 15 / 21 / 26）や 0 件の再現も成立しない。
`CA` を実データでも通るように書き換えると、代わりに画面の精度を失う。

そこで**期待値の立てかたを変えた別ファイル**にする。ここでは
「登録したら 1 件増える」「削除したら消える」「絞り込んだ行はすべて条件を満たす」のように、
**データの中身に依存しない不変条件**だけを書く。件数・銘柄コードは実行時に画面か API から読み取って比べる。
エラー応答・ローディング・0 件の網羅は `CA` の担当で、ここでは求めない。

## 実行方法

既定では**動かない**（`E2E_REAL_API` が無ければ丸ごとスキップ）。実 API に当てるときだけ、
2 つの前提をそろえて実行する。

1. `.env` の `VITE_ENABLE_MSW` を `false` にして `docker compose up -d --force-recreate frontend`
2. バックエンドを起動しておく（`(cd ../Pre-Market_Trading && docker compose up -d api)`）

```powershell
docker compose run --rm -e E2E_REAL_API=1 e2e npx playwright test ca.real-api
```

MSW が有効なままだと実 API を見ていないので、各シナリオの冒頭で検出して失敗させる。
画面から更新系を送るには `.env` の `VITE_USER_CODE` も要る（未設定だと `X-User-Code` が飛ばず 422 になる）。

バックエンドの `api` と DB は 1 つしかないので、**実 API E2E は worktree 間で排他**にする。

## 実データを書き換える

CAR-02 以降は**実 DB に登録・更新・削除を行う**。ローカルの開発 DB を前提にしているので、
共有環境では実行しない。

CA には自然キーが無く、実 API の登録は**毎回新しい行を INSERT する**（同じ銘柄・種別・日付の行が
複数あっても正当）。海外休場日のような「未使用の値を選ぶ」必要は無い代わりに、試験用の行を
**備考の目印**で見分ける。

- 備考は `実 API 接続確認（E2E が削除する）` で始める（実行ごとの識別子を後ろに付ける）。
  CAR-07 / CAR-08 の編集でもこの接頭辞は保つ
- 銘柄コードは実 API が銘柄マスタ実在を検証するので、**実行時に一覧の既存行から借りる**
- 日付は実運用のデータと混ざらないよう **2035 年**に寄せる（一覧は効力発生日の降順なので 1 ページ目に出る）
- 開始時（`beforeAll`）と終了時（`afterAll`）の両方で、`include_deleted=true` の一覧を API で直接引き、
  **備考が目印で始まり `取消区分=0` の行を DELETE する**。前回が途中で落ちた残骸もここで片付くので、
  2 回続けて実行しても結果は変わらない

削除は論理削除なので、**1 回の実行につき `取消区分=1` の行が 1 件（途中で落ちた回は残骸の分も）DB に積まれる**。
有効な行としては残らない。増えすぎたら DB から整理してよい（備考の目印で絞り込める）。

CAR-02〜09 は 1 本の流れ（登録 → 絞り込み → 検証 → 編集 → 競合 → 削除）で、CAR-02 で登録した行を
後続が使う。**順に実行する**。途中だけを `--grep` で抜き出すと前提が崩れる。

## 行の指しかた（CAR-06〜09）

主キーは `ID`（integer のサロゲートキー）で、行の「編集」「削除」の `data-testid` は
`ca-edit-<ID>` / `ca-delete-<ID>` になる。`ID` は実 API の採番なので**値は実行時にしか判らない**。
CAR-02 の登録後に API を直接引き、実行ごとに一意な備考でその行の `ID` を特定してから使う。

## 楽観ロック（CAR-07 / CAR-08）

一覧の `更新日時` は ISO の date-time（例 `2026-08-20T09:30:00`）で返り、`CAUpdateRequest` の説明は
`YYYY-MM-DD HH:MM:SS` 形式になっている。フロントは書式を変換せずに送り返す（`src/api/ca.js` の `toCaRequest`）。
CAR-07 はこの非対称のまま受理されることを、CAR-08 は照合が実際に効いて衝突が拒否されることを見る。

登録直後や既存の自動取込の行は `更新日時` が null のことがあり、そのときフロントは合札を送らない
（照合されない）。CAR-07 はそれを避けるため、合札が付いていなければ API で一度更新してから画面を開く。

2026-09-25 の実測:

- POST 直後の行は `更新日時` が null（`作成日時` だけが入る）。CAR-07 の下ごしらえの PUT で初めて付く
- ISO のまま送った合札（`"更新日時":"2026-09-25T10:36:00"`）で PUT が 200 で受理された
- 別経路の更新後に古い合札で PUT すると 409 で拒否され、本文は
  `他のユーザーによって更新されています。最新の情報を取得してからやり直してください。(取得時: …, 最新: …)`。
  MSW の文言（`src/mocks/handlers/ca.js` の競合メッセージ）とは異なるが、画面は文言を固定していないので影響しない
- 別経路の PUT は `{ "備考": … }` だけの部分更新（`CAUpdateRequest`）で受理された
