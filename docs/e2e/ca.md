# CAマスタ

- 略号: `CA`
- 画面: `src/views/CorporateActionListView.vue`
- テスト: `e2e/ca.spec.js`

`/masters/ca` の受け入れ条件。ページ位置と検索条件は URL クエリ（`offset` / `stock_code` /
`ca_type`）を正としているため、**実ブラウザでの URL と画面の同期**をここで守る。

既定モックは銘柄 8 件 × CA 7 件の 56 件（1 ページ 50 件）で、実 API と同じ並び
（効力発生日の降順、同じ日付なら ID の降順）。先頭行は最も新しい効力発生日を持つ行になる。
モックはこのほかに取消済み（論理削除）の行を 1 件持つが、既定の一覧には出ない。

この画面は**一覧・新規追加・編集・削除**を持つ。CSV 入出力と更新履歴は実 API にはあるが
画面では扱わない。

**削除は論理削除。** 実 API は行を残して 取消区分 を 1 にし、一覧は既定で取消済みを返さないので、
読み直すと消えたように見える。確認ダイアログの対象は日付 1 つでは特定できないため
`銘柄コード / CA種別名 / 効力発生日` を 1 行にして出す（CA-23）。

**編集は全項目を変更できる。** `CARequest` はレコード全体を差し替える形なので、
銘柄コードも CA種別も直せる。更新は一覧取得時の `更新日時` を送り返す楽観的ロック付きで、
競合（409）は通信・サーバ障害と**同じ枠**に出す（CA-21。画面は 409 を特別扱いしない）。

**CA には一意性の規則が無い。** 自然キーを持たず、同じ銘柄・同じ CA種別・同じ日付の行が
複数あっても正当（既定モックも 1 銘柄に「現金配当」を 3 件持つ）。そのため受注不可日の
「既に登録されています」にあたる重複のシナリオは無い。代わりにサーバが見るのは
**銘柄コードが銘柄マスタに実在するか**で、その不合格が CA-14。

**ステータスは実 API 未実装の仮の項目。** CAItem に対応する項目が無いので、値は MSW のモックだけが
返す（既定モックの配分は 完了 16 件 / 確定 24 件 / 予定 16 件）。選択肢と表示名はコードマスタ
（`GET /codes` の `ステータス`）から引き、画面は静的な対応表を持たない。絞り込みのクエリ `status` も
実 API には無く、モックだけが解釈する。**列は操作列の左に置く。**

一方で画面モックの「権利確定日」は依然として出さない。実 API に対応する項目も値の当ても無いため
（日付は 権利付最終日 / 効力発生日 / 支払日 の 3 つ）。

**ユーザー操作フラグが 1 の行には色が付く。** 自動取込のままの行と見分けるための印なので、
「色が付いている行がある」ことではなく「フラグ 1 の行だけ背景色が他と違う」ことを守る（CA-08）。

`mockApi()` は固定の body を返すだけで `offset` / `stock_code` / `ca_type` を解釈しないため、
ページングと絞り込み（CA-02 / 03 / 04 / 05）はクエリを実際に処理する既定ハンドラで見る。

未知の `ca_type` を手で URL に書いたときの扱い、`CA種別名` を欠いた応答、表示件数の倍数でない
`offset` は、画面の導線からは起こらないので
[docs/unit/views-corporate-action-list-view.md](../unit/views-corporate-action-list-view.md)
側の担保に譲り、ここには書かない。
