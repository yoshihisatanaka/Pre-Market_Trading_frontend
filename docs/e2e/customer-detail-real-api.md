# 顧客詳細（実 API 接続）

- 略号: `CDTR`
- 画面: `src/views/CustomerDetailView.vue`（枠）/ `src/views/CustomerSummaryView.vue`（外株預り）/ `src/views/CustomerOrdersView.vue`（注文照会）/ `src/views/CustomerCalculationView.vue`（仮計算）
- テスト: `e2e/customer-detail.real-api.spec.js`

顧客詳細 `/customers/:customerId/summary`・`/orders` を**実 API（`GET /masters/customers/{account_id}`・
`GET /holdings`・`GET /orders`）に当てて、フロントとバックエンドの噛み合わせだけ**を見る。
MSW のモックに当てる版（`docs/e2e/customer-detail.md`）はこの文書の作成時点ではまだ無い。
作るときは別ファイル・別略号にし、こちらと混ぜない。

いまはリリースまでの合格線どおり**スモーク 2 本**（外株預り 1 本・注文照会 1 本）を先頭に置き、
任意の 1 本（存在しない顧客）を足してある。CDTR-04 以降は**新規注文への導線**
（タブの「注文入力」・預りの行の「買い」「売り」・「＋ 新規注文」）で、いずれも顧客詳細の注文入力タブ
（`/customers/<id>/order-entry`。顧客カードとタブは残り、「注文入力」タブが選択中）に移って
部店・口座番号が引き継がれ、新規注文の画面が実 API（`GET /masters/customers?account_no=`）で
その顧客を引き直せるところまでを見る。**注文は送信しない**（確認・発注まで進まない）。

- 導線の行は**発注権限**（`GET /auth/me` の `order`）が要る。操作者は `.env` の `VITE_USER_CODE` で決まり
  テストからは変えられないので、権限が無ければ（行の操作が「閲覧のみ」なら）スキップする
- 実 API のテストデータは保有 0 件の見込みなので、行の「買い」「売り」は 0 件ならスキップする。
  引き継ぐ銘柄・預り区分の**値そのものは期待値に書かず**、URL のクエリと新規注文の入力欄が
  **押した行の表示と食い違わない**ことだけを見る

## なぜ分けるか

MSW 版はフィクスチャの中身（顧客 ID・保有銘柄・注文の件数）を期待値にする。実 API に当てるとデータが違うので全滅し、
`mockApi()`（`window.__mswOverrides`）は MSW を切ると効かないため、エラー応答や 0 件の再現も成立しない。
そこで**データの中身に依存しない不変条件**だけを書く。

- **顧客 ID は固定しない**（実 DB の ID は分からない）。顧客検索の一覧の**先頭の顧客名リンク**から入る
- **0 件でも通る**書き方にする。実 API のテストデータは薄く（`docs/api/requests.md` の「テストデータの不足（#32）」）、
  顧客マスタの口座は保有 0 件、注文は 100 件が 1 状態だけで顧客マスタの口座と噛み合っていない見込み
- **`GET /holdings` の値の正しさは見ない**（項目の意味を確認中。`docs/api/requests.md` #36）。
  件数と行数が食い違わないこと、4 状態のどれに落ちたかだけを見る

## 2 本目が書き込みでない理由

合格線のスモークは「一覧 1 本・書き込み 1 本」だが、**この画面は読むだけ**（訂正・取消・新規注文は別画面へ移る）。
そこで 2 本目は**注文照会タブ**にした。顧客カードの部店と口座番号を、api 層が `branch_code` / `account_no`
（integer）に変えて `GET /orders` に送る。FastAPI は知らないクエリを黙って無視するので、送出名がずれても
MSW 版では気づけない。リクエストに顧客の口座番号が載っていることを直接見る。

## 実行方法

既定では**動かない**（`E2E_REAL_API` が無ければ丸ごとスキップ）。実 API に当てるときだけ、前提をそろえて実行する。

1. `.env` の `VITE_ENABLE_MSW` を `false` にして `docker compose up -d --force-recreate frontend`
2. バックエンドを起動しておく（`(cd ../Pre-Market_Trading && docker compose up -d api)`）

```powershell
docker compose run --rm -e E2E_REAL_API=1 e2e npx playwright test customer-detail.real-api
```

MSW が有効なままだと実 API を見ていないので、各シナリオの冒頭で検出して失敗させる。
顧客が 1 件も無い DB では入口が無いので、CDTR-01 / CDTR-02 はスキップされる。

**実 DB には書き込まない**。CDTR-07 までは GET だけ。CDTR-08 以降の仮計算は `POST /calculations` を送るが、
openapi.json の説明が「DB更新なし」（`src/api/calculations.js` の冒頭も同じ）なので、1 回の実行で DB に残るものは無い。
各行は独立していて、`--grep` で 1 本だけ抜き出してよい。

## 仮計算タブ（CDTR-08 以降）

`/customers/:customerId/calculations`（`src/views/CustomerCalculationView.vue`）を `POST /calculations` に当てる。
MSW 版は `docs/e2e/customer-detail.md` の CDT-36〜44。

- 計算はすべてサーバが行い、画面は応答を書式に流すだけ。そこで**金額を期待値に書かず**、画面が送った本文を
  `apiContext` から**同じ本文で直接 POST し直した応答**と、画面の表示を突き合わせる（為替は為替マスタの直近レートなので、
  同じ本文なら同じ結果になる前提）
- 銘柄は固定しない。`GET /masters/symbols` の先頭の `銘柄コード` を使う（0 件ならスキップ）
- 入力は「数量 1・単価 100」と、ハンド入力の行だけ「為替 150・現地手数料① 1.23」。どれも結果の値ではなく送出の確認に使う
- **国内約定日・現地手数料区分は前提にしない。** 国内約定日は `CalculationRequest.約定日` が入った（2026-10-08）が
  フロントはまだ送らない。現地手数料区分は画面モック `18ed9d1` で削除済み（2026-10-09 に画面からも外した）で、`CalculationRequest` にも無い
  （どちらも `docs/api/requests.md` #47 で未確定）。現地手数料①が空なら仮計算マスタの率で自動計算になること（`18ed9d1`）は
  CDTR-13 で見る
- API の 422（本文の型の不備）は画面の入力検証が先に止めるので画面からは出せない。400（銘柄が無い）で理由の帯を見る
- 400 / 500 / ローディングの再現は MSW 版（CDT-41 / 43 / 44）の担当
