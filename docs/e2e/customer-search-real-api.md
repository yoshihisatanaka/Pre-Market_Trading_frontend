# 顧客検索（実 API 接続）

- 略号: `CSER`
- 画面: `src/views/CustomerSearchView.vue`
- テスト: `e2e/customer-search.real-api.spec.js`

顧客検索 `/customers/search` を**実 API（`GET /masters/customers`）に当てて、フロントとバックエンドの
噛み合わせだけ**を見る。MSW のモックに当てる版（`docs/e2e/customer-search.md`）はこの文書の作成時点では
まだ無い。作るときは別ファイル・別略号にし、こちらと混ぜない。

いまはリリースまでの合格線どおり**スモーク 2 本**（一覧 1 本・絞り込み 1 本）を先頭に置き、
任意の 2 本（顧客詳細への移動・扱者コードの絞り込み）を足してある。

## なぜ分けるか

MSW 版はフィクスチャの中身（件数・先頭行の顧客名）を期待値にする。実 API に当てるとデータが違うので全滅し、
`mockApi()`（`window.__mswOverrides`）は MSW を切ると効かないため、エラー応答や 0 件の再現も成立しない。
そこで**データの中身に依存しない不変条件**だけを書く。口座番号・扱者コードは実行時に一覧の 1 行目から読む。
エラー応答・ローディング・0 件の網羅は MSW 版の担当で、ここでは求めない。

## 2 本目が書き込みでない理由

合格線のスモークは「一覧 1 本・書き込み 1 本」だが、**この画面は読むだけ**（登録・更新・削除の導線が無い）。
そこで 2 本目は**口座番号での絞り込み**にした。この画面の噛み合わせで最も壊れやすいのは**クエリ名**で、
URL 上の `account_number` を api 層が `account_no`（integer）に変えて送る。FastAPI は知らないクエリを黙って
無視するので、送出名がずれても MSW 版では気づけない。表示行がすべてその口座になることで、効いていることが判る。

## 実行方法

既定では**動かない**（`E2E_REAL_API` が無ければ丸ごとスキップ）。実 API に当てるときだけ、前提をそろえて実行する。

1. `.env` の `VITE_ENABLE_MSW` を `false` にして `docker compose up -d --force-recreate frontend`
2. バックエンドを起動しておく（`(cd ../Pre-Market_Trading && docker compose up -d api)`）

```powershell
docker compose run --rm -e E2E_REAL_API=1 e2e npx playwright test customer-search.real-api
```

MSW が有効なままだと実 API を見ていないので、各シナリオの冒頭で検出して失敗させる。

**実 DB には書き込まない**（GET だけ）。各行は独立していて、`--grep` で 1 本だけ抜き出してよい。
