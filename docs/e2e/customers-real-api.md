# 顧客マスタ（実 API 接続）

- 略号: `CUR`
- 画面: `src/views/CustomerListView.vue`
- テスト: `e2e/customers.real-api.spec.js`

[customers.md](customers.md)（`CU`）と対象画面は同じだが、**当てる先が違う**。
`CU` は MSW のモックに当てて画面の細かい挙動を固定する。こちらは**実 API に当てて、
フロントとバックエンドの噛み合わせだけ**を見る。

## なぜ分けるか

`CU` は「既定モックの件数」「先頭行の口座番号・顧客名」「法人で絞ると N 件」のように
フィクスチャの中身を期待値にしている。実 API に当てるとデータが違うので全滅し、しかも
`mockApi()`（`window.__mswOverrides`）は MSW を切ると効かないため、
エラー応答（CU-09）・更新の競合を差し替える CU-22・0 件の再現も成立しない。
`CU` を実データでも通るように書き換えると、代わりに画面の精度を失う。

そこで**データの中身に依存しない不変条件**だけを書く。件数・口座番号・部店コードは実行時に画面か API から読み取って比べる。
エラー応答・ローディング・0 件・列順・色分け・金額の整形・バッジの網羅は `CU` の担当で、ここでは求めない。

この画面で特に見たい噛み合わせは次の 4 つ。

- **画面の URL クエリと実 API のクエリ名が違う**（画面 `account_number` ↔ 実 API `account_no`（integer））。
  ほかの `branch_code` / `customer_name` / `corporate_type` は同名。変換は `src/api/customers.js` だけが持つ。
  旧名を送っても実 API はエラーにせず無視するので、**画面が実際に送ったクエリ名**と、表示行がすべて条件を満たすことを見る（CUR-03〜06）
- 一覧の配列キーが `customers`（`CustomerListResponse`）
- 編集のパスキーが行の `ID`（`/masters/customers/{account_id}`、integer）で、**業務キーの口座番号は `CustomerUpdateRequest` に無い**（編集で変更不可）
- 部店・扱者・コンプラランクの選択肢は `/branches` / `/handlers` / `/codes` の実 API から来る（MSW を切ると、これらもモックではなくなる）

## 実行方法

既定では**動かない**（`E2E_REAL_API` が無ければ丸ごとスキップ）。実 API に当てるときだけ、
次の前提をそろえて実行する。

1. `.env` の `VITE_ENABLE_MSW` を `false` にして `docker compose up -d --force-recreate frontend`
2. バックエンドを起動しておく（`(cd ../Pre-Market_Trading && docker compose up -d api)`）
3. `.env` の `VITE_USER_CODE` が設定されていること（未設定だと画面から送る更新系が 422 になる）。
   **全店参照権限のあるユーザ**にする（無いと一覧が自部店に限定され、試験用の口座を他店で作ると見えない）

```powershell
docker compose run --rm -e E2E_REAL_API=1 e2e npx playwright test customers.real-api
```

MSW が有効なままだと実 API を見ていないので、各シナリオの冒頭で検出して失敗させる。
バックエンドの `api` と DB は 1 つしかないので、**実 API E2E は worktree 間で排他**にする。

## 実データを書き換える

CUR-02 以降は**実 DB に登録・更新・論理削除を行う**。ローカルの開発 DB を前提にしているので、
共有環境では実行しない。

口座番号は一意な業務キーで、削除は論理削除（`取消区分=1`）。一度使った口座番号を登録すると
**再有効化**の経路（事前検証の警告 → 押し直しで登録）に入るので、CUR-02（素の新規登録）には**一度も使われていない口座番号**が要る。

- 口座番号は `2035000`〜`2035999`（`RESERVED_YEAR` を頭に付けた 7 桁）から、`include_deleted=true` でも
  見つからない最小の値を実行時に選ぶ。1000 件を使い切ると、その旨のエラーで止まる
- 顧客名は `E2E実API確認` で始める（目印）。編集（CUR-10 / 11）でもこの接頭辞は保つ
- 部店・扱者は一覧の 1 行目に実際に出ている組をそのまま使う（実在する組み合わせでないと事前検証で弾かれるため）。
  0 件のときだけ選択肢の先頭を使う
- 開始時（`beforeAll`）と終了時（`afterAll`）の両方で、`customer_name=E2E実API確認&include_deleted=true` を API で直接引き、
  **口座番号が上の範囲で `取消区分=0` の行を `DELETE /masters/customers/{ID}` する**。画面に削除の導線は無い（2026-09-28 決定）ので
  後片付けは API で行う。前回が途中で落ちた残骸もここで片付くので、2 回続けて実行しても結果は変わらない
- CUR-12 / 13 の下ごしらえで、CUR-02 の行を API から論理削除する（画面から取消済みの口座を作れないため）

登録の値は**業務規則**（`openapi.json` の `CustomerRequest` / `CustomerValidateRequest` の description と
`docs/api/requests.md` #45 の回答。2026-10-06）に合わせる。画面の入力検証はこの規則を持たない（サーバの事前検証に任せ、
不合格の理由がモーダル内に出ることは MSW 版の `CU-18` が見る）ので、spec の側で規則どおりの値を入れる。

| 項目 | 入れる値 | 規則 |
|---|---|---|
| 個人／法人 | 個人（画面の既定） | 法人だと 生年月日 `'0'`・NISA契約 `'0'`・特定口座区分 `'3'` が固定になる |
| 顧客名 | `E2E実API確認　顧客`（姓名の間は**全角**スペース） | 個人は姓名の間を全角スペースで区切る |
| 顧客名カナ | `ﾃｽﾄ ｺｷｬｸ`（姓名の間は**半角**スペース） | 半角カナ・半角数字・ハイフン・半角スペースだけ。個人は姓名の間を半角スペースで区切る |
| 生年月日 | `19800101` | 個人は YYYYMMDD で必須（画面では任意項目） |
| コンプラランク | `C`（選択肢に無ければ空でない先頭） | 許容値は A〜J, X, Y, Z。A・B・Y・Z は発注制限の対象なので避ける |
| 円貨預り金・USD預り金・NISA買付可能額（当年・翌年） | `0` を明示 | NISA契約 0 のとき買付可能額は 0。預り金は総預り資産（0）以下 |

編集（CUR-10 / 11）で入れる顧客名も同じく姓名の間を全角スペースにする（`E2E実API確認　変更後` ほか）。

**1 回の実行につき、口座番号 `2035xxx` の取消済み（`取消区分=1`）の行が 1 件 DB にたまる**（有効な行としては残らない）。
増えすぎたら DB から整理してよい（顧客名の接頭辞か口座番号の範囲で絞り込める）。

CUR-02 以降は 1 本の流れ（登録 → 重複 → 編集 → 競合 → 取消 → 再有効化）で、CUR-02 で登録した行を
後続が使う。**順に実行する**。途中だけを `--grep` で抜き出すと前提が崩れる（CUR-01・03〜07 は単独でも動く）。

（`POST /masters/customers/validate` が未送信の金額項目の `None * 150` で 500 を返していた）。
バックエンドが Phase 66 で直し、あわせて「本文どおりに送っても業務規則（氏名の空白・生年月日 など）で

「実データを書き換える」の表の値へ直し、状態を**未着手**に戻した（実 API ではまだ流していない）。
本体セッションの検証モードで流して `実装済` / `保留` を確定させる。

## 行の指しかた（CUR-09〜13）

主キーは `ID`（integer のサロゲートキー）で、行の「編集」の `data-testid` は `customers-edit-<ID>` になる。
`ID` は実 API の採番なので**値は実行時にしか判らない**。CUR-02 の登録後に API を直接引き、
口座番号でその行の `ID` を特定してから使う。

一覧は口座番号の昇順なので、`2035xxx` の行が 1 ページ目に出るとは限らない。
**行を追いかけず、その口座番号で検索して 1 件に絞ってから操作する**（`CU-16` と同じ考え方）。
