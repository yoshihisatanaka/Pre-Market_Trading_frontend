# Dream登録状況（実 API 接続）

- 略号: `DSR`
- 画面: `src/views/DreamStatusListView.vue`
- テスト: `e2e/dream-status.real-api.spec.js`

[dream-status.md](dream-status.md)（`DS`）と対象画面は同じだが、**当てる先が違う**。
`DS` は MSW のモックに当てて画面の細かい挙動を固定する。こちらは**実 API（`GET /orders/dream-status` /
`GET /orders/dream-status/statuses` / `PUT /orders/dream-status/{order_id}`）に当てて、
フロントとバックエンドの噛み合わせだけ**を見る。

## なぜ分けるか

`DS` はフィクスチャの中身（56 件・先頭行は注文ID `#56`・エラーの行は 3 件・遷移先の文言）を期待値にしている。
実 API に当てるとデータが違うので全滅し、`mockApi()`（`window.__mswOverrides`）は MSW を切ると効かないため、
エラー応答・0 件・409 の差し替え（`DS-13` / `DS-14` / `DS-21`）も成立しない。
そこで**データの中身に依存しない不変条件**だけを書く。絞り込みに使う値は、開いた時点（条件なし）に
**画面自身が受け取った `GET /orders/dream-status` の応答**の先頭の注文から読む（`EXR` と同じ考え方。
テストから API を直接引くと `X-User-Code` が画面と違い、部店の限定で見える注文が変わる）。
エラー応答・ローディング・0 件・列順・色分け・STS変更の送信後の反映は `DS` の担当で、ここでは求めない。

この画面の噛み合わせで壊れやすいのは次の 4 つ。

- **画面の URL クエリと実 API のクエリ名が違う。** URL `account_number` ↔ API `account_no`（integer）、
  `dream_status` は同名、`registered_from` / `registered_to` ↔ `start_date` / `end_date`、`dream_ref` ↔ `receipt_number`。
  変換は `src/api/dreamStatus.js` だけが持つ。FastAPI は知らないクエリを黙って無視するので、
  **画面が実際に送ったクエリ名**と、表示行がすべて条件を満たすことを見る
- **検索の登録日は注文の作成日**（`作成日時`）で絞る。画面の「登録日時」列（`Dream完了日時`）ではない
- **STS変更の導線はサーバの `STS変更可` と `変更可能状況` に従う。** 画面は遷移先を固定で持たず、
  行ごとの応答から選択肢を組む。擬似コード `ERROR` で絞ると、出る行はすべて STS変更可 になるはず
- **Dream登録状況のプルダウンは `GET /orders/dream-status/statuses` から来る**（MSW を切るとこれもモックではなくなる）

## 2 本目（書き込み）を保留にした理由

合格線のスモークは「一覧 1 本・書き込み 1 本」だが、この画面の書き込み（STS変更）は**元に戻せない**。

- `PUT /orders/dream-status/{order_id}` の遷移は `9 → 0 / 2 / 8` と `C9 → C0 / C2` だけで、
  **どれも `9` / `C9` に戻る経路が無い**（変更後の行は STS変更可 でなくなる）
- `0` / `C0`（再送待ち）へ戻すと、Dream 連携のバッチがその注文を再送する。`2` / `C2` は Dream 側に
  受付済みという扱いになり処理状況も進む（`C2` は `034` 取消済）。どれも**実注文の業務上の状態を変える**
- 登録失敗（`9`）の注文を API で作ることも、変更後に戻すこともできない（注文の登録 API は Dream 連携の
  結果までは作れず、`DELETE` も無い）。試験用の行を自分で用意して自分で片付ける形にならない

したがって `DSR-02` は**保留**。代わりに、送信の直前まで（行のプルダウン → 確認ダイアログ → キャンセル）を
実データで通し、**PUT を送らずに**導線が噛み合うことを `DSR-03` で見る。

検証モードで書き込みまで通したいときは、**ユーザが使い捨ててよい登録失敗の注文 ID を指定**し、
終端で副作用の無い `8`（登録対象外）へ変える形が候補（1 回の実行で登録失敗の行を 1 件消費する。再実行には別の注文が要る）。
その判断はユーザに委ね、ここでは書かない。

## 実行方法

既定では**動かない**（`E2E_REAL_API` が無ければ丸ごとスキップ）。実 API に当てるときだけ、前提をそろえて実行する。

1. `.env` の `VITE_ENABLE_MSW` を `false` にして `docker compose up -d --force-recreate frontend`
2. バックエンドを起動しておく（`(cd ../Pre-Market_Trading && docker compose up -d api)`）
3. `.env` の `VITE_USER_CODE` が設定されていること。**全店参照権限のあるユーザ**が望ましい
   （無いと一覧が自部店に限定される。`DSR-10` はその場合でも 1 行目の部店なので通る）

```powershell
docker compose run --rm -e E2E_REAL_API=1 e2e npx playwright test dream-status.real-api
```

MSW が有効なままだと実 API を見ていないので、各シナリオの冒頭で検出して失敗させる。

**実 DB には書き込まない**（GET だけ。`DSR-03` は確認ダイアログをキャンセルで閉じ、PUT を送らないことを確かめる）。
各行は独立していて、`--grep` で 1 本だけ抜き出してよい。
注文が 0 件なら `DSR-01` は空状態を確かめて通り、値を 1 行目から読む行は**スキップ**する。
