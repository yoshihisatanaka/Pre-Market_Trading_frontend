# 手数料優遇マスタ（実 API 接続）

- 略号: `FPR`
- 画面: `src/views/FeePreferenceListView.vue`
- テスト: `e2e/fee-preferences.real-api.spec.js`

[fee-preferences.md](fee-preferences.md)（`FP`）と対象画面は同じだが、**当てる先が違う**。
`FP` は MSW のモックに当てて画面の細かい挙動を固定する。こちらは**実 API に当てて、
フロントとバックエンドの噛み合わせだけ**を見る。

## なぜ分けるか

`FP` は「既定モックは有効な行 52 件」「先頭行の口座番号」のようにフィクスチャの中身を期待値にしている。
実 API に当てるとデータが違うので全滅し、しかも `mockApi()`（`window.__mswOverrides`）は MSW を切ると効かないため、
エラー応答や 0 件の再現も成立しない。`FP` を実データでも通るように書き換えると、代わりに画面の精度を失う。

そこで**データの中身に依存しない不変条件**だけを書く。件数・口座番号は実行時に画面か API から読み取って比べる。
エラー応答・ローディング・0 件・列の整形・適用されない方式の淡色表示の網羅は `FP` の担当で、ここでは求めない。

この画面で特に見たい噛み合わせは次の 3 つ。

- 一覧の配列キーが `fee_preferences`（`FeePreferenceListResponse`）で、プロパティ名が日本語。
  **画面が受け取った応答の `total` と先頭行の `口座番号` が、画面の件数表示と 1 行目に出る**（FPR-01）
- 登録は「事前検証（`POST /masters/fee-preferences/validate`）→ 登録（`POST /masters/fee-preferences`）」の 2 段で、
  事前検証は `warnings` を返しうる（警告が出たら同じボタンを押し直して続行する）
- 削除のパスキーが行の `ID`（`/masters/fee-preferences/{fee_preference_id}`、integer）

## 実行方法

既定では**動かない**（`E2E_REAL_API` が無ければ丸ごとスキップ）。実 API に当てるときだけ、
次の前提をそろえて実行する。

1. `.env` の `VITE_ENABLE_MSW` を `false` にして `docker compose up -d --force-recreate frontend`
2. バックエンドを起動しておく（`(cd ../Pre-Market_Trading && docker compose up -d api)`）
3. `.env` の `VITE_USER_CODE` が設定されていること（未設定だと画面から送る更新系が 422 になる）。
   **全店参照権限のあるユーザ**にする（無いと一覧が自部店に限定され、他店の口座で登録した行が画面に出ない）
4. 実 DB に**有効な顧客（口座）が 1 件以上あり、そのうち手数料優遇の登録が一度も無い口座が残っている**こと
   （無ければ FPR-02 はその旨のメッセージで失敗する）

```powershell
docker compose run --rm -e E2E_REAL_API=1 e2e npx playwright test fee-preferences.real-api
```

MSW が有効なままだと実 API を見ていないので、各シナリオの冒頭で検出して失敗させる。
バックエンドの `api` と DB は 1 つしかないので、**実 API E2E は worktree 間で排他**にする。

## 実データを書き換える

FPR-02 は**実 DB に登録と論理削除を行う**。ローカルの開発 DB を前提にしているので、共有環境では実行しない。

手数料優遇は **1 口座 1 レコード**で、自由入力欄（備考）を持たない。削除は論理削除（`取消区分=1`）で、
取消済みの行がある口座に登録し直したときの挙動（再有効化か新規か）は仕様に書かれていない。そこで次のようにする。

- 登録に使う口座は、顧客マスタの有効な口座（`GET /masters/customers`）から、
  **手数料優遇に一度も登録されたことの無い口座**（`GET /masters/fee-preferences?include_deleted=true` に無い口座）を
  実行時に選ぶ（口座番号の昇順で最初のもの）。素の新規登録の経路だけを通すため
- 目印は**数値の組**で付ける。掛目 `99.75`（%）と為替スプレッド `0.9876`（円/USD）を入れ、手数料パターンはデフォルト、
  ベイシスは未設定（パターン方式）にする。実運用でこの組が使われることはまず無い
- 開始時（`beforeAll`）と終了時（`afterAll`）の両方で、`include_deleted=true` の一覧を API で直接引き、
  **掛目とスプレッドが目印の組で `取消区分=0` の行を `DELETE /masters/fee-preferences/{ID}` する**。
  終了時はあわせて、今回選んだ口座の有効な行も消す（登録の無かった口座なので今回の行とみなせる。
  目印の数値がサーバ側で丸められても漏れない）。前回が途中で落ちた残骸もここで片付くので、2 回続けて実行しても結果は変わらない

**1 回の実行につき、取消済み（`取消区分=1`）の手数料優遇が 1 件 DB にたまり、その口座は次回から候補に入らない**
（有効な行としては残らない。登録の無い口座を 1 つずつ使い潰す）。候補が尽きたら、目印の組
（掛目 `99.75`・スプレッド `0.9876`）で取消済みの行を DB から整理してよい。

## シナリオ

| ID | 前提 | 操作 | 期待結果 | 状態 |
|---|---|---|---|---|
| FPR-01 | MSW off・api 起動。データ件数は問わない | `/masters/fee-preferences` を開く | 件数表示と表の行数が一致する（1 ページ 50 件まで）。件数が 1 以上なら表とページ送り、0 なら空状態が出る。エラーは出ない。**画面が受け取った一覧の応答**（`fee_preferences` / `total`）の `total` が件数表示と一致し、1 件以上なら応答の先頭行の `口座番号` が表の 1 行目の口座番号の列に出る | 実装済 |
| FPR-02 | FPR-01 と同じ。手数料優遇の登録が一度も無い有効な口座がある（実行時に選ぶ） | 「新規追加」から、その口座番号・掛目 `99.75`・為替スプレッド `0.9876` を入れて「追加」を押す（事前検証の警告が出たら、もう一度押して続行する） | モーダルが閉じ、口座番号を含む成功メッセージが出て、件数が 1 増える。その口座番号で検索すると URL に `account_no=<その値>` が付き「1 件」になり、行にその口座番号が出る。API を直接引いてもその口座の行が有効（`取消区分=0`）で存在し、掛目・スプレッドが入れた値になっている。終了時に API から論理削除する | 実装済 |

FPR-01 は単独で動く。FPR-02 も単独で動く（下ごしらえと後片付けは `beforeAll` / `afterAll` が持つ）。
