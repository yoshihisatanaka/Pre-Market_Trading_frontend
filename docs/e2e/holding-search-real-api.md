# 預り検索（実 API 接続）

- 略号: `HSR`
- 画面: `src/views/HoldingSearchView.vue`
- テスト: `e2e/holding-search.real-api.spec.js`

[holding-search.md](holding-search.md)（`HSE`）と対象画面は同じだが、**当てる先が違う**。
`HSE` は MSW のモックに当てて画面の細かい挙動を固定する。こちらは**実 API（`GET /holdings`）に当てて、
フロントとバックエンドの噛み合わせだけ**を見る。

## なぜ分けるか

`HSE` はフィクスチャの中身（64 件・先頭行の口座番号やティッカー）を期待値にしている。実 API に当てるとデータが違うので全滅し、
`mockApi()`（`window.__mswOverrides`）は MSW を切ると効かないため、エラー応答や 0 件の再現も成立しない。
そこで**データの中身に依存しない不変条件**だけを書く。絞り込みに使う値（口座番号・部店・顧客名・銘柄・預り区分）は
実行時に開いた時点の一覧（条件なし。顧客検索と同じく開くとすぐ引く）の 1 行目から読む。エラー応答・ローディング・0 件の網羅は `HSE` の担当で、ここでは求めない。

この画面の噛み合わせで最も壊れやすいのは**クエリ名**。URL 上の名前（`account_number` / `stock_name`）を api 層が
実 API の名前（`account_no` / `symbol_name`）に変えて送る。FastAPI は知らないクエリを黙って無視するので、
送出名がずれても MSW 版では気づけない。絞り込みの各行は「送ったリクエストのクエリ」と「表示行がすべて条件を満たすこと」の両方を見る。

## 2 本目が書き込みでない理由

合格線のスモークは「一覧 1 本・書き込み 1 本」だが、**この画面は読むだけ**（登録・更新・削除の導線が無い。
「買い」「売り」は新規注文の画面へ移るだけ）。そこで 2 本目は**口座番号での絞り込み**にした（顧客検索の `CSER-02` と同じ考え方）。

## テストデータが薄い

ローカルの開発 DB は保有が少なく、**保有のある口座（1・3100）が顧客マスタに無い**
（[docs/api/requests.md](../api/requests.md) の「テストデータの不足」#32）。そのため:

- 預りが 0 件なら `HSR-01` は空状態を確かめて通り、`HSR-02` 以降は**スキップ**する
- 1 行目の値が空（`—`）で条件に使えない行は、その行だけスキップする
- `HSR-08`（顧客詳細へ移る）は、表示中の明細のうち**顧客マスタにある口座の明細**が無ければスキップする。
  データが入るまでは実質スキップになる見込み

## 実行方法

既定では**動かない**（`E2E_REAL_API` が無ければ丸ごとスキップ）。実 API に当てるときだけ、前提をそろえて実行する。

1. `.env` の `VITE_ENABLE_MSW` を `false` にして `docker compose up -d --force-recreate frontend`
2. バックエンドを起動しておく（`(cd ../Pre-Market_Trading && docker compose up -d api)`）

```powershell
docker compose run --rm -e E2E_REAL_API=1 e2e npx playwright test holding-search.real-api
```

MSW が有効なままだと実 API を見ていないので、各シナリオの冒頭で検出して失敗させる。

**実 DB には書き込まない**（GET だけ）。各行は独立していて、`--grep` で 1 本だけ抜き出してよい。

## 検証記録

**2026-10-02**（MSW off・`premarket-api` 起動。`GET /holdings` は 6 件）: 5 通過・3 スキップ・失敗 0。
スキップの 3 行は画面・API の不具合ではなく**テストデータの不足**なので `保留` にした（[requests.md](../api/requests.md) #32）。

- `HSR-04`（スキップ）: 明細 6 件すべてで `顧客名` / `顧客名カナ` が null（口座 1・3100 が顧客マスタに無い）
- `HSR-08`（スキップ）: 明細の口座が顧客マスタに無い（上と同じ理由）

1 回目の実行は全行が起動時の覆い（「読み込んでいます」）のまま失敗した。`GET /codes` がその時だけ 27.5 秒かかっていた
（直後の計測は 0.3〜0.5 秒、直叩き 87 ms）。別 worktree の実 API E2E と重なった負荷とみて、`--workers=2` で流し直して上の結果を得た。
