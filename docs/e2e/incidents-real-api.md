# 障害管理（実 API 接続）

- 略号: `IR`
- 画面: `src/views/IncidentManagementView.vue`
- テスト: `e2e/incidents.real-api.spec.js`

[incidents.md](incidents.md)（`IN`）と対象画面は同じだが、**当てる先が違う**。
`IN` は MSW のモックに当てて画面の挙動を細かく固定する。こちらは**実 API
（`/operations/order-suspensions` 配下）に当てて、フロントとバックエンドの噛み合わせだけ**を見る。
期待値はデータの中身に依存させず、現在値は実行時に画面と API から読んで比べる。

先頭の 2 行（IR-01 一覧 / IR-02 書き込み）がリリースまでの合格線の**スモーク**。
IR-03 以降はステージング期間に流す網羅の行で、次の噛み合わせを見る。

- 「現在の運用状態」の合成と全体停止中の抑止が、応答のフラグ（`発注停止中` / `全体停止中` / `停止中の対象`）どおりか（IR-03）
- 履歴の各列が `SuspensionHistoryItem` から読めているか。とくに停止理由は `変更後データ.停止理由` という
  description にしか書かれていないキーから読んでいる（IR-04）
- 履歴のページ送りで `offset` が実 API に効くか（IR-05）
- 楽観的ロックの 409 がダイアログにサーバの文言で出るか（IR-06）
- 再開の確認に出す停止時の記録（`停止理由` / `停止日時` / `停止者`）が応答から読めているか（IR-07）
- 全体（`ALL`）の停止・再開（進捗表の「注文入力制御」）が実 API に受理され、`全体停止中` の表示・ルートの抑止・
  履歴が応答どおりになるか（IR-08）。全体の楽観的ロックの 409（IR-09）

**全体（`ALL`）を止める行（IR-08 / IR-09）について。** 実 DB 上で注文の新規受付・取消と IB 発注・Dream 連携の
バッチまで止まるので、IR-03 の条件付きの確認（「そのとき全体が止まっていれば」）では「注文入力制御」の
実 API 軸が埋まらなかった。IR-08 / IR-09 は**全体もルートもすべて通常**のときだけ始め、1 つのテストの中で
停止と再開を対にし、途中で落ちても `afterEach` / `afterAll` が API を直接叩いて全体を再開する。
確実な再現の精度（色・文言の固定）は MSW 版（IN-12 / IN-20 / IN-23）に残す。

**置かない行と理由:**

- **「すでに停止中」の 400 は置かない。** 画面は停止中の対象には再開のダイアログを出すので、400 を起こすには
  古い画面から停止を送るしかない。そのとき `更新日時` も変わっているので、サーバが 400 と 409 のどちらを先に返すかが
  仕様（`openapi.json`）から決まらない。競合の経路は IR-06 の 409 で見る
- **停止理由の 422 は置かない。** 画面が空白だけの理由を送らず（`trim` で止める）、200 字を超える入力は
  `maxlength` で打てないので、画面からは届かない
- エラー応答（500）・ローディング・履歴 0 件の再現は MSW 版（IN-09 / IN-10 / IN-28）の担当

## 実行方法

既定では**動かない**（`E2E_REAL_API` が無ければ丸ごとスキップ）。実 API に当てるときだけ、
前提をそろえて本体セッションで実行する。

1. `.env` の `VITE_ENABLE_MSW` を `false` にして `docker compose up -d --force-recreate frontend`
2. バックエンドを起動しておく（`(cd ../Pre-Market_Trading && docker compose up -d api)`）

```powershell
docker compose run --rm -e E2E_REAL_API=1 e2e npx playwright test incidents.real-api
```

MSW が有効なままだと実 API を見ていないので、各シナリオの冒頭で検出して失敗させる。

## 実データを書き換える（IR-02 / IR-06 / IR-07 / IR-08 / IR-09）

**発注停止はバックエンド全体に効く。** 停止中は注文の新規受付・取消と、IB 発注・Dream 連携の
バッチが止まる。IR-02 / IR-06 / IR-07 / IR-08 / IR-09 はローカル DB の発注停止マスタを実際に書き換えるので、次を前提にする。

- **他の実 API E2E と排他で流す。** 実行中に別の画面の実 API E2E が注文を出すと拒否される
- **1 つのテストの中で停止と再開を必ず対にする。** 再開まで確かめてからテストを終える。
  途中で落ちたときに備えて `afterEach` でも API を直接叩き、停止中なら再開して戻す
- ルートの行（IR-02 / IR-06 / IR-07）が操作するのは**注文ルート 1 つ**（`2` VWAP）。
  IB（`1`）は自己取引も含むので避ける（2026-09-30 の取り込みで自己取引 `3` と OTC `4` のルート停止は廃止）
- 全体（`ALL`）を止めるのは IR-08 / IR-09 だけ。**全体もルートもすべて通常**でなければ始めない
  （全体が停止中・他のルートが停止中なら、誰かの意図した状態かもしれないので戻さずに失敗させて理由を出す。
  VWAP の残骸だけは前回の後片付け漏れとみなして再開する）。前提を通ったあとに全体が停止中なら
  それはこのテストが止めたものなので、`afterEach` / `afterAll` が API で再開する。
  全体停止が残ると注文の新規受付・取消が止まったままになるため、**実行後は画面か API で全体が通常に戻っていることを確かめる**
- 実行前に全体が停止中なら、ルートの操作は画面が塞ぐので**失敗させて理由を出す**（DB を先に戻す）

**戻せないもの**: 停止対象の `停止理由` / `停止日時` / `停止者` / `再開日時` / `再開者` / `更新日時` は
実行時の値になる（再開後も直前の停止理由を保持する仕様）。VWAP の `停止理由` は最後に流れた IR-07 の理由
（`E2E 再開確認 <時刻>`）、全体の `停止理由` は IR-09 の別経路の理由（`E2E 全体 別経路 <時刻>`）で終わる。
操作履歴は 1 回の実行で **10 行**積まれる（IR-02 / IR-06 / IR-07 / IR-08 / IR-09 が 2 行ずつ。
IR-06 / IR-09 はそれぞれ VWAP / 全体の `更新日時` が空のとき、下ごしらえでさらに 2 行積む）。
したがって**ローカルの開発 DB 専用**。共有環境・本番では実行しない。

**IR-01 以降は直列に実行する**（IR-06 は IR-02 で VWAP の `更新日時` が埋まっている前提を使う。
単独で流したときは下ごしらえで埋める。IR-09 も同様に IR-08 で全体の `更新日時` が埋まる）。
`--grep` で抜き出しても壊れはしないが、履歴の行数は上の見積もりからずれる。
