# 障害管理

- 略号: `IN`
- 画面: `src/views/IncidentManagementView.vue`
- テスト: `e2e/incidents.spec.js`
- 公開モック: `https://uspreorder-vmbhej3k.manus.space/operations/incidents`
- 単体側のシナリオ: [views-incident-management-view.md](../unit/views-incident-management-view.md) /
  [components-incidents-incident-control-dialog.md](../unit/components-incidents-incident-control-dialog.md)
- 実 API 側のシナリオ: [incidents-real-api.md](incidents-real-api.md)（`IR`・スモーク 2 本）

障害発生時に、全体（`ALL`）または注文ルート別に発注を停止・再開する画面。
API は `/operations/order-suspensions` 配下の 4 本（照会・履歴・停止・再開。`docs/api/openapi.json`）。

## この画面の前提（読む前に）

**画面は仕様の「停止対象」の表にしてある。** 公開モックの「IB送信制御 / 注文入力制御」の 2 区画は採らない。
仕様の停止対象（`ALL` + 注文ルート 5 種）と軸が違い、2 区画のままだと みずほ / VWAP / 自己取引 / OTC の
停止が画面に出ない。モックの「全体を止めるか、経路だけ止めるか」は、表の先頭行（全体）で表す。

**「現在の運用状態」の文言だけは画面が合成する。** サーバはフラグ（`発注停止中` / `全体停止中` /
`停止中の対象`）しか返さないので、`src/utils/suspensionState.js` が
「全体停止中」/「一部停止中（IB, VWAP）」/「通常運用」を組み立てる。

**「操作利用者（モック）」セレクタは実装しない。** 公開モックのヘッダ右にある 001〜006 の切り替えは、
(1) 権限仕様が無く切り替えても何も変わらない、(2) 操作者コードは `src/api/client.js` が環境変数
`VITE_USER_CODE` から全リクエストに `X-User-Code` として載せており、画面から切り替えるには共有資産に
口を開ける必要がある（SSO 導入時に捨てる作りになる）、(3) モック側も `<form>` に submit ハンドラが無く
モック作成時の確認用治具と読める、の 3 点による。

**操作履歴 0 件は「空」ではない。** ローディング / エラー / 空 / データあり の 4 状態は
「停止状態と履歴をまとめた 1 回の取得」に対して 1 本引く。履歴が 0 件でも停止対象の表は出るので、
それはデータあり側の内訳になる（画面の「空」は停止状態そのものが取れなかったとき）。

## 既定モックの中身

- 停止対象: 6 行（全体 / みずほ / IB / VWAP / 自己取引 / OTC の順）。すべて「通常」
- 全体と IB は過去に停止して再開した記録を持ち、停止理由が残っている（仕様: 再開後も直前の理由を保持）
- 現在の運用状態: `通常運用`
- 操作履歴: 4 件（新しい順）
- 停止・再開はモックの状態を書き換える（テストごとに `resetMockState()` で戻るのは単体テストだけ。
  E2E はハンドラの状態がページの JS に載っているので、`page.goto()` で読み込み直せば初期状態に戻る）

**欠番: `IN-03` / `IN-05`**（旧 2 区画の「区画が並ぶ」「制御する が押せない」。期待結果が反転したので削除した。
番号は再利用しない）。
