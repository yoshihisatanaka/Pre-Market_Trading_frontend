# 障害管理

- 略号: `IN`
- 画面: `src/views/IncidentManagementView.vue`
- テスト: `e2e/incidents.spec.js`（未作成）
- 公開モック: `https://uspreorder-vmbhej3k.manus.space/operations/incidents`
- 単体側のシナリオ: [views-incident-management-view.md](../unit/views-incident-management-view.md) /
  [components-incidents-incident-control-dialog.md](../unit/components-incidents-incident-control-dialog.md)

障害発生時に IB 送信と注文入力を**別々に**止めるための画面。現在の運用状態を見て、どちらを制御するかを
選び、確認ダイアログで意思を確かめる。

## この画面の前提（読む前に）

**API は全面的に仮置き。** `docs/api/openapi.json` の `/operations/` 配下は `activity-logs` と
`activity-logs/targets` の 2 本だけで、障害管理・発注停止のエンドポイントは 1 本も定義されていない。
形が確定したら `src/api/incidents.js` と `src/mocks/` の該当ハンドラだけを直す（画面は変えなくてよい）。
**実 API 版のシナリオ（`incidents-real-api.md`）は作らない**。パスごと存在しないので MSW を切ると
404 になるだけで、データの中身に依存しない検証すら成立しない。

**制御の実行（状態遷移）は未実装。** 公開モックも同じ段階で、ボタンには JS ハンドラが無く本文に
「現段階では制御ボタンの表示のみです」と書かれている。この画面では確認ダイアログを開くところまでを作り、
主ボタン「制御する」は **押せない状態（disabled）** にして理由を出す。押せるのに何も起きないボタンを
作ると、「押しても何も起きないこと」をテストが守ってしまい、次段で確実に嘘になる。

**「操作利用者（モック）」セレクタは実装しない。** 公開モックのヘッダ右にある 001〜006 の切り替えは、
(1) 権限仕様が無く切り替えても何も変わらない、(2) 操作者コードは `src/api/client.js` が環境変数
`VITE_USER_CODE` から全リクエストに `X-User-Code` として載せており、画面から切り替えるには共有資産に
口を開ける必要がある（SSO 導入時に捨てる作りになる）、(3) モック側も `<form>` に submit ハンドラが無く
モック作成時の確認用治具と読める、の 3 点による。

**障害対応履歴 0 件は「空」ではない。** ローディング / エラー / 空 / データあり の 4 状態は
「運用状態と履歴をまとめた 1 回の取得」に対して 1 本引く。履歴が 0 件でも運用状態と制御ボタンは出るので、
それはデータあり側の内訳になる（画面の「空」は運用状態そのものが取れなかったとき）。
