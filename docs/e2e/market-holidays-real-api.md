# 海外休場日マスタ（実 API 接続）

- 略号: `MR`
- 画面: `src/views/MarketHolidayListView.vue`
- テスト: `e2e/market-holidays.real-api.spec.js`

[market-holidays.md](market-holidays.md)（`MH`）と対象画面は同じだが、**当てる先が違う**。
`MH` は MSW のモックに当てて画面の細かい挙動を固定する。こちらは**実 API に当てて、
フロントとバックエンドの噛み合わせだけ**を見る。

## なぜ分けるか

`MH` は「既定モックは 56 件」「1 行目は 2029-12-26」のようにフィクスチャの中身を
期待値にしている。実 API に当てるとデータが違うので全滅し、しかも
`mockApi()`（`window.__mswOverrides`）は MSW を切ると効かないため、
エラー応答や 0 件の再現も成立しない。
`MH` を実データでも通るように書き換えると、代わりに画面の精度を失う。

そこで**期待値の立てかたを変えた別ファイル**にする。ここでは
「登録したら 1 件増える」「削除したら消える」のように、**データの中身に依存しない
不変条件**だけを書く。件数・日付は実行時に画面から読み取って比べる。

## 実行方法

既定では**動かない**（`E2E_REAL_API` が無ければ丸ごとスキップ）。実 API に当てるときだけ、
2 つの前提をそろえて実行する。

1. `.env` の `VITE_ENABLE_MSW` を `false` にして `docker compose up -d --force-recreate frontend`
2. バックエンドを起動しておく（`(cd ../Pre-Market_Trading && docker compose up -d api)`）

```powershell
docker compose run --rm -e E2E_REAL_API=1 e2e npx playwright test market-holidays.real-api
```

MSW が有効なままだと実 API を見ていないので、各シナリオの冒頭で検出して失敗させる。

## 実データを書き換える

MR-04 以降は**実 DB に登録・削除を行う**。ローカルの開発 DB を前提にしているので、
共有環境では実行しない。

使う日付は実運用のデータと混ざらないよう 2035 年に寄せ、**まだ一度も使われていない日**を
実行時に選ぶ。削除が論理削除なので、一度使った日付をもう一度登録すると
「再有効化」の経路に入ってしまい、MR-04（素の新規登録）が確かめられなくなるため。
終了時にその行を論理削除して戻すので、有効な行としては残らない。

つまり **1 回の実行につき、2035 年に取り消し済みの行が 1 件たまる**。
繰り返し実行しても結果は変わらないが、増えすぎたら DB から整理してよい
（365 日ぶんを使い切ると実行できなくなり、その旨のエラーで止まる）。

MR-04〜08 は 1 本の流れ（登録 → 重複 → 削除 → 警告 → 再有効化）なので**順に実行する**。
途中だけを `--grep` で抜き出すと前提が崩れる。

| ID | 前提 | 操作 | 期待結果 | 状態 |
|---|---|---|---|---|
| MR-01 | 実 API に接続。データ件数は問わない | 一覧を開く | 表が描画され、件数表示の数と表の行数が一致する（1 ページ分を超える分は 2 ページ目以降）。ページ送りが出て、エラーは出ない。0 件のときだけ空状態になりページ送りは出ない | 実装済 |
| MR-02 | 実 API に接続 | 短縮取引日「短縮取引日」で検索する | URL に `holiday_type=1` が付き、表示された行の短縮取引日列がすべて「13:00 ET 終了」になる。件数は全件以下になる | 実装済 |
| MR-03 | 実 API に接続 | 一覧の最初の行の日付を日付に入れて検索する | URL に `date=` が付き、その日付の行だけが表示され、件数が「1 件」になる | 実装済 |
| MR-04 | 実 API に接続。試験用の日付（2035 年の未使用日）は未登録 | その日付と休場理由を入れて「追加」を押す | モーダルが閉じて成功メッセージが出る。件数が 1 増え、その日付の行が一覧に現れる | 実装済 |
| MR-05 | MR-04 の直後 | 同じ日付でもう一度「追加」を押す | モーダルは閉じず、事前検証の理由（既に登録されている旨）が表示される。件数は変わらない | 実装済 |
| MR-06 | MR-04 の直後 | その行の「削除」→「削除する」を押す | 削除ボタンの `data-testid` が `market-holidays-delete-<数字>`（行の `ID`）になっている。モーダルが閉じて成功メッセージが出る。件数が 1 減り、その行が一覧から消える | 実装済 |
| MR-07 | MR-06 の直後（その日付は取り消し済み） | 同じ日付でもう一度「追加」を押す | モーダルは閉じず、再有効化の警告が表示され、送信ボタンの文言が「続行」になる。件数は変わらない | 実装済 |
| MR-08 | MR-07 の直後（警告が出ている） | 送信ボタン（「続行」）を押す | モーダルが閉じて成功メッセージが出る。件数が 1 増え、その日付の行が一覧に戻る。戻った行も `data-testid` が数字の id を持つ | 実装済 |

## 行の指しかた（MR-06 / MR-08）

主キーは `ID`（integer のサロゲートキー）で、**休場日は主キーではない**。削除ボタンの
`data-testid` には行の `id` が入るが、実 API の採番なので**値は実行時にしか判らない**。
そこで日付で行を絞ってからその行の「削除」を引き、`data-testid` が
`market-holidays-delete-<数字>` になっていることだけを確かめる。
ここが `market-holidays-delete-`（id が空文字）なら実 API が `ID` を返していない徴候なので、
対象を特定できずに落ちる前に、原因の判る形で止まる。

実 API は再有効化で**元の行の `ID` を引き継ぐ**（2026-09-18 に実測。
[../api/requests.md](../api/requests.md) の依頼 #10）が、**それは期待値にしない**。
採番の仕様はこの画面の受け入れ条件ではなく、変わっても落とす意味が無いため。
`MR-08` が見るのは「どちらであれ id が付いている」ことだけ。

## MR-04〜08 の保留は解消した（2026-09-18）

2026-09-17 の時点では、実 API が `ID` を返さず行を特定できないため、書き込み系の 5 本を
`PENDING_BACKEND_ID` で丸ごと止めていた（`MR-04` / `MR-05` だけは id を使わないが、この 5 本は
「登録 → 重複 → 削除 → 警告 → 再有効化」の直列 1 本で、削除だけを止めると試験用の日付が
実 DB に残って次回の `MR-04` が失敗するため、流れごと止めていた）。

2026-09-18 の取り込みで仕様が `/masters/market-holidays/{holiday_id}` と
`MarketHolidayItem.ID`（required）を定義したので、定数ごと外して 8 本すべてを実行している。
