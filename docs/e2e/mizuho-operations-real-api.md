# みずほ注文締（実 API 接続）

- 略号: `MZR`
- 画面: `src/views/MizuhoOperationsView.vue`
- テスト: `e2e/mizuho-operations.real-api.spec.js`

[mizuho-operations.md](mizuho-operations.md)（`MZ`）と対象画面は同じだが、**当てる先が違う**。
`MZ` は MSW のモックに当てて画面の細かい挙動を固定する。こちらは**実 API（`GET /closing/status` /
`POST /closing/mizuho` / `POST /closing/mizuho/reset` / `GET /executions` / `GET /executions/export-csv`）に当てて、
フロントとバックエンドの噛み合わせだけ**を見る。

## なぜ分けるか

`MZ` はフィクスチャの中身（約定 12 件・先頭は `#1`・部店 `123` + `AMD` で 1 件・締め状態は毎回「受付中」から始まる）を
期待値にしている。実 API に当てるとデータが違うので全滅し、`mockApi()`（`window.__mswOverrides`）は MSW を切ると
効かないため、500 / 403 の再現・締め済からの開始（`MZ-05〜07`）・CSV 出力の失敗（`MZ-25`）も成立しない。
そこで**データの中身に依存しない不変条件**だけを書く。絞り込みに使う値は、開いた時点（条件なし）に
**画面自身が受け取った `GET /executions` の応答**の先頭の約定から読む（テストから API を直接引かないのは、
`X-User-Code` が画面（`.env` の `VITE_USER_CODE`）と違うと部店の限定で見える約定が変わるため。約定照会 `EXR` と同じ）。
エラー応答・ローディング・0 件の網羅と、注文ファイル作成（`MZ-21 / 22`）は `MZ` の担当で、ここでは求めない。

この画面の噛み合わせで壊れやすいのは次の 4 つ。

- **締め状態の読み取りと往復。** `GET /closing/status?closing_type=MIZUHO` の `締め状態`（0 / 1）を「受付中 / 締め済」に
  写し、`POST /closing/mizuho` / `POST /closing/mizuho/reset` の応答で差し替える。`openapi.json` は
  2026-10 の取り込みで `history` と「本文の `実行者` は無視（`X-User-Code` で記録）」が入っており（Phase 62）、
  `src/api/closing.js` の前提（照会は `更新日時` / `実行者` を返さない）と食い違っている可能性がある。
  ここでは**両方で通る不変条件**だけを書く（状態の語・ボタンの出し分け・履歴行は操作の応答から出る）
- **`route=0` の固定。** 一覧も CSV も `src/api/mizuhoExecutions.js` が `route=0`（みずほ）を必ず付ける。
  付かなければ他の預託先の約定が混ざるが、MSW 版では気づけない
- **クエリ名の変換。** URL の `date_from` / `date_to` を api 層が `start_date` / `end_date` に変える。
  売買区分と出来状況は URL も実 API も同じコード（`side=1` / `status=010`）
- **CSV 出力が一覧と同じ条件で落ちること。** 本文はバックエンドが作る（列の並びは画面側で固定しない）

## 実行方法

既定では**動かない**（`E2E_REAL_API` が無ければ丸ごとスキップ）。実 API に当てるときだけ、前提をそろえて実行する。

1. `.env` の `VITE_ENABLE_MSW` を `false` にして `docker compose up -d --force-recreate frontend`
2. バックエンドを起動しておく（`(cd ../Pre-Market_Trading && docker compose up -d api)`）
3. `.env` の `VITE_USER_CODE` を設定しておく（締め・締め解除の実行者は `X-User-Code` で記録される。
   未設定だと `SYSTEM` で記録されるか 422 で弾かれる）

```powershell
docker compose run --rm -e E2E_REAL_API=1 e2e npx playwright test mizuho-operations.real-api
```

MSW が有効なままだと実 API を見ていないので、各シナリオの冒頭で検出して失敗させる。
バックエンドの `api` と DB は 1 つしかないので、**実 API E2E は worktree 間で排他**にする。

## 実データを書き換える

**みずほの締め状態は基準日ごとに 1 つしか無い共有の状態**で、「まだ使われていない値を選んで副作用を隔離する」ことが
できない。そこで**退避と復元**で辻褄を合わせる。

- `beforeAll` で `GET /api/closing/status?closing_type=MIZUHO` を取り、`締め状態` を退避する
- `MZR-02` は**実行前の状態から往復**する。受付中なら 締め → 締め解除、締め済なら 締め解除 → 締め の順に
  画面から操作し、終わりに実行前の状態へ戻っていることを API でも確かめる
- `afterAll` で `締め状態` を取り直し、退避値と違っていれば（途中で落ちた場合）`POST /closing/mizuho` か
  `POST /closing/mizuho/reset` を直接叩いて戻す

**戻せないものがある。**

| 項目 | 実行後 |
|---|---|
| `更新日時` / `実行者` | 最後の操作の時刻・`X-User-Code`（画面からは `VITE_USER_CODE`、afterAll の復元は `e2e`）になる |
| 締め・解除の履歴（`ClosingStatusResponse.history`） | 1 回の実行で 2 行（往復）積まれる。消す API は無い |

**締め状態そのものは実行前に戻る**（締め済のあいだに受け付けられなかったみずほ注文があれば影響するので、
ローカルの開発 DB 専用。共有環境・本番では実行しない）。約定一覧と CSV 出力は GET だけで、何も書かない。

`MZR-01 → MZR-02` は `serial` で順に実行する。`MZR-03` 以降は独立していて、`--grep` で 1 本だけ抜き出してよい。
約定が 0 件なら `MZR-01` は空状態を確かめて通り、値を 1 行目から読む行は**スキップ**する。
