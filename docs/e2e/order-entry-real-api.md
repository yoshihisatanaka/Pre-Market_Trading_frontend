# 新規注文（実 API 接続）

- 略号: `NR`
- 画面: `src/views/OrderEntryView.vue`（`/orders/new`）
- テスト: `e2e/order-entry.real-api.spec.js`

[order-entry.md](order-entry.md)（`NO`）と対象画面は同じだが、**当てる先が違う**。
`NO` は MSW のモックに当てて画面の挙動を細かく固定する。こちらは**実 API
（`/masters/symbols`・`/masters/customers`・`/orders/validate`・`/orders` ほか）に当てて、フロントとバックエンドの
噛み合わせだけ**を見る。期待値はデータの中身に依存させず、照会に使う口座番号・ティッカーは
実行時に API から 1 件読んで決める。

先頭 2 行はスモーク（照会 1 本・事前検証 1 本）。この画面は一覧ではなく入力フォームなので、
`-01` を「画面表示と照会」、`-02` を「送信（事前検証）」に読み替えている。
**`NR-02` は事前検証（`POST /orders/validate`）までで止め、注文は確定しない。** 確定は `NR-06` が受け持ち、
作った注文はその場で取り消す（下の「実データを書き換える」）。

## なぜ分けるか

`NO` はフィクスチャの中身（顧客名「高橋 みどり」・AAPL の前日終値・為替 150.25・採番 1005〜）を期待値にしている。
実 API に当てるとデータが違うので全滅し、`mockApi()`（`window.__mswOverrides`）は MSW を切ると効かないため、
初期読み込みの 500・0 件（期間指定の空）・権限なし・全体停止中・事前検証や登録の 500 / 不受付の再現も成立しない。
**それらは `NO` の担当**で、ここでは実データで成り立つ不変条件だけを書く。

## 実行方法

既定では**動かない**（`E2E_REAL_API` が無ければ丸ごとスキップ）。実 API に当てるときだけ、
前提をそろえて本体セッションで実行する。

1. `.env` の `VITE_ENABLE_MSW` を `false` にして `docker compose up -d --force-recreate frontend`
2. バックエンドを起動しておく（`(cd ../Pre-Market_Trading && docker compose up -d api)`）
3. `.env` の `VITE_USER_CODE` に**発注権限のある**社員コードを入れておく（権限なし・全体停止中なら `NR-02` 以降はスキップされる）
4. `NR-06` を流すときは、**IB 発注・Dream 連携のワーカー（バッチ）を止めておく**（下記）

```powershell
docker compose run --rm -e E2E_REAL_API=1 e2e npx playwright test order-entry.real-api
```

MSW が有効なままだと実 API を見ていないので、各シナリオの冒頭で検出して失敗させる。

## 実データを書き換える

`NR-01`〜`NR-05` は GET と `POST /orders/validate`（DB に書かない）だけで、DB に何も残さない。

**`NR-06` は `POST /orders` で `d_注文` に注文を 1 件作る。** ローカルの開発 DB 前提。

- 作った注文は、完了画面を確かめた直後に `POST /orders/{order_id}/cancel` で取り消す
  （未発注 `000` の注文は即時取消 `034` になる。openapi.json の cancel の説明）。テストが途中で落ちても
  `afterAll` が、この実行で作った注文 ID を取り消す
- 注文は物理削除できないので、**1 回の実行につき取消済み（`034`）の注文が 1 件残る**
- 作成から取消までのあいだに IB 発注のワーカーが `000` を拾うと、取消が「取消依頼（`030`）」の経路に入り、
  発注まで進む恐れがある。**ワーカーを止めてから流す**。取消の応答の `status` は報告用に標準出力へ残す
- 数量は 1 株・成行・買いに固定し、口座と銘柄は実行時に API の先頭から選ぶ（特定の顧客を狙わない）

## 未確定の仕様（docs/api/requests.md #24）

事前検証の業務エラーを 200 の `valid:false` で返すか 4xx で返すかが未確定。`NR-02` は
**どちらで返っても**「確認画面へ進む」か「理由の帯が出る」かのどちらかになることだけを見て、
帯の種類（入力エラー / 通信エラー）までは固定しない。`NR-06` は、事前検証で確認画面へ進めなかったとき
（実データの残高・余力・規制で弾かれた）は前提が成り立たないのでスキップする。

**NR-07 を保留にした理由:** `規制情報` のコード値が未確定（openapi.json の `SymbolItem` に enum が無く、
`src/utils/symbolTypes.js` の 0 / 1 は仮置き）で、どの銘柄が「取引不可」かを実データから選べない。さらに
業務エラーを 200 の `errors` で返すか 4xx で返すか（docs/api/requests.md #24）が決まるまで、帯の種類を固定できない。
どちらかが決まったら `未着手` に戻す。

**NR-02 と NR-06 は同じ口座・銘柄を使うが、互いに依存しない**（どちらも画面を開き直して入力から始める）。
`--grep` で 1 本だけ抜き出しても前提は崩れない。
