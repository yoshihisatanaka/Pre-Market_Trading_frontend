# 注文照会・注文訂正・注文取消（実 API 接続）

- 略号: `OIR`
- 画面: `src/views/OrderInquiryListView.vue`（一覧）/ `src/views/OrderAmendView.vue`（訂正）/ `src/views/OrderCancelView.vue`（取消）
- テスト: `e2e/order-inquiry.real-api.spec.js`

[order-inquiry.md](order-inquiry.md)（`OI`）/ [order-amend.md](order-amend.md)（`OAM`）/ [order-cancel.md](order-cancel.md)（`OCN`）と
対象画面は同じだが、**当てる先が違う**。あちらは MSW のモックに当てて画面の細かい挙動を固定する。
こちらは**実 API（`GET /orders`・`GET /orders/{order_id}`。`OIR-02` / `OIR-12` は試験注文に対する `POST /orders/{order_id}/cancel`・`/amend` も）に当てて、フロントとバックエンドの噛み合わせだけ**を見る。
訂正・取消は注文照会から入る別ルートだが、同じ `GET /orders` のデータを起点にするので 1 つの文書と spec にまとめる。

## なぜ分けるか

`OI` / `OAM` / `OCN` はフィクスチャの中身（注文 15 行・画面の行 9 行・`#35` が先頭・`#30` は訂正 2 回）を期待値にしている。
実 API に当てるとデータが違うので全滅し、`mockApi()`（`window.__mswOverrides`）は MSW を切ると効かないため、
エラー応答・404・権限なしの差し替え（`OI-14` / `OI-21` / `OAM-03`〜`05` / `OCN-03`〜`05`）も成立しない。
そこで**データの中身に依存しない不変条件**だけを書く。絞り込みに使う値は、開いた時点（条件なし）に
**画面自身が受け取った `GET /orders` の応答**から読む。テストから API を直接引かないのは、`X-User-Code` が
画面（`.env` の `VITE_USER_CODE`）と違うと部店の限定（`branch_code` の説明）で見える注文が変わるため。

この画面の噛み合わせで壊れやすいのは次の 4 つ。

- **件数と行数が一致しない画面である。** 件数表示はサーバの `total`（注文の行数。訂正前の版とスライス子注文を含む）で、
  表の行は `元注文ID` で畳んだ元注文ごとのまとまり。`src/api/orderInquiry.js` の `groupOrders` の規則で
  **応答からまとまりの数を再計算して**行数と比べる（他の画面の「件数 = 行数」は使えない）
- **クエリ名の変換。** URL の `account_number` を api 層が `account_no`（integer）に変えて送る。
  `status` は処理状況コードをそのまま載せる。FastAPI は知らないクエリを黙って無視するので、ずれても MSW 版では気づけない
- **出来状況の選択肢はコードマスタ `注文照会出来状況`から来る。**
  2026-10-06 に実 API の `/codes` に入った（`docs/api/requests.md` #30）。無くなれば選択肢が空になり、
  絞り込みの行はスキップする（それ自体が報告になる）
- **訂正・取消の画面は `GET /orders/{order_id}` の `order`（`OrderRecord`）を読む。** 一覧の `OrderItemResponse` と
  同じ日本語キーだが、`指値単価` が decimal の文字列（`'410.0000'`）で来る。画面の初期値が応答の値と一致することを見る

## 2 本目（書き込み）: 試験注文を作ってすぐ取り消す

合格線のスモークは「一覧 1 本・書き込み 1 本」だが、この画面の書き込み（訂正・取消）は**既存の注文を壊す**。
そこで既存の注文には触らず、**試験注文をテストの中で作り、訂正・取消のあと必ず取り消す**。
この運用は 2026-10-09 に認められた（それまでは `OIR-02` / `OIR-12` を保留にしていた。
理由は、作った直後にバッチが IB 発注・Dream 登録へ進めると、取消が取消依頼（030）に変わり 133 で止まりうるため）。

- **バッチ（`premarket-scheduler`）を止めてから流し、終わったら戻す。** 止めていれば未発注（000）の注文は
  その場で取り消され（000 → 034）、訂正もその場で反映される（`mode` が `IN_PLACE`）。止めるのは実行する人の役目で、
  spec は止まっていることを前提にする（動いていると `OIR-02` の 034・`OIR-12` の `IN_PLACE` が崩れて落ちる）
- 試験注文は**新規注文の画面（`/orders/new`）から作る**（`POST /orders/validate` → `POST /orders`）。
  画面の操作者（`.env` の `VITE_USER_CODE`）で作れば注文照会に必ず見え（部店の限定がそろう）、区分値・有効期限は
  画面が組み立てる。口座は [order-entry-real-api.md](order-entry-real-api.md) の `NR-01` / `NR-06` と同じく
  顧客マスタの先頭の有効な行（操作者の部店のもの。全部店の参照権限があれば先頭）を優先し、エクイティ／リスク商品の
  買付停止の口座は除く。**銘柄は、その口座に取消済（034）でない注文が無いもの**を銘柄マスタの先頭から選ぶ
  （事前検証は同一口座・同一銘柄・同一売買区分の未取消の注文が本日あると `valid:false` で弾き、`重複確認区分=1` での
  再送を求めるが、画面に再送の操作が無いため。取消済は重複に数えない。2026-10-09 実測）。
  口座の業務制限（確認書類の未受入・コンプライアンスランク A）はマスタの項目では見分けきれないので、口座を変えるより銘柄を変える。
  買い・数量 1・成行・円決・当日中（画面の既定は指値・外決なので、成行と円決は押して選ぶ）。事前検証で確認画面へ進めない（余力・規制・発注停止）ときは**前提不成立でスキップ**する
- 後始末は `afterAll` と各テストの `finally` で、作った注文のうち**まだ取消できる処理状況のものを
  `POST /orders/{id}/cancel` で取り消す**（`X-User-Code` は画面の操作者にそろえる）。テストが途中で落ちても未発注のまま残さない
- **1 回の実行につき、取消済（034）の試験注文が 2 件残る**（`OIR-02` で 1 件・`OIR-12` で 1 件。`OIR-12` の 1 件は数量が 2）。
  消す手段は無いので、ローカルの開発 DB に限る
- `OIR-07` / `OIR-08` は開いた時点の件数と比べるので、試験注文の作成と並列に走ると揺れる。
  この spec は 1 つの worker で宣言順に流し、書き込みの 2 行を最後に置いている。
  同じ時間に別の spec（`order-entry.real-api` の `NR-06` など）で注文を作らない

## 実行方法

既定では**動かない**（`E2E_REAL_API` が無ければ丸ごとスキップ）。実 API に当てるときだけ、前提をそろえて実行する。

1. `.env` の `VITE_ENABLE_MSW` を `false` にして `docker compose up -d --force-recreate frontend`
2. バックエンドを起動しておく（`(cd ../Pre-Market_Trading && docker compose up -d api)`）
3. `OIR-02` / `OIR-12` を流すときは、バックエンドのバッチ（`premarket-scheduler`）を止めておく。終わったら戻す

```powershell
docker compose run --rm -e E2E_REAL_API=1 e2e npx playwright test order-inquiry.real-api
```

MSW が有効なままだと実 API を見ていないので、各シナリオの冒頭で検出して失敗させる。

**実 DB には書き込まない。ただし `OIR-02` / `OIR-12` だけは例外**で、試験注文を作って取り消す（上の節）。
それ以外の行は GET だけで、訂正・取消の確定ボタンは押さない。各行は独立していて、`--grep` で 1 本だけ抜き出してよい
（書き込みの 2 行も、それぞれ自分の試験注文を作って片付けるので単独で流せる）。
注文が 0 件なら `OIR-01` は空状態を確かめて通り、値を応答から読む行は**スキップ**する。

## 検証記録

### 2026-10-09（MSW off・`VITE_USER_CODE=admin`・`premarket-scheduler` 停止）

`--grep "\[OIR-(02|12)\]"` を 1 回、続けて `--repeat-each=2` で 4 本、すべて通過。試験注文 #1966〜#1973 を作り、
すべて取消済（034）で残した（OIR-12 の訂正は `mode: IN_PLACE`・`amendment_order_id: null`）。
最初の数回は次の 3 点で落ち、spec を直した（いずれもバックエンドの不具合ではない）。

- 先頭の口座・銘柄に未取消の注文（#1961）があり、事前検証が重複で弾いた → 未取消の注文の無い銘柄を選ぶ
- 口座の業務制限（買付停止・確認書類・コンプライアンスランク）で弾かれた → 買付停止の口座を除き、先頭の口座で銘柄を変える
- 行の特定に使った正規表現 `#<id>(?!\d)` が、行の textContent（`#1964100…` と部店の数字が続く）に当たらなかった
  → `#<id>` だけを持つ要素で絞る
