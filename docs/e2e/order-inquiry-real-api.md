# 注文照会・注文訂正・注文取消（実 API 接続）

- 略号: `OIR`
- 画面: `src/views/OrderInquiryListView.vue`（一覧）/ `src/views/OrderAmendView.vue`（訂正）/ `src/views/OrderCancelView.vue`（取消）
- テスト: `e2e/order-inquiry.real-api.spec.js`

[order-inquiry.md](order-inquiry.md)（`OI`）/ [order-amend.md](order-amend.md)（`OAM`）/ [order-cancel.md](order-cancel.md)（`OCN`）と
対象画面は同じだが、**当てる先が違う**。あちらは MSW のモックに当てて画面の細かい挙動を固定する。
こちらは**実 API（`GET /orders`・`GET /orders/{order_id}`）に当てて、フロントとバックエンドの噛み合わせだけ**を見る。
訂正・取消は注文照会から入る別ルートだが、同じ `GET /orders` のデータを起点にするので 1 つの文書と spec にまとめる。

## なぜ分けるか

`OI` / `OAM` / `OCN` はフィクスチャの中身（注文 14 行・画面の行 8 行・`#35` が先頭・`#30` は訂正 2 回）を期待値にしている。
実 API に当てるとデータが違うので全滅し、`mockApi()`（`window.__mswOverrides`）は MSW を切ると効かないため、
エラー応答・404・権限なしの差し替え（`OI-14` / `OI-21` / `OAM-03`〜`05` / `OCN-03`〜`05`）も成立しない。
そこで**データの中身に依存しない不変条件**だけを書く。絞り込みに使う値は、開いた時点（条件なし）に
**画面自身が受け取った `GET /orders` の応答**から読む。テストから API を直接引かないのは、`X-User-Code` が
画面（`.env` の `VITE_USER_CODE`）と違うと部店の限定（`branch_code` の説明）で見える注文が変わるため。

この画面の噛み合わせで壊れやすいのは次の 4 つ。

- **件数と行数が一致しない画面である。** 件数表示はサーバの `total`（注文の行数。訂正前の版とスライス子注文を含む）で、
  表の行は `元注文ID` で畳んだ元注文ごとのまとまり。`src/api/orderInquiry.js` の `groupOrders` の規則で
  **応答からまとまりの数を再計算して**行数と比べる（他の画面の「件数 = 行数」は使えない）
- **クエリ名の変換。** URL の `account_number` を api 層が `account_no`（integer）に変えて送る。
  `status` は処理状況コードをそのまま載せる。FastAPI は知らないクエリを黙って無視するので、ずれても MSW 版では気づけない
- **出来状況の選択肢はコードマスタ `注文照会出来状況`から来る。**
  2026-10-06 に実 API の `/codes` に入った（`docs/api/requests.md` #30）。無くなれば選択肢が空になり、
  絞り込みの行はスキップする（それ自体が報告になる）
- **訂正・取消の画面は `GET /orders/{order_id}` の `order`（`OrderRecord`）を読む。** 一覧の `OrderItemResponse` と
  同じ日本語キーだが、`指値単価` が decimal の文字列（`'410.0000'`）で来る。画面の初期値が応答の値と一致することを見る

## 2 本目（書き込み）を保留にする理由

合格線のスモークは「一覧 1 本・書き込み 1 本」だが、この画面の書き込み（訂正・取消）は**既存の注文を壊す**。
試験用の注文を `POST /orders` で作って訂正・取消まで流す案は、次の理由でいまは採らない。

- [order-entry-real-api.md](order-entry-real-api.md) が `POST /orders` の確定を「`d_注文` に行が残り、IB 発注・Dream 連携の
  バッチの対象になるため、消す手段がそろってから（10/15 以降）」と決めている。作った直後に取り消しても、
  その隙にバッチが Dream へ登録すると取消が取消依頼（030）に変わり、ローカルでは 133（Dream取消失敗）で止まりうる
- 試験注文を API で作るには `強制区分`・残高・区分値の組合せが要り、業務エラーの返し方が未確定（`docs/api/requests.md` #24）

そこで `OIR-02`（取消の送信）と `OIR-12`（訂正の送信）は**保留**にし、訂正・取消は「画面が開いて API の値と一致し、
確定ボタンが出る」ところまでを見る（`OIR-10` / `OIR-11`。**確定は押さない**）。
解除の条件は、ローカルでバッチを止めた状態で試験注文を作って即時取消（000 → 034）する運用が認められること。
その形なら 1 回の実行につき取消済の注文が 1 件残る。

## 実行方法

既定では**動かない**（`E2E_REAL_API` が無ければ丸ごとスキップ）。実 API に当てるときだけ、前提をそろえて実行する。

1. `.env` の `VITE_ENABLE_MSW` を `false` にして `docker compose up -d --force-recreate frontend`
2. バックエンドを起動しておく（`(cd ../Pre-Market_Trading && docker compose up -d api)`）

```powershell
docker compose run --rm -e E2E_REAL_API=1 e2e npx playwright test order-inquiry.real-api
```

MSW が有効なままだと実 API を見ていないので、各シナリオの冒頭で検出して失敗させる。

**実 DB には書き込まない**（GET だけ。訂正・取消の確定ボタンは押さない）。各行は独立していて、`--grep` で 1 本だけ抜き出してよい。
注文が 0 件なら `OIR-01` は空状態を確かめて通り、値を応答から読む行は**スキップ**する。
