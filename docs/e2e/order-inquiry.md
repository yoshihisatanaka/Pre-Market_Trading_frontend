# 注文照会

- 略号: `OI`
- 画面: `src/views/OrderInquiryListView.vue`
- テスト: `e2e/order-inquiry.spec.js`

**当てる先は MSW のモック。** 期待値にフィクスチャの中身（注文 ID・件数）を使うので、実 API に当てると通らない。

`/orders/inquiry` の受け入れ条件。元注文ごとに 1 行を出し、訂正履歴と自動分割（スライス）の明細を
その下に畳んで持つ一覧。検索条件は URL クエリ（`branch_code` / `account_number` / `symbol` / `status`）を
正としているため、**実ブラウザでの URL と画面の同期**をここで守る。

既定モック（`src/mocks/fixtures/orderInquiry.js`）は注文 15 行で、画面の行は元注文ごとにまとめた 9 行。
並びはサーバの既定（注文 ID の降順）で、まとまりが最初に現れた位置に出るので先頭行は `#35`
（子注文 `#45` が最も新しい）。件数の表示はサーバの `total`（注文の行数）なので「15 件」になる。
同じフィクスチャを滞留注文抽出（[stalled-orders.md](stalled-orders.md)）も処理状況で絞って読む。

出来状況の絞り込み（OI-16〜20）は、選択肢（コードマスタ `注文照会出来状況`）の値が
処理状況コードで、それを `status` に載せて送り、既定ハンドラがカンマ区切りのどれかとの完全一致で絞る。
取消済（`034`）は `032,034`、注文エラー（`101`）は `101,103` に api 層が広げて送る（URL は `034` / `101` のまま）。
既定モックに `032` の行は無く、`103`（IB発注失敗）は `#29` の 1 行だけある（注文エラーで絞ると `#40` と `#29` が当たる）。
**絞り込みは行単位**なので、当たった行だけが元注文ごとにまとめ直される
（訂正前の版だけが当たる・子注文だけが当たって 1 行ずつ出る、が起こる）。URL にも処理状況コード
（`status=003`）が載る。

操作列と「新規注文」は発注権限（`GET /auth/me` の `権限.order`）で出し分ける。既定モックは管理責任者（権限あり）。
権限なし（OI-21）は `/auth/me` を `noOperationOperator` に差し替えて見る。
「訂正」「取消」はその元注文の**最新の版**の ID で別画面へ移る（OI-22 / 23）。移った先の画面は
[order-amend.md](order-amend.md)（`OAM`）/ [order-cancel.md](order-cancel.md)（`OCN`）が見る。

ローディングの過渡状態（モック応答が即座に返るため実ブラウザでは安定して観測できない）、選択肢に無い `status` を
手で URL に書いたときの無視、処理状況コードへの読み替えの表、まとめ直しの細かい分岐は単体テスト
（[views-order-inquiry-list-view.md](../unit/views-order-inquiry-list-view.md) /
[api-order-inquiry.md](../unit/api-order-inquiry.md) /
[components-orders-order-inquiry-table.md](../unit/components-orders-order-inquiry-table.md)）側で担保する。
