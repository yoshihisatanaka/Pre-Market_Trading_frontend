# 滞留注文抽出

- 略号: `SO`
- 画面: `src/views/StalledOrderListView.vue`
- テスト: `e2e/stalled-orders.spec.js`

`/operations/stalled-orders` の受け入れ条件。ブローカー・自システムの障害で発注できなかった
注文（**注文エラー**）と、別システムで発注しコンファメーションを取り込んだあと未約定のままの
注文（**注文中**）を、1 回の検索で 2 本の一覧に出し分ける画面。

検索条件は URL クエリ（`branch_code` / `account_number` / `symbol`）を正としているため、
**実ブラウザでの URL と画面の同期**をここで守る。ページャは無い（一覧は全件を出す）。

一覧に専用の API は無く、注文照会と同じ `GET /orders` を処理状況で絞って 2 回呼ぶ
（注文エラー = `status=101,103`、注文中 = `status=003`。`src/api/stalledOrders.js`）。
MSW も注文照会と共用の既定ハンドラ（`src/mocks/handlers/orders.js`）が
`src/mocks/fixtures/orderInquiry.js` の `orderInquiryRows` で応答し、処理状況・部店・口座番号・銘柄の
クエリを解釈する。既定モックで出るのは **注文エラー 2 件（#40 = 101 Dream発注失敗 / #29 = 103 IB発注失敗）・
注文中 2 件（#42 / #34）**。部店 `234` は注文エラーだけ（#29）、銘柄 `AAPL` は注文中だけ（#34）に当たるので、
**片方だけが空になる**確認に使える。

表の「確認状況」列にあたる項目はサーバに無い（docs/api/requests.md #1② で問合せ中）ため、
注文中の行の確認状況はいまは常に「—」になる（SO-03）。

処理状況ごとのエラー理由の選び分け（101 は `Dreamエラー内容` 優先 / 103 は `エラー内容` 優先）や、
`limit` の上限ずつのページ送り・口座番号が数字以外のときに送らない扱いは単体テスト側
（`src/api/stalledOrders.spec.js`）が持つ。既定モックは 200 件に満たないので、ページ送りは E2E では見ない。

**CSV 3 種（別システム発注CSVサンプル / 注文エラーのCSV出力 / コンファメーションCSVサンプル）は
サーバを通さずフロントで組み立てる**（`src/utils/stalledOrderCsv.js`）。ここでは実ブラウザで
ダウンロードが起き、ファイル名と中身（BOM 付き・CRLF・ヘッダ・行）が期待どおりかを見る（SO-15〜19）。
値の変換の細かい分岐（クォート・未知の区分の空欄など）は単体テスト側が持つ。

**コンファメーション CSV の取込（`POST /operations/stalled-orders/confirmation-import`）は
2026-10-07 の取り込みで仕様に入り、MSW のハンドラを消して実 API へ素通しさせている。**
一覧の `GET /orders` の既定ハンドラは、取込で一覧が変わる可変状態を持たない。
そのため取込のシナリオ（SO-20〜24）は、取込の応答（`CsvImportResponse` の生の形 / 400 の `{ detail }` /
500）を `mockApi()` で差し込んで、成功 / 行エラー / ファイルごとの拒否（400）/ 通信の失敗（500）の
4 通りの**画面の出し分け**だけを実ブラウザで通す。`mockApi()` は固定応答しか返せないので、
**取込の結果が一覧に反映されること（約定・取消の行が外れる、未約定の行が注文中へ移る）は検証しない**
（反映はバックエンドの責務。実 API 版のシナリオはまだ無い）。

アクセス制御（運用管理権限の無い利用者はこの画面に入れない）は画面をまたぐので
[access-control.md](access-control.md)（`AC`）が持つ。
