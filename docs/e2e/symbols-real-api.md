# 銘柄マスタ（実 API 接続）

- 略号: `SMR`
- 画面: `src/views/SymbolListView.vue`
- テスト: `e2e/symbols.real-api.spec.js`

[symbols.md](symbols.md)（`SM`）と対象画面は同じだが、**当てる先が違う**。
`SM` は MSW のモックに当てて画面の細かい挙動を固定する。こちらは**実 API に当てて、
フロントとバックエンドの噛み合わせだけ**を見る。

## なぜ分けるか

`SM` は「既定モックは 56 件」「先頭行は `S001`（AAPL）」「取引可で絞ると 51 件」のように
フィクスチャの中身を期待値にしている。実 API に当てるとデータが違うので全滅し、しかも
`mockApi()`（`window.__mswOverrides`）は MSW を切ると効かないため、
エラー応答（SM-08 / 17 / 25 / 26 / 33）や 0 件の再現も成立しない。
`SM` を実データでも通るように書き換えると、代わりに画面の精度を失う。

そこで**データの中身に依存しない不変条件**だけを書く。件数・銘柄コードは実行時に画面か API から読み取って比べる。
エラー応答・ローディング・0 件・列順・色分け・整形の網羅は `SM` の担当で、ここでは求めない。

この画面で特に見たい噛み合わせは次の 3 つ。

- **画面の URL クエリと実 API のクエリ名が違う**（画面 `symbol_code` / `regulation` / `order_route` / `vwap_target`
  ↔ 実 API `symbol` / `restriction` / `route` / `vwap_target`）。変換は `src/api/symbols.js` だけが持つ。
  旧名を送っても実 API はエラーにせず無視するので、**画面の件数と、同じ条件で API を直接引いた `total` を比べる**（SMR-03〜05）
- 一覧の配列キーが `stocks`（`SymbolListResponse`）
- 編集・削除のパスキーが行の `ID`（`/masters/symbols/{symbol_id}`、integer）

## 実行方法

既定では**動かない**（`E2E_REAL_API` が無ければ丸ごとスキップ）。実 API に当てるときだけ、
次の前提をそろえて実行する。

1. `.env` の `VITE_ENABLE_MSW` を `false` にして `docker compose up -d --force-recreate frontend`
2. バックエンドを起動しておく（`(cd ../Pre-Market_Trading && docker compose up -d api)`）
3. `.env` の `VITE_USER_CODE` が設定されていること（未設定だと画面から送る更新系が 422 になる）

```powershell
docker compose run --rm -e E2E_REAL_API=1 e2e npx playwright test symbols.real-api
```

MSW が有効なままだと実 API を見ていないので、各シナリオの冒頭で検出して失敗させる。
バックエンドの `api` と DB は 1 つしかないので、**実 API E2E は worktree 間で排他**にする。

## 実データを書き換える

SMR-02 以降は**実 DB に登録・更新・削除を行う**。ローカルの開発 DB を前提にしているので、
共有環境では実行しない。

銘柄コードは一意な業務コードで、削除は論理削除（`取消区分=1`）。一度使ったコードを再登録したときの
挙動は仕様（`openapi.json`）に書かれていないので、**実行のたびに新しいコードを作って使い回さない**。
2026-10-02 の実測では **再有効化**だった（下の「検証の記録」）。素の新規登録を確かめるには未使用のコードが要る。

- 銘柄コードは `E2E-` で始め、後ろに実行時刻から作る英大文字・数字 8 桁を付ける（12 文字。`SymbolRequest` の上限は 14）。
  ティッカーコードは `E2E` + 同じ値の末尾 7 桁（10 文字。上限 10）。銘柄名（日本語）は固定の試験用の名前
- 備考には `marker()` の目印（`銘柄マスタ 実 API 接続確認（E2E が削除する）`）を入れる。編集（SMR-09 / 11）でもこの接頭辞は保つ
- 開始時（`beforeAll`）と終了時（`afterAll`）の両方で、`symbol=E2E-&include_deleted=true` の一覧を API で直接引き、
  **銘柄コードが `E2E-` で始まり `取消区分=0` の行を DELETE する**。前回が途中で落ちた残骸もここで片付くので、
  2 回続けて実行しても結果は変わらない
- SMR-10 の下ごしらえで、試験用の行に限って API から `市場名` / `前日出来高` を書き込む（画面から作れない項目のため）

**1 回の実行につき、`E2E-` で始まる取消済み（`取消区分=1`）の行が 1 件 DB にたまる**（途中で落ちた回は、次回の開始時に
論理削除される残骸の分も）。有効な行としては残らない。増えすぎたら DB から整理してよい（銘柄コードの接頭辞で絞り込める）。

SMR-02 以降は 1 本の流れ（登録 → 重複 → 編集 → 項目の保持 → 競合 → 削除）で、SMR-02 で登録した行を
後続が使う。**順に実行する**。途中だけを `--grep` で抜き出すと前提が崩れる。

## 編集・削除の前提（バックエンド待ち）

`docs/progress.md` の課題表では、編集・削除は次の 2 点で**バックエンド待ち**になっている（2026-09-16 起票）。
SMR-08〜12 は書いておくが、**検証モードで落ちたときはまずこの 2 点を疑い、バックエンド起因なら `保留` にする**。

1. **主キーが `id` になったが、実 API の詳細照会・更新履歴は `/masters/symbols/{symbol}` のまま。**
   `id` が空の行を編集・削除できない。→ SMR-08 は編集ボタンの `data-testid` が `symbols-edit-<数字>` になっていること、
   SMR-09 / 12 は送ったパスが `/api/masters/symbols/<数字>` であることを先に確かめ、`ID` が来ていない徴候を原因の判る形で止める
2. **更新で送らなかった項目（`市場名` / `前日出来高` / `Pre区分`）を保つかがバックエンドで確認中。**
   画面はこの 3 項目を送らない。→ SMR-10 が実 API の値を編集の前後で比べる

なお 2026-10-02 時点の `docs/api/openapi.json` は、詳細照会・更新履歴とも `/masters/symbols/{symbol_id}`（integer）で、
PUT の説明は「本文に含めた項目のみ更新し、含めなかった項目は既存値を維持する」になっている。
`src/api/symbols.js` の `toSymbolRequest()` のコメントにも「2026-09-25 に `備考` だけを PUT して `市場名` / `Pre区分` が残ることを実測」とある。
課題表のほうが古い可能性があるので、**SMR-08〜12 が通ったら課題表の 2 行を閉じてよいか本体セッションで判断する**。

## 行の指しかた（SMR-08〜12）

主キーは `ID`（integer のサロゲートキー）で、行の「編集」「削除」の `data-testid` は
`symbols-edit-<ID>` / `symbols-delete-<ID>` になる。`ID` は実 API の採番なので**値は実行時にしか判らない**。
SMR-02 の登録後に API を直接引き、実行ごとに一意な銘柄コードでその行の `ID` を特定してから使う。

一覧は銘柄コードの昇順なので、`E2E-` で始まる行が 1 ページ目に出るとは限らない。
**行を追いかけず、その銘柄コードで検索して 1 件に絞ってから操作する**（`SM-20` と同じ考え方）。
検索欄は実 API の `symbol`（銘柄コードまたは Ticker の部分一致）に乗るので、`E2E-<値>` は試験用の行だけに当たる
（ティッカーコードには `-` を入れていない）。
