# 銘柄マスタ

- 略号: `SM`
- 画面: `src/views/SymbolListView.vue`
- テスト: `e2e/symbols.spec.js`

`/masters/symbols` の受け入れ条件。ページ位置と検索条件は URL クエリ（`offset` / `symbol_code` /
`regulation` / `order_route` / `vwap_target`）を正としているため、**実ブラウザでの URL と画面の同期**を
ここで守る。

既定モックは有効な銘柄 56 件（1 ページ 50 件）で、並びは銘柄コードの昇順。先頭行は `S001`（AAPL）。
モックはこのほかに取消済み（論理削除）の行を 1 件持つが、既定の一覧には出ない。

**検索欄は 1 つで銘柄コードと Ticker の両方に当たるが、銘柄名では絞れない。** 実 API が
`銘柄コード` / `Ticker` / `銘柄名` を別々のパラメータに分けていて 1 語でまとめて探せないため、
この欄は `銘柄コード` にだけ乗る（モックのハンドラも同じ挙動）。利用者が驚きやすい仕様なので
SM-07 で固定する。

一覧・検索（SM-01〜SM-12）に加えて、ヘッダの「新規追加」からの登録（SM-13〜SM-20）・
行ごとの編集（SM-21〜SM-27）・行ごとの削除（SM-30〜SM-34）をこの画面の受け入れ条件に含む。
CSV 入出力と更新履歴は実 API にはあるが画面では扱わない。

登録は「サーバの事前検証 → 登録」の 2 段で、エラーの出し先が 3 系統に分かれる
（必須未入力は項目の直下 / 事前検証の不合格は箇条書き / 通信・サーバ障害は専用の表示）。
どの系統がどこに出るかを SM-14 / 16 / 17 で守る。登録の既定モックは追加した行を保持するため、
**登録後に件数が 1 増える**ところまで実ブラウザで見る（モックの状態はページを開くたびに初期化される）。
手本は[受注不可日マスタ](blackout-dates.md)の BD-11〜BD-18。

**追加した行が 1 ページ目に出るとは限らない。** 一覧は銘柄コードの昇順なので、入力したコードが
どこに挟まるかは決まらない。行を追いかけず、成功メッセージ（銘柄コードを含む）で受理を確かめ、
そのコードで検索して内容を見る（SM-20）。

**フォームは 10 項目で、`市場名` / `前日出来高` / `Pre区分` を持たない。** 画面から作れない項目は
送らず、サーバ側に委ねる。区分 3 つ（取引可否 / 預託先区分 / VWAP対象区分）は未選択を作らず、
実 API の既定と同じ値（`0`）から始める。

**ユーザー操作フラグが 1 の行には色が付く。** 自動取込のままの行と見分けるための印なので、
「色が付いている行がある」ことではなく「フラグ 1 の行だけ背景色が他と違う」ことを守る（SM-09）。

相場の 3 列は未取得を `null` で受け取り「—」で出す。0 と未取得の区別が消えていないことを
SM-11 で見る（フィクスチャでは 1 ページ目の `S021` が未取得の行）。

`mockApi()` は固定の body を返すだけで `offset` / `symbol` / 区分 3 つを解釈しないため、
ページングと絞り込み（SM-02〜SM-07）はクエリを実際に処理する既定ハンドラで見る。

編集は登録と同じ「サーバの事前検証 → 更新」の 2 段で、エラーの出し先も同じ 3 系統
（`data-testid` が `symbols-edit-…` に振り替わる）。更新は一覧取得時の更新日時を送り返す
楽観的ロック付きで、他の利用者が先に更新していればサーバが 409 を返す。409 は通信・サーバ障害と
同じ枠に出す（画面は 409 を特別扱いしない）ので、実ブラウザでは**その見えかた**だけを SM-26 で守る。

**銘柄コードは編集できない。** 主キーは `id` になって銘柄コードは一意な業務コードに格下げされたが、
実 API の詳細照会・更新履歴が `/masters/symbols/{symbol}` としてこの値で 1 件を指すため、
編集モーダルでは読み取り専用にする（SM-21）。そのため**事前検証の不合格を画面の導線からは
起こせない**（重複も存在エラーも銘柄コードを変えないと起きない）ので、SM-25 は
`mockApi()` で事前検証の応答を差し替えて出しかただけを守る。

**編集すると `市場名` / `前日出来高` / `Pre区分` が消える。** 画面がこの 3 項目を送らず、モックが
送られてこなかった項目を落とすため（一覧では前日出来高が `—` になる）。送らなかった項目を保つのは
バックエンドの責務で**まだ確認中**であり、モックはその未解決を隠さないためにこの挙動を持つ。
ただしこれはモック固有の振る舞いなので、**シナリオでは守らない**（SM-22 / 23 の期待結果も
これに依存させない）。確認が取れたらモックごと直す。

削除は実 API 側が論理削除（取消区分=1）で、一覧は既定で取消済みを返さないため、読み直すと行が消える。
登録・編集と違い**事前検証が無い**（DELETE は本文を取らない）のでエラーの系統は 1 つだけで、
サーバの拒否は確認ダイアログの中に出す（SM-33）。楽観的ロックも無い（`更新日時` を送らない）。
確認ダイアログが示す対象は日付のような 1 値では特定できないので、
**`銘柄コード / ティッカーコード / 銘柄名` を 1 行にして**出す（SM-30。CAマスタの CA-23 と同じ考え方）。
手本は[受注不可日マスタ](blackout-dates.md)の BD-19〜BD-23。

ローディングの過渡状態、送信中に「追加中…」「更新中…」「削除中…」となってボタンが押せなくなる過渡状態、
手で URL に書いた未知のコード（`?regulation=9` など）、表示件数の倍数でない `offset`、
`規制情報名` を欠いた応答は、画面の導線からは起こらない（または実ブラウザでは安定して
観測できない）ので単体テスト側の担保に譲り、ここには書かない。編集・削除についての分担は次のとおり。

| 論点 | E2E | 単体 | 理由 |
|---|---|---|---|
| 409 競合 | SM-26（PUT を 409 に差し替え、**見えかた**のみ） | STS-20（既定モックに古い合札を送り**検知ロジック**を通す）+ STV-30 | 実ブラウザで「他の利用者」を作るには 2 セッションが要る |
| 「更新中…」 | — | STV-31 | 応答を握る必要があり実ブラウザでは安定しない |
| 更新の 500 / 404 | — | STS-21 | 409 と同じ枠・同じ見えかたになる。404 は画面の導線からは起こらない |
| 絞り込み中の変更でのページ戻し | — | STV-34 | 空状態が一瞬挟まる過渡状態 |
| 追加と編集でエラーの枠が混ざらないこと | — | STV-32 | 片方のモーダルを開き直す操作が要り、E2E では回りくどい |
| 「削除中…」 | — | STV-39 | 応答を握る必要があり実ブラウザでは安定しない |
| 削除でのページ戻し | SM-34 | — | 編集側（STV-34）と同じ `stepBackIfPageEmpty()` なので、単体に二重に置かない |
