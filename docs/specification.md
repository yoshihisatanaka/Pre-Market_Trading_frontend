## 0. 本書の読み方

- 各仕様項目には根拠となる議事録の日付を `[MM/DD]` 形式で付記した（例: `[09/17]` = 2026-09-17 の議事録）。日付のない「第3回定例」は `[第3回]`（8月中旬〜下旬と推定）、IWI×INDP 保守運用体制打合せは `[IWI初回]`（8/24 直後と推定）と表記する。
- 同一論点で内容が変遷している場合は、**最新日付の議事録を正** とし、旧内容は「15. 主要論点の変遷」にまとめた。
- 議事録上で未決・仮決め・要確認とされている項目は、本文中に **【要確認】** を付し、「14. 未確定事項一覧」にも集約した。テストケース作成時は該当項目を「仕様確定待ち」として扱うこと。
- 社名・人名は議事録上でマスキングされており、ファイル間で同じ記号（【会社A】等）が同じ組織を指すとは限らない。本書では文脈から以下のとおり読み替えている。
  - AKTN / あかつき = 発注元の証券会社（ユーザー）
  - INDP = システムベンダー（本システムの開発元）
  - IWI = 運用保守（コンティンジェンシープラン実行）の委託候補先
  - IB = Interactive Brokers（米国側の執行ブローカー。TWS / TWS API を提供）
  - みずほ = IB 以外の預託先・執行先（一部銘柄のみ。「B銘柄」「みずほ銘柄」）
  - Dream（STAR Dream / Dream-S / DSB） = 証券基幹システム（フロコン設定・注文記録・残高・約定計上の正）
  - みんかぶ = CA（コーポレートアクション）情報の提供元
- 本書で「フロントシステム」「新フロント」「Web システム」は、本プロジェクトで新規構築する Web 発注システム（FastAPI）を指す。「Access ツール」「本体ツール」は既存の Access + RPA（Python）による米株発注約定ツール群を指す。

## 1. システム概要

### 1.1 目的

米国株式の 23 時間取引制度（米国時間 20:00 開始のプレマーケット〜翌アフターマーケット終了）に対応するため、プレマーケット注文の受付・IB への API 発注・リアルタイム約定確認を可能にする Web フロントシステムを構築する。あわせて、既存の Dream 直接入力および Access ツール群（VWAP 注文ツール・オーバーナイト注文ツール・締後注文発注ツール）による注文入力を本システムに集約する。`[07/23][08/24][09/07]`

### 1.2 全体構成（Ph.1）`[09/17][09/28][09/25][09/16]`

```
IFA / 営業店 / コールセンター
   │ ONEGATE（Entra ID）認証、IFA ポータルのリンクから遷移
   ▼
┌──────────────── Azure ────────────────────────────────┐
│ ② フロントシステム（FastAPI + MySQL）                       │
│    ・注文入力／照会／マスタ／フロコン                        │
│    ・発注データを Blob Storage（中継ストレージ）へ格納          │
│                  │ ファイル連携（API ではない）               │
│                  ▼                                        │
│ ③ TWS API 発注用端末（Azure VM、TWS/IB Gateway 常駐）        │
│    ・ストレージから注文データ取得 → TWS API で TWS に投入      │
│    ・注文ステータス／約定をコールバックで受信しストレージへ返却  │
│                  │ Blob Storage 経由                        │
│                  ▼                                        │
│ Dream 登録 RPA（Python）… 30 分定点で Dream に注文を登録       │
└──────────────────────────────────────────────────────┘
          │ TWS ⇄ IB サーバ（既存と同じ通信。本開発の対象外）
          ▼
        IB（米国市場）

AWS：Ph.1 では「注文ファイルの退避先」のみ（障害時に取り出して TWS 端末から手発注）
社内：既存 TWS ハンド操作用端末（CSV アップロード／手発注・状況確認用）
Access ツール群（本体ツール）：残高構築・約定処理・Dream 約定登録は当面継続
```

- 注文投入は Web 経由、最終発注はローカル（Azure VM 上）の TWS/IB Gateway 経由で行う。外部サーバから IB へ直接発注する設計ではない。`[09/09][09/28]`
- FIX API は IB の審査上利用不可（受発注専用ベンダーのみ）となったため、TWS API で実現する。`[09/25][09/28]`
- Ph.2 で AWS に同一構成をホットスタンバイとして構築し、Azure/AWS 冗長構成とする。`[09/16][09/25]`

### 2.3 休日・受注不可日 `[09/02][09/07][09/10][09/17]`

- 国内の受注休日（年末年始・ゴールデンウィーク等）は「休日マスタ（受発注日マスタ）」で管理し、該当日は注文入力不可とする。
- 米国祝日は「海外祝日マスタ」で管理する（半どん情報も同マスタに持つ）。
- 受注不可日（連休前日など当社が受注を止める日）は、プレ注文を入力しようとすると「受注不可日のため注文できません」エラーとする。アフター終了時点で残っている注文データは全件キャンセルを流す。
- Ph.1 では土日祝はサービス停止（参考株価・参考為替・前日終値・出来高・ユニバース銘柄・手数料優遇顧客等のデータは土日はスライドさせる作りとする方向で検討）。24 時間 365 日稼働とするかは継続議論。
- 「受注不可日明け処理対象一覧」帳票は祝日の取扱いが確定するまで継続出力する。

| 強制フラグ | フロコンで「エラー（強制可）」となった場合、確認済みフラグをチェックして発注可能にする（権限制御あり） |
| 注文送信時のチェック | 必須項目欠落時は送信ボタンを押下不可。属性ロック・口座ロック・銘柄取引可否・受付時間外（IPO 等の時刻制御を含む）は送信時に即時エラー |
| 送信結果 | IB からのリターン（Submitted／エラー）は即時に反映。失敗は注文照会で確認する（Ph.2 で送信中表示等の作り込み検討） |

### 3.4 取消・訂正 `[07/28][08/24][09/02]`

- Ph.1 の画面は「注文入力」と「取消」のみ。**「訂正」機能・文言は設けない。**
- 訂正は「取消 → 新規入力」で運用する（Dream の外国株仕様と同一。日本株は訂正可だが外国株は取消・差し直しのみ）。
- 取消後の画面表示：元注文の出来状況欄が「取消済み」に変わり、新規注文が下に並ぶ（親子関係でぶら下げる方式は採用しない）。
- 取消は注文照会画面から実行する。Ph.1 ではコールセンター（本店）および営業店（支店長権限）のみ実行可。IFA ログイン時は取消ボタンを非活性または非表示とする。`[09/10][10/01]`
- 修正（訂正）画面は Ph.1 納品に間に合わなくてもよく、後付け可能な作りとする（Ph.2 までに検討）。
- 取消は IB へ Cancel Order を API 送信し、Dream へは次回の 30 分定点で取消を登録する。

### 3.5 一部約定時の取消 `[07/28][09/02]`

- 一部約定した注文を取り消す場合：IB へ残数量の取消を送信し、Dream に対しては元注文を取り消したうえで「約定済み数量」で注文を 1 本登録し、IB の約定をその注文に付ける。残り数量分の余力は解放する。
- 受注番号（Dream）と IB オーダーリファレンス（例: `671_A0043`）の紐付けは本システム側で番号管理テーブルを持って対応する。
- 一部約定後の残数量に対する指値変更は、上記取消のうえ残数量で新規注文を入力する。

### 3.6 重複注文・数量チェック `[07/28][08/24]`

| チェック | 仕様 |
|---|---|
| 売却残数チェック | 売却数量 ≦（保有数量 − 注文中数量）。注文中の数量を加味する（例: 1,000 株保有・500 株注文中なら残り 500 株のみ発注可） |
| 買付重複アラート | 同一顧客・同一銘柄で買付注文が既に存在する場合、「他にも注文が出ており、両方約定する可能性がある」旨を画面表示する |
| 冗長承認（強制実行） | プレ注文が残っている状態でレギュラー注文を出す等、継続中注文がある場合は「この注文は継続中ですが、それでも発注しますか？」の確認を設け、強制実行フラグを立てて進める（運用判断） |
| VWAP 重複チェック | VWAP で発注済みの銘柄を委託でも重複発注していないかのチェックはフロント側で制御（Access 帳票は不要） |

### 3.7 発注上限（ハードリミット・3 倍ルール）`[08/24][第3回][IWI初回][10/01]`

- 注文上限は「前営業日基準の預かり資産の 3 倍」と「ワンショット 5,000 万円（仮置き）」のいずれか小さい方を適用する。
- ワンショットに加え、システム内累計（当日の米株注文合計 5,000 万円超）もチェックする。累計の対象は米株のみ（他商品はリアルタイム取得不可のため）。
- 3 倍ルールは Dream ではなく本システム（ツール）側のチェックで、前営業日基準の総預かり資産で判定する。当日入金分は顧客マスタで預かり資産額を補正して対応する（問い合わせベース）。`[09/10][10/01]`
- 上限超過時の運用（管理者承認・緊急連絡窓口）は **【要確認】**。
- 集計単位（顧客／口座／銘柄、対象ステータス）は **【要確認】**。

### 3.8 注文スライス `[第3回][09/07][09/10][09/17]`

- IB が大口注文（数量上限 50 万株、金額は非公開基準）を受け付けないケースに備え、内部処理で注文を自動分割（スライス）する機能を **実装する**。将来的に機能を無効化できること（無効時は「レギュラーのみの発注」が最低限残ること）。
- 閾値は「スライス基準マスタ（ハードリミットマスタ）」で AKTN が変更可能（市場関与率、現行 5%→3%・2% 等。現行基準は IB 基準の約 1/10）。
- スライス対象になりそうな注文はアラートを上げる作りも可能。
- スライスした注文の Dream 連携は現行同様に親子関係を持たせて管理する。
- スライス一覧の Access 帳票は廃止し、注文一覧画面のフラグ・フィルタ（スライス済み／マルチ等）で確認する。
- スライス機能を無効化した場合、または閾値内でも IB で弾かれた場合の自動再発注は行わない（手作業でスライス・再発注）。IB プライスアルゴの継続利用／エラー返却方式の選択は社長説明のうえ決定 **【要確認】**。

### 3.9 CSV 一括発注 `[07/28][第3回][09/10][09/17]`

- 大量注文（1 日 500〜600 件の IFA、同業証券会社からの注文）向けに、指定レイアウトの CSV をアップロードして一括発注する機能を設ける。
- テンプレートファイルを画面からダウンロードできること。
- アップロード時に必須項目を全件チェックし、**明細に 1 件でもエラーがあれば全体を差し戻し**（通過分のみ発注はしない）。
- 本店（コールセンター）限定機能とし、IFA 部店には表示しない（二重アップロード等の誤操作防止）。

### 3.10 VWAP 注文 `[09/02][09/07][09/10][09/17]`

- VWAP 注文は Ph.1 から本システムの発注画面に組み込む（専用画面は設けず、色分け等で区別し目立たない位置に配置）。
- 高権限者（VWAP 特殊権限ユーザー、3 名程度）のみ表示・発注可能。特殊権限はマスタではなくシステム内でユーザー（アドレス）を直接登録する画面で管理する。IFA が VWAP を直接発注することは想定しない（社長確認事項）。
- VWAP 取扱銘柄ファイルを取り込み、銘柄マスタの VWAP フラグが立っている銘柄のみ VWAP 発注可。
- VWAP はレギュラーのみの取扱い見込み（確認書の取得は別途必要）。VWAP の受付終了時刻・市場区分は **【要確認】**。
- VWAP は締めてネッティングした結果を発注するため、締めタイミングが必要（同一銘柄複数受注の合算）**【要確認：ネッティング要否と締め時刻】**。
- VWAP 関連帳票（IFA_VWAP エクセル・VWAP 結果・VWAP 約定明細）は継続出力。

### 3.11 みずほ注文 `[09/10][09/17]`

- みずほ銘柄のレギュラー注文はフロントで受注する（預託先がみずほの銘柄を選択した時点で、注文入力画面でプレ不可・期間指定（出合い）不可等を制御）。
- 「みずほ注文締め」ボタンで 17:00 に締め、締め後は注文入力を弾く。締め後に「注文ファイル作成」で現在 Excel で送付しているみずほ向けオーダーシートを作成する（約定照会画面で預託先＝みずほのデータを抽出してファイル作成）。
- みずほ分は Dream の受注番号が必要なため、Dream 登録同期でみずほ注文締め（17:00）までに必ず登録し切る。

### 3.12 銘柄単位の受付制御 `[07/28][09/02][09/17]`

- 銘柄マスタの「取引可否」を不可にすると、その銘柄は日中でも即時に注文不可となる。
- IPO 銘柄等、特定時刻（例: 22:00）まで受付したくない銘柄は、銘柄マスタに受付開始時刻を持ち、注文送信時に「受付時間外」エラーを返す（プルダウンの都度切替は行わない）。新規 IPO は銘柄マスタに新規追加して登録する。
- CA 発生銘柄は Dream 残高が反映されるまで発注禁止とする（取引可否で制御）。CA ハルト・上場廃止等は IB／市場側でエラーが返るため、リアルタイムでエラーが判別できる前提。
- 新規上場銘柄は Dream で注文入力可能な状態にしてから銘柄マスタへ反映する（Dream 未登録のまま発注すると Dream 登録でエラーとなり「Dream 注文失敗」ステータスになる）。

## 4. フロントコンプライアンス（フロコン）仕様 `[10/01]`

### 4.1 基本方針

- 現行 Dream の抑止照合設定（設定シート 170〜180 項目のうち米株該当 31 項目）と同じものを本システムに実装する。原則そのまま採用。
- **判定データは前日夜締め時点**（属性・入出金状況）。当日の入金・属性変更はリアルタイム反映されない（Dream との最大の相違点）。
- エラー種別は 3 段階：

| 種別 | 挙動 |
|---|---|
| ワーニング | 注意喚起のみ。通常手順で発注可 |
| エラー（強制可） | ワーニングより強い表示。「確認済み」強制フラグをチェックすると発注可（承認権限者） |
| エラー（強制不可） | 発注不可 |

- Ph.1 ではコールセンターは同一権限（承認者 1／2 の区別なし）。9/17 時点では現行締後発注システムと同様の 2 段階承認（上長承認）の踏襲が検討されたが、Entra ID に承認権限の項目がなく Ph.1 では実現不可のため同一権限とした（Ph.2 での権限区分実装は調整中）。`[09/17][10/01]`IFA には強制権限を渡さない（Ph.2 でも IFA 自身に強制させず、コールセンターへ電話して確認後に強制発注する案が有力）。
- 締後注文ツール・VWAP ツールで実装している独自フロコン（年齢 85 歳以上のワーニング／エラー等）を取り込むかは **【要確認】**。
- 3 倍ルール（3.7）はフロコンとは別にツール側でチェック。

## 5. データ仕様（残高・顧客・銘柄・為替）

### 5.1 日次バッチ（朝）`[08/24][09/03][09/07][09/10]`

- 毎朝 9:00 までに、Dream から前日基準の残高・顧客属性・銘柄属性・未入金等を取り込み、フロント用データを洗い替える（約 1 時間）。この間フロントは起動したまま、バックエンド側で準備・切替を行う。
- 朝 9:00 時点のフロント残高の算出式：

```
フロント残高 = Dream 前日残高 ＋ 前日約定分 ＋ 権配明細リクエストから取得する CA 情報 ＋ 権配明細の EB 債償還情報
```

- 当日入庫分（他社移管・EB 債入庫等）は朝 9:00 には反映できない。入庫確認（IB は夏時間 13:00／冬時間 14:00 のステートメント確認後、みずほは連絡受領後）の後に「残高補正」で数量を増やし、その後に売却可能とする（預かりがない状態での売却を避ける）。
- 残高構築は Access（本体ツール）で継続し、計算結果だけをフロントへ連携する。
- Ph.1 のフロントは預託残（IB／みずほ別の内訳）を保持せず、顧客ごとの顧客銘柄台帳（保有数量）のみを保持する。預託先別の残高超過（IB マイナス残）の検知は Access 側で行う（10 章）。`[09/07][09/10]`
- バッチの完了／未完了（終了予定時刻超過）通知はメール・Slack で AKTN・INDP（・IWI）に飛ぶ。`[09/25]`

### 5.2 残高補正・売却不可 `[09/07][09/10][09/17]`

| 機能 | 仕様 |
|---|---|
| 残高補正（数量加算） | 顧客単位・銘柄単位で外国株保有数量を補正する。画面個別入力に加え、CSV アップロード（ダイレクト入庫ファイルをそのまま取り込む形）で一括反映できること（1 日 1 回でも可）。事故処理・緊急的な残高不一致対応にも利用 |
| 新規加算 | システムに存在しない銘柄を保有しており売却したい場合は、新規行として加算 |
| 売却不可区分 | 預り明細から銘柄ごとにフラグを立て、売却不可にする（同一銘柄の一部数量のみの制御は想定しない）。Dream 取込時に既に売却不可区分が立っている場合はその情報も取り込み、預り明細でグレーアウト表示 |

### 5.3 株式分割・併合・CA `[07/28][09/07][09/17]`

- 株式分割の権利落ち日時点では既存保有分のみ売却可。分割で増加する数量は入庫（転配）処理完了後に売却可能とする。
- 株式併合銘柄は取引停止措置（Dream でも弾かれる）。
- CA 情報はみんかぶから受領するファイル（5〜6 シートを 1 シートに加工済み）を取り込み、CA マスタとして閲覧する（取り込んで確認する程度の用途）。CA 情報確認用ファイル（移管チーム閲覧用）と SCSK への送付は現行機能を残置する。
- CA ハルト（米国 CA 発表に伴う売買停止制度）については、CA 情報・当社独自停止リストに基づく銘柄停止制御をマスタで行う。正式なハルト情報は米国時間 9:00 想定で取得経路未確定 **【要確認】**。

### 5.4 顧客マスタ `[09/10][09/17][10/01]`

- フロント表示用の顧客情報を保持する（前日基準で毎朝 Dream から自動取込・上書き）。
- **新規顧客登録**機能を実装する（当日開設口座から当日発注するケース用。最低限の情報で緊急登録）。
- **編集（属性変更）**機能は緊急時用の本社機能として実装する。変更可能項目はフロコンで使う項目（コンプラランク、不着ロック等の取引抑止に関わる項目、預かり資産額の補正）に限定し、氏名・住所は対象外。NRI（Dream）側への反映は連動しない。IFA 等フロント側では変更不可。運用上は属性変更を原則行わず、Dream で属性変更を確認したうえでコールセンターが強制発注する運用を基本とする。対応可能時間帯（コンプラ在席時間）は運用ルールとして整理 **【要確認】**。
- 顧客詳細表示項目：非課税枠、コンプラランク、前日の資産状況、年齢、外貨預り等。

### 5.5 銘柄マスタ `[07/28][09/07][09/10][09/17]`

| 項目 | 内容 |
|---|---|
| 取込 | ユニバース銘柄ファイル（約 2,300 銘柄）をファイル取込。VWAP 取扱銘柄ファイルで VWAP フラグを更新 |

### 8.3 注文ステータス管理 `[09/09][09/16]`

- IB の Order State / Status（Pending Submit → Pre Submitted → Submitted → …）の遷移をコールバックで受信し、都度ステータスを更新する。**Submitted をもって IB への到達とみなす**。
- 本システムのステータス（例）：受注済み → 市場執行待ち（レギュラーのみ注文がプレ時間中に貯まっている状態。IB には存在しない）→ 執行中（Submitted）→ 約定／一部約定／取消済み／注文失敗／Dream 注文失敗。
- IB 障害時等に「市場執行待ち」のまま止まった注文を別ルート（TWS 手発注）で執行した場合、本システム側のステータスを手動で強制上書きできる機能を用意する。
- 到達確認は TWS GUI（既存端末のペンディングオーダー表示）でも可能。独自画面での到達確認要件は **【要確認】**。

### 8.4 約定取込 `[07/28][08/24][09/16]`

- 約定は IB からのプッシュ（約定通知）でリアルタイムに取り込む（ポーリングではない）。IB は約定を分割で返すため、都度積み重ねて管理する。
- みずほ分のみ別ファイル（翌朝 10 時頃のコンファメーション取込・Access）。
- 翌朝の約定処理（Access）では、プレ・レギュラー両方を含む IB コンファメーションファイルを正として取り込み、注文内容は本システムから連携してコンファメーション ID で紐付ける。アフター対応後はコンファメーションを「IB プレ・レギュラー」「みずほレギュラー」「IB アフター」の 3 系統に分けて 2 段階で約定付けする。
- 証跡として API 取得の約定結果とクライアントポータルのコンファメーションを日次で照合したい（要望）。

### 8.5 CSV（バスケットトレーダー）

- 滞留注文を TWS バスケットトレーダー向け CSV で出力・アップロードする障害時ルートを用意する（12.3 参照）。発注プログラム起動中の CSV 取込可否、CSV による大量取消の可否は **【要確認：IB 側一次調査では取消は不可の可能性】**。

## 9. Dream 連携仕様 `[07/23][07/28][第3回][09/02][09/10][09/17]`

- 本システムは Dream のフロコンを経由せず IB へ直接発注し、Dream へは事後に注文情報を登録する（当初の「Dream 登録→フロコン通過後に IB 発注」方式は撤回）。
- Dream 登録は Python RPA シナリオ（Dream 注文入力）で行う。Blob Storage 経由で注文データを受け渡す。

| 項目 | 仕様 |
|---|---|
| 周期 | 30 分定点（貯まった発注・取消を一括で Dream に登録）。周期（30 分／1 時間／1 日 1 回）はボリュームを踏まえて確定 **【要確認】** |
| 開始 | 前日約定の出来付け処理が終わる 11:00 頃から |
| 終了 | 18:30 頃まで（Dream 注文入力可能時間。実際は 19〜20 時まで入力可） |
| みずほ注文 | 受注番号取得のため、みずほ注文締め（17:00）までに必ず登録し切る |
| 登録内容 | 発注と取消のみ。約定はつけない（約定登録は翌朝の Access 処理） |
| ステータス | 登録待ち／エラー／済み。エラー時は原因（属性・口座）を整備後、ステータスを「登録待ち」に戻すと次回定点で再登録 |
| 一部約定取消 | 3.5 のとおり元注文取消＋約定分 1 本登録 |
| スライス | 親子関係で管理 |
| Dream フラグ | プレ注文識別用に「伝達済み区分」を使用する方向（引合番号は VWAP 用。メモ欄も利用可）**【要確認：直接発注方式へ変更後も同じ項目を使うか】** |
| 新規上場銘柄 | Dream に銘柄が未登録だと Dream 登録エラー（「Dream 注文失敗」ステータス）。マスタ追加銘柄は Dream 投入を遅らせる等の考慮が必要 **【要確認】** |
| 電子出しフラグ | すべてフロントから発注する前提のため、別途保持しない `[09/07]` |
| 手書き伝票 | 全注文がツール経由となるため原則不要。仲介補助簿は Dream の注文データを正として代替（コンプラ最終確認待ち）**【要確認】** |

## 10. 約定・後続処理（Access 本体ツール）`[08/24][09/07][09/10]`

- 残高構築、約定処理（出来登録・不出来登録・照合）、Dream への約済み登録（RPA）、為替確定後の約定登録は当面 Access ツールで継続する（Ph.3 で Web 化を検討）。
- プレ注文の約定は夜間レギュラー注文と同様に翌営業日扱いとし、翌日の 10:15 為替で約定を付け、11 時頃に Dream へ約定投入、翌朝 Dream からデータ取得という現行スケジュールを踏襲する。
- Bloomberg の価格取得は、店頭廃止に伴いアフター終値が不要になるため、レギュラー引け後 15〜30 分程度で取得可能に変更する。締め処理で使用する単価はレギュラー引け値でよい。
- 本体ツールに預託先残高照合機能を追加する：IB／みずほそれぞれの預託先残高を日次で差分検証し、IB 銘柄なのにみずほにしか残高がない等（IB マイナス残）の場合に、みずほ→IB への振替を業務担当にアナウンスする（画面または帳票）。
- 「Dream 残高＋約定＋入出庫−IB 残高」による残高確認プロセスは現行どおり。

## 12. 運用・障害・コンティンジェンシープラン `[08/24][09/03][09/16][09/17][09/25][IWI初回]`

### 12.1 運用体制

| 項目 | 内容 |
|---|---|
| Ph.1 | 発注は最長 20:00 まで（コールセンター対応）のため IWI の運用部隊は不要。障害時はコールセンターが受注を手動で止め、IB 専用端末（TWS）からの手発注に切り替える |
| Ph.2 以降 | IWI が 24 時間体制で一次対応（運用保守＝発注業務の継続。事前に取り決めたエラーコード・手順に基づく対応に限定。原因究明・改修は INDP）。INDP は在籍時間帯（8 時頃〜18 時頃）にシステム保守。手順に載っていない事象は翌営業日に INDP が対応 |
| 通知 | バッチ／RPA 失敗を INDP の Slack と AKTN へのメール（AKTN メールサーバ利用）で自動通知。IWI の運用チームにも同通知を飛ばし、自動でチケット起票 |
| 納品物 | エラーコード一覧・エラー内容一覧、運用マニュアル・操作手順書（コンチプラン、障害通知、代理発注手順、切り分けフロー）は INDP が作成 |
| 定時作業 | TWS の週次再認証（AKTN 管理の方向）、サマータイム切替のバッチ時刻変更（INDP 作業） |

### 12.2 障害時の機能要件

| 機能 | 仕様 |
|---|---|
| 緊急停止（受注抑止）ボタン | 最高権限者のみ押下可。全利用者を発注禁止にする。2 パターン：①注文入力自体を不可にする、②入力は受け付けるが IB へは送らない（受注情報を残す必要がある場合。重複発注防止） |
| 案内表示 | 受注抑止中はコールセンターへの電話案内等を画面表示 |
| 滞留注文の抽出 | 本システムに入っているが IB に届いていない注文（市場執行待ち・IB エラー）を、TWS バスケットトレーダー向けレイアウトの CSV で出力。エラーメッセージとあわせて銘柄・数量等の発注に必要な情報を自動出力 |
| 手動ステータス更新 | TWS で手発注した注文について、TWS の約定結果（コンファメーション DL）を取り込んで本システムのステータス（執行済み・約定）を更新。個別の強制上書きも可 |

| Dream 登録エラー | Dream 登録状況画面で再ラン |

### 12.3 障害ケース別の対応方針（Ph.1 → Ph.2）

| 障害箇所 | Ph.1 | Ph.2（AWS ホットスタンバイ） |
|---|---|---|
| アプリ層のみ | Azure 上のアプリ再起動を試行。セッションが切断されていなければ Cancel on Disconnect は成立しないため Azure 復旧を優先 | 同左。AWS は待機 |

| VPN／ネットワーク | 滞留注文を CSV 出力し TWS 手発注 | 同左 |
| IB 側障害 | IB の API 以外の口（TWS 画面）が使えれば手発注。IB 全体停止はやむを得ない | 同左 |
| TWS 端末のログイン切断 | 手動再ログイン（担当者・手順を明確化） | 同左 |
| 切り戻し | — | Azure 復旧後は基本的に Azure へ切り戻す（当日は AWS、翌日 Azure） |
