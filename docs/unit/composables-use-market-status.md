# composables/useMarketStatus（市場状況の時計と定期再取得）

- 略号: `UMS`
- 対象: `src/composables/useMarketStatus.js`
- テスト: `src/composables/useMarketStatus.spec.js`
- ストア側のシナリオ: [stores-market-status.md](stores-market-status.md)
- 表示内容の組み立て: [utils-market-status.md](utils-market-status.md)

`AppHeader` のヘッダが「開いてから一度も更新されない」「画面を離れてもタイマーが動き続ける」を
起こさないための土台。この文書のスコープは **2 本のタイマーと後片付け** だけに絞る。

- **毎分のティック**（60,000ms）… `now` を進めるだけ。現在セッションの判定はローカルで済む
  （サーバがくれる `JPN開始` / `JPN終了` は tz 付きの絶対時刻なので比較するだけ）
- **5 分ごとの再取得**（300,000ms）… `store.load()` を呼ぶ。日付を跨いだときと、
  運用中に海外休場日マスタが編集されたときに追いつくため

セッションの境界・休場・短縮取引・取得失敗時の見え方は `toMarketDisplay()` の担当
（`MKS-14`〜`MKS-27`）なので、ここでは作り直さない。期待値もラベル文字列を書かず、
`toMarketDisplay()` の戻り値と突き合わせる。

時刻はレギュラーの終了境界をまたぐように置き、マウント時刻をその 30 秒手前にする。
こうすると「まだティックが来ていない」と「ティックが来て再判定された」を値の差で区別できる。
再取得の検証は `store.load` を差し替えて行い、**通信は起こさない**
（フェイクタイマーと axios のタイムアウトを噛み合わせないため）。

| ID | 前提 | 操作 | 期待結果 | 状態 |
|---|---|---|---|---|
| UMS-01 | ストアに通常営業日の応答が入っている / 現在時刻がレギュラー終了の 30 秒前 | `useMarketStatus()` を呼ぶホストをマウントする | 戻り値の `.value` が、その時刻の `toMarketDisplay()` と同じ（初回表示に 1 分待たない） | 実装済 |
| UMS-02 | UMS-01 の状態 | タイマーを 59,999ms 進める（レギュラーの終了を越えている） | `.value` は初回のまま（1 分未満では再判定しない。時計を直接読み直していないことが分かる） | 実装済 |
| UMS-03 | UMS-01 の状態 | タイマーを 60,000ms 進める | `.value` がその時点の `toMarketDisplay()` と同じ値に変わる（レギュラー → 終了後） | 実装済 |
| UMS-04 | 1 回目のティックでは境界に届かない時刻でマウント | 60,000ms を 2 回進める | 各回の時点の `toMarketDisplay()` と一致し続ける（1 回きりではなく間隔ごとに繰り返す） | 実装済 |
| UMS-05 | UMS-01 の状態 | アンマウントしてから 60,000ms 進める | 保留中のタイマーが 1 本も残らず、`.value` はアンマウント時のまま | 実装済 |
| UMS-06 | 2 つのホストを別々にマウント | 片方だけアンマウントし、60,000ms 進める | 残った側は更新され続ける（後片付けが自分のタイマーだけを止める） | 実装済 |
| UMS-07 | `store.load` を差し替え、呼ばれたら休場の応答を入れるようにする | 300,000ms 進める | `store.load` が呼ばれ、取り直した内容が `.value` に反映される（「○ Closed」＋休場理由）。60,000ms では呼ばれない | 実装済 |
